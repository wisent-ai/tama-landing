Session-scoped enable

How does Tama change what runs in a live agent session — and why can it only ever make policy stronger there? Through one narrow mutation: enable a hook, or every hook, in exactly one session, applied not by Tama but by that session's own supervisor. There is no per-session disable, by contract (core-contracts).

What it is

A private file-based request/response exchange in ~/Library/Application Support/Tama/session-control/ (directory mode 0700, files 0600). Tama writes <controlKey>.<requestId>.request.json and polls every 0.05 s, for at most 10 s, for the matching <controlKey>.<requestId>.response.json. The request carries schema (ai.wisent.tama.session-control.v2), sessionId, controlKey, requestId (UUID), confirmed: true, operation, and for set-hook the hookId with enabled: true. The response carries schema, requestId, ok, error, and state — the authoritative session record after the change.

Two operations exist, but they are not interchangeable:

  • set-hook — enable one registered hook id in this session. During a global emergency disable, the preflight and write must observe the same nonempty emergency changedAt generation;
  • enable-all — outside a global emergency disable, enable every registered hook and schedule one runtime reload after the active agent turn settles. Concurrent reloads coalesce, and a failure restores the preceding override state. While the global emergency disable remains active, this operation is refused with global-emergency-disable-active.

Retrying the same single-hook enable in the same emergency generation is idempotent.

Who applies it

The session's own supervisor — never Tama. The supervisor validates the envelope against the exact identity tuple in its session record (enforcement-control): the controlKey is a 64-hex secret, the agentId must start with an ASCII letter and be 1–32 characters, and the record must be live (process mode: the pid answers kill(pid, 0); heartbeat mode: updatedAt within heartbeatTTLSeconds, clamped to 5–3600, default 900). It applies the override atomically as <controlKey>.override.json and answers with the resulting state.

What can refuse it

Every failure is actionable, never optimistic. The public refusal states include:

| Failure | Sentence or reason | |---|---| | Malformed session identity | Tama rejected an invalid agent session control endpoint. | | Unparseable response | The agent runtime returned an invalid session-control response. | | Only v1 records on disk | Tama found only legacy v1 session records. Reinstall the verified bundled runtime, then stop or resume the affected agent session to publish v2 state. | | Supervisor said no | The agent runtime rejected the session-control request: <reason> | | 10 s deadline passed | The agent runtime did not acknowledge the session-control request before the deadline. | | Session exited mid-request | The agent session ended before the session-control request completed. | | Disabled state has no usable generation | global-emergency-state-missing-generation | | Emergency state changes during one-hook activation | emergency-state-changed-during-activation | | Enable-all requested during global disable | global-emergency-disable-active |

Composition with machine enforcement

Session enablement is additive to the machine policy (enforcement-control):

  • in all-hooks mode, every registered hook already runs;
  • in selected-hooks mode, a hook runs when its id is in the machine selection or this session's enabledHookIds. A session cannot remove an id from the machine selection;
  • during a global emergency disable, the machine selection is bypassed. enabledHookIds is the session's explicit allowlist, but only when the override's emergencyChangedAt exactly equals the active emergency state's nonempty changedAt. Those are the only hooks that run.

The supervisor persists that generation binding beside the allowlist and in the OMP session's retained override entry. Reloading or resuming the same session preserves the exact enable while the emergency generation is unchanged. A fresh global disable creates a new generation: legacy overrides with no binding and stale overrides from an earlier generation contribute no enabled hooks or capability. tama-cli sessions and the desktop therefore render the supervisor's already-sanitized enabledHookIds, not an old allowlist copied from disk.

Runtime status

The session record and tama_hook_runtime_status publish enforcementMode (all or only) and machineEnabledHookIds, the validated, sorted registered ids selected by the durable machine state. These sit beside enabledHookIds, which remains the session's additive state. Under emergency disable, the machine ids stay visible as retained configuration but do not run.

Where it surfaces

  • The Session screen renders the live record and can request one-hook or enable-all mutations. Enable-all remains a normal-state reload operation and reports the supervisor's refusal during a global emergency disable (desktop/session).
  • The Hooks inspector calculates Enabled from enabledHookIds when the selected session is globally disabled, and from disabledHookIds otherwise. Its single-hook action uses the same generation-bound control path (desktop/hooks).
  • Inside an OMP session, the bundled adapter exposes the same plane as session tools: tama_set_session_hook, tama_enable_all_session_hooks, tama_hook_runtime_status, tama_request_session_capability, tama_reload_hook_runtime — and states that session hook disablement is prohibited.

Reload support and refusals

The deferred reload tool requires OMP to expose ctx.requestReload. When that API is unavailable, it returns OMP does not expose deferred runtime reload requests; the runtime keeps reloadPending: false and continues using the previously loaded release. Installing a new release does not repair that missing API or make the running session use the new code.

The existing /tama_reload_hook_runtime slash command uses OMP's command-handler ctx.reload() instead. Run it in the same session to reload without restarting the process; it does not enable every hook or lift the global emergency disable. Then read tama_hook_runtime_status: the installed and loaded release ids and checksums must match, and each requested hook must be present in the effective enabled ids. A queued request, successful installation, or unchanged process id alone does not prove that the new rules are running.

Completion hooks enabled through this control

Installed prompt text can tell an agent to keep working, but prose does not execute the completion contract. A completion rule runs only when its registered Stop hook is enabled and the runtime dispatches that event. For the repaired completion contract, block-stop-with-open-work deterministically replays the latest successful tracker snapshot and subsequent successful tracker calls, then blocks while any item remains pending or in progress. check-open-items-with-model independently sends the real user messages, bounded current-turn tool evidence, and proposed final response to Tama's existing objective reviewer.

The reviewer must block for even one executable unfinished item or one task error without later evidence of repair. It passes completed work, a requested read-only/direct answer, work the user explicitly stopped or restricted, and work whose only remainder is genuinely external and unavailable. It does not treat a heading, a success claim, or the proposed final response as proof.

The reviewer keeps the existing settings: credentials are read through Skarbiec from tama-objective-authority-model-router and agent:wisent-app; Brama defaults to https://brama.wisent.com/v1/chat/completions with model route -best, agent identity wisent-app, temperature 0, max_tokens: 160, a 3-second connect timeout, and a 25-second total timeout. Missing transcript or credentials, transport/HTTP failure, and an invalid verdict are not silent permission: the hook prints TAMA_HOOK_INFRASTRUCTURE: check-open-items-with-model: <reason> and exits 70.

Not to be confused with

  • Disabling. The opposite direction exists only as the machine-global, operator-confirmed emergency disable. Agent-facing controls never weaken policy.
  • A capability. Enabling changes which hooks run; a capability grants what the session may do under the hooks that run. They travel in the same session record and are otherwise independent.
  • Installing. Outside global emergency disable, enable-all binds its override to the installed release and checksum, but it does not install anything; a session running an older release needs the reload that enable-all schedules, not a new install.
