tama find-violations

Replays the shared content and file-size hooks, reporting the first violation per file and one finding per crowded folder without modifying the repositories. The CLI, repair command and MCP tool use the same scanner.

Invocation

tama find-violations (--repo <path> | --tree <dir> | --owner <gh-user-or-org> | --me) [...]
                     [--json] [--summary] [--size-only] [--hook <path>] [--clone-dir <dir>]

Targets are repeatable and combinable. --repo names one directory; --tree discovers Git checkouts; --owner uses gh and shallow-clones missing repositories; --me selects the authenticated user and their organizations. --hook overrides the replayed hook, --clone-dir changes the clone cache, and --json selects structured reports.

The file-size rule is read from block_oversized_files.sh beside the selected hook. A custom hook directory must contain that companion file; an unreadable or failing hook appears in errors and makes the scan fail. Each file is enumerated once, the 300-line boundary is checked, and .tama-violations-ignore applies to both content and size checks. The repair command uses this same result, so an oversized file cannot disappear from its work list.

The line limit does not apply to structured data, a drawing or a manuscript, and the scan answers exactly as the hook does: .json, .jsonl, .ndjson, .toml, .yml, .yaml, .lock, .csv and .tsv are documents a loader reads whole — splitting a registry or a product catalogue breaks its reader — .svg is one picture a renderer wrote, and .tex, .bib, .sty, .bst and .cls are one document with the venue's own length. A file under migrations/ is exempt too: it states what already ran, under the name the database recorded. The exemption is the format, not the name: toml_reader.rs is still source.

The folder limit leaves a database's own directories alone for the same reason — supabase/migrations and supabase/seeds hold numbered documents loaded in name order, which a sub-folder would rename — along with node_modules, .git, __pycache__, tests and any migrations directory.

The folder limit also counts only files somebody wrote and somebody else has to find again. A screenshot, a recording, an icon, a font, a drawing or an archive is not a module: spis keeps one folder per journey holding official-recording.mp4 and one state-NN.png per state the journey passed through, so that folder's file count is the number of states, and "move files into sub-folders or consolidate" asks for something that cannot be done to two screenshots. Until 2026-09-21 the scan printed skip … (binary content) for those very files in the line pass and then counted every one of them in the folder pass — 267 of spis's crowded folders were captures. The modules beside a capture still count: four modules and twenty screenshots leave room for a fifth module, and the sixth is refused. The audit asks the guard itself, block-crowded-folders, so the two can never answer differently.

Whose repositories are scanned

A --tree sweep scans the checkouts this workshop owns. A checkout whose origin names another GitHub owner is somebody else's product — oh-my-pi belongs to can1357, sits here because we use it, and every edit to it is refused by the guards — so the sweep names the owner and scans nothing inside. It was 1800 of the 3282 files the machine-wide sweep reported over the line limit and 238 of its crowded folders, none of them ours to move. An explicit --repo still scans whatever it is pointed at, and a checkout with no origin, or one on a host that is not GitHub, stays ours: an unpublished repository is nobody else's.

A skip is not a failure. It prints as SKIPPED <owner> <path> where a failure prints PROBLEM, the summary's last line says how many checkouts in the tree are owned elsewhere, and only real failures raise the exit status — a workshop with nothing left to fix has to be able to finish at zero while those checkouts sit beside it. A copy of somebody else's project that lives inside one of our repositories is a different case: it has no origin of its own, so the repository declares it in .tama/violations-ignore with the owner written beside it, the way wisent-ios declares the five upstream Swift packages vendored into the app.

Which hook is replayed

Without --hook, Tama looks for shared-hooks/pre_write_edit.sh in the checkout it resolved, and then for ~/.shared-hooks/pre_write_edit.sh, the copy tama install writes and the one enforcing policy on this machine. The compiled-in checkout path is the release's export tree, which the release deletes after the build, so before this fallback every scan started outside a tama checkout refused with a path that no longer existed. When neither place has a hook, the refusal keeps its first line, hook not found: <path>, and then names both places it looked and the ways forward: install the guards, name one with --hook, or run --size-only.

--size-only answers the two size rules — one file over 300 lines, one folder over 5 files — in this process, over the same enumeration and with the same sentences, so it needs no hook at all and finishes a whole tree in seconds instead of hours. A --hook named alongside it is reported as not replayed. --summary prints one row per repository, worst first. Use the fast pass to choose what to fix, then re-scan that one repository without it for the content rules the hooks own.

Which checkouts a tree claims

--tree decides by provenance, not by a list of directory names. A checkout whose .git is a file is a linked worktree or a submodule, so its content belongs to the repository that owns it and it is not a target of its own. A checkout inside a path its owning repository ignores was written by a package manager, a cache or a scratch run — that ignore rule is the owner's own statement about provenance — so it is skipped too. Dependency and build directory names are still pruned, but only to keep the walk cheap.

Two checkouts that share an origin remote are one repository: the shallowest path is kept, with a lexicographic tie-break so the answer never depends on walk order, because fixing the source fixes every clone of it. A checkout with no origin remote is nobody's copy and is always kept, and a repository named with --repo is never deduplicated away.

Output and state

Text mode groups findings by rule and ends with repository, violation, and discovery-problem totals. JSON returns repos, problems, and totals. Exit 0 means no violations or problems; any violation or discovery problem exits 1. Command-gating rules are out of scope because they inspect shell commands rather than file content.

Refusals and failures

Missing targets, empty or missing option values, and unknown arguments print usage and exit 2. Missing paths produce exactly hook not found: <path>, repo not found: <path>, or tree not found: <path> and exit 2. When discovery yields no repositories, Tama writes no repositories found; it exits 1 if discovery also reported a problem, otherwise 0.
