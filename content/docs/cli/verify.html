tama verify

Runs the native release verification harness bundled next to the Tama CLI.

Invocation

tama verify

The command has no required input or public options. It resolves tama-require-live-runtime beside the running CLI and starts it with the selected Tama root as its working directory.

Output and state

The harness owns its output and runs two stages, in this order.

Catalog validation first, because a catalog the release itself rejects makes every scenario result meaningless. It is the same verdict tama validate prints — validate_catalog plus the wired-but-uncatalogued check — reported as catalog validation: <n> hooks, <n> errors, <n> warnings. Errors are listed one per line as ERROR <sentence> and the stage refuses with INVALID CATALOG: the release's own catalog validation fails, so no live scenario result would mean anything. Fix the errors above, or run `tama validate` for the same list., exit 1, before a single fixture runs. Warnings do not stop it.

Live hook fixtures second: every claimed runtime and editor path exercised with real execution and captured payloads, ending in one JSON report and either REAL RUNTIME COVERAGE COMPLETE or INCOMPLETE REAL RUNTIME COVERAGE: …. Tama exits with the harness exit code; a signal or spawn failure maps to exit 1.

The fixtures need every catalogued hook to run — they assert which hook fired and read the payload another hook captured — so the harness does not read this machine's hook selection (enforcement). It points TAMA_HOOK_ENFORCEMENT at a path of its own under .live-runtime-tmp/ that does not exist, the state the reader treats as no selection, and reports it as enforcement state for this run: <path> (absent: every catalogued hook runs). An explicit TAMA_HOOK_ENFORCEMENT in the environment is left alone. A run under a machine selection instead fails every scenario whose hook or capture shim sits outside it, with an empty payload list.

What a complete run needs

Every claimed runtime has to be usable on the machine, and a runtime that is not answers as a failed scenario rather than a missing prerequisite: an unauthenticated Claude CLI surfaces as Claude stream-json did not include expected Bash tool_use carrying Not logged in · Please run /login, a Codex CLI that cannot run reports real Codex runtime did not report expected hook block: status=null, and the editor scenarios need the editor adapters live. The two global Git scenarios expect a dirty-worktree refusal from the user-global dispatcher, which by contract runs the repository's own .githooks/<name>, the archived per-repository hook, or a preserved backup and nothing else (hook-releases), so a temporary fixture repository matching none of the three is not refused.

Until 2026-09-07 the harness ran only the second stage while this page and the command summary promised both, so a release could verify green with a catalog tama validate rejects.

Refusals and failures

If the native harness is not installed next to the CLI, Tama writes exactly tama-require-live-runtime not found next to this binary and exits 1. The command has no fallback to the removed Node CLI.
