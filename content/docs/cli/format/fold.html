tama format fold

Folds the formatters' form into the unpublished commits that wrote each file: rustfmt's for Rust files, and for any other file the form of the formatter the commit's own tree declares for its extension in .tama/formatters.json (see tama standing). The push gate (check-rust-format) refuses a push whose commits carry Rust files rustfmt would write differently, a repository's own format gate refuses its other files, the commit review charges the session that commits a file out of its formatter's form, and it refuses a commit that only reformats, so the formatting belongs inside the commits that wrote those files. tama format fold puts it there.

Invocation

tama format fold [--repository <PATH>] [--through <COMMIT>] [--reword <COMMIT> --message <FILE>]... [--json]

Without --repository it folds the checkout the command runs in.

--through <COMMIT> formats only the unpublished prefix up to and including that commit. For example, tama format fold --through HEAD^ --json formats through the previous commit and carries the last commit without running its formatters. Later commits keep their source changes, messages, authors, dates and attestation notes, with rewrite records when their parents change. This does not qualify those later commits or bypass a push or reference-move review. It lets an earlier source dependency be prepared independently of an unfinished later target. Without this option every unpublished commit is formatted as before.

What it does

It reads the branch the checkout has checked out, its head, and the commits between the branch's upstream and that head, oldest first. For each commit it writes out the commit's tree in the checkout's ignored build directory (.build/tama-rust-format), runs rustfmt on every Rust file the commit adds or changes, under that file's edition and the tree's own configuration, exactly as the push gate checks it, and keeps each file rustfmt wrote differently. The commit is then written again on its (possibly folded) parent with the same message, author, committer and dates, its own changes laid on that parent through a private index, and its formatted files in rustfmt's form. A commit after the first folded one is carried onto the folded parent even when it needed no formatting of its own. Commits before the first one that needed formatting keep their identities. A commit's note under refs/notes/attestation is copied to the commit that replaces it.

Every other file the commit adds or changes whose extension the commit's tree declares a formatter for is run through that formatter in the written-out tree, with the file's path appended to the declared argv; its standard output is the file's formatted text, and a file it writes differently is folded like a Rust file. A tree that declares no formatter leaves its other files as they are; a declaration that cannot be read or parsed, an entry with an empty argv, and a formatter that fails refuse the fold with the cause.

A commit whose own changes were only the form rustfmt writes, such as a commit that formatted what an earlier unpublished commit wrote, has nothing left once that formatting is folded into the earlier commit: it is dropped, with its note, and the commits after it are carried onto its parent. A commit that was empty before the fold is kept.

A manifest target the commit does not hold yet, such as a [[test]] whose file a later commit adds, is a target that does not resolve in that commit, like one whose modules do not resolve: a file that target alone would place is refused naming it and the cause the manifest declares <path>, which this commit does not hold, and every other file of the commit is formatted.

A merge in the unpublished range is written again when it records only published history: every parent but its first is a commit the upstream already holds, and its tree is its first parent's, as when the remote took a change on an older base and the checkout merged it back with nothing of its own. It is written on its folded first parent with the same published parents, so the published commits it merged stay merged. Any other merge refuses the fold.

--reword <COMMIT> --message <FILE> writes that unpublished commit again with the message the file holds instead of its own, whether or not its files needed a formatter, for a message that must change, such as one that names what a public repository may not carry. Each --message belongs to the --reword before it, and the option may be given for several commits. The reworded commit keeps its tree, author, committer and dates, the commits after it are carried onto it, and it carries the same rewrite record as a folded commit. Its attestation note is not carried, because the note attests the message it replaced: attest the reworded commit again after the fold.

Every commit the fold writes, and the commit a dropped one is folded into, carries a rewrite record: a note under refs/notes/rewritten listing, one per line, the ids of the commits it stands for and of those they stood for. Formatting changes a commit's patch, so nothing matching patches can follow it; the record lets the branch-move review (review-ref-move) and oko defects rebased follow a commit the defect register names to the commit that replaced it.

The branch review reads the rewrite-note listing once per move and obtains all note bodies with one git cat-file --batch call. It checks which standing commits the proposed head can reach once, then answers each replaced commit from memory. The replacement index is limited to the dropped commits requiring protection and borrows their identifiers. Unrelated records do not allocate entries or copy replacement identifiers into that index. A protected commit without a reachable rewrite record still requires author and patch comparison. A note on an unreachable commit cannot authorize removing a repair. Malformed headers, missing or truncated note bodies, mismatched object identifiers and invalid UTF-8 refuse the move with the affected note and cause instead of silently ignoring it.

The branch moves to the folded head only from the head the fold read. When Git's effective reference-transaction hook is Tama-managed, the fold invokes that same dispatcher in reference-move preflight mode: the full review runs before Git prepares the ref transaction. A private admission binds the exact branch and old/new tips to the Git child and its observed process start, and prepared checks it without walking history or querying Oko again. Ordinary Git keeps its own hooks when no Tama dispatcher owns the operation. After the move, every rewritten path follows the new head in the index and working tree only where it still held the old content; another session's changes are preserved. The upstream and published commits are never rewritten.

Reference-move preflight

The installed reference dispatcher declares ownership with # tama managed global Git dispatcher and support with # tama reference-move preflight. These are installer-emitted protocol identities, not executable-name or directory-name guesses. Both tama format fold and stado release history resolve the effective hook through Git and invoke that file with move REF NEW OLD MESSAGE. Its own declared runtime performs the review; a different Tama on the caller's PATH is not substituted. The preflight entrypoint is tama hook review-ref-move move REF NEW OLD MESSAGE and requires a current, executable managed dispatcher.

A legacy managed dispatcher without the preflight declaration, an unreadable hook or a hook this caller cannot execute refuses before the branch move. Update the dispatcher through Tama's supported installation and the operator's existing release consent; there is no automatic installation, raw-Git retry after a failed preflight, or environment variable that disables review. With no managed dispatcher, the caller uses ordinary Git and its existing hook chain.

Git may point its hooks location at a file rather than a directory. That location has no reference hook, just as a missing hooks directory has none; the fold uses ordinary Git without changing that configuration. Tama resolves the hooks directory through Git before appending the hook filename, so Git's path canonicalization cannot mistake a non-directory location for a failed history review. Other read errors remain refusals naming the hook and the operating-system cause.

The review asks about all dropped commits in one register question. The admission binds the Git process id and its measured start in both its filename and body, so PID reuse cannot overwrite or remove another process lifetime's admission. It also binds the remote refs and rewrite-note ref observed before review; prepared refuses a changed observation, another process, another branch plan or reuse. Git still compares the expected old tip atomically. Ordinary Git moves without an admission retain the full review; they are not exempted.

After Git succeeds and the parent verifies that prepared consumed the exact admission, the parent follows named revisions and returns {"kind":"tama reviewed reference move","reference":"<REF>","old":"<OLD>","new":"<NEW>"}. Callers require that typed result to match their plan, including valid names requiring JSON unescaping; an empty successful answer is not completion evidence. An already-current old/new tip is confirmed without creating a transaction or admission. Input-write failures report the observed branch rather than mistaking an empty successful Git process for a completed move. The parent reports follow and receipt-removal failures because Git ignores failures from a committed hook.

A refusal before the move leaves the branch unchanged. A failure after Git moved it explicitly names the new state; it is not described as an unreferenced folded head. The fold still reconciles its index and working files against that observed new head without replacing another session's changes, and reports any reconciliation failure with the move diagnostic. No failed follow silently rolls back the branch.

Output

One line per rewritten commit, <old> -> <new>: <files>, naming the files that were formatted, or carried onto the folded parent for a commit that needed none, followed by ; written with the message given, so attest it again for a reworded commit, and <old> dropped: … for a dropped commit. When nothing needed formatting it says so and rewrites nothing. --json prints {"repository": …, "folded": [{"old", "new", "files", "reworded"}]}, new being null for a dropped commit and reworded saying whether the commit was written with the message given.

Refusals and failures

Exit 0 is success, exit 1 a refusal or failure, exit 2 a usage error. Each refusal names its cause:

  • the checkout's head names no branch to fold — the head is detached.
  • <branch> has no upstream to mark what is already published — nothing says which commits are unpublished.
  • the unpublished range … holds merge <commit>, which a fold does not rewrite: it merges <parent>, which <upstream> does not hold, or …: its tree differs from its first parent's, so it carries a change of its own — the merge brings history or a change no published commit holds.
  • no formatter was run: … — Oko's ruling does not admit running build tools on this product; the ruling is quoted.
  • <branch> is at <observed> rather than the folded head <new> because … names a concurrent move or refusal. <branch> is now at <new> … but the move reported: … distinguishes a completed branch move whose post-move work failed; the cause and any index or working-tree failure remain visible.
  • commit <commit> is not an unpublished commit of this branch, so it cannot be reworded; nothing was rewritten — --reword named a published commit or one off the branch.
  • --reword <commit> names no commit: …, --reword <commit> has no --message, --message <file> follows no --reword of its own, cannot read the message file <file>: … and the message file <file> is empty — the reword request is incomplete; nothing is rewritten.
  • --through <commit> names no commit: … or --through <commit> is not an unpublished commit of this branch; nothing was rewritten — the inclusive boundary must resolve to an unpublished commit of this branch. A published, unknown or off-branch boundary is refused before formatting or moving the branch.
  • --through needs a commit or --through may be given only once — supply exactly one boundary when using the option.
  • A manifest or edition that cannot be read, a scratch directory Git does not ignore, and a Git or rustfmt command that fails are named with their command and output, as the push gate names them.

The real journey tests/format/fold.rs runs the built tama against a published remote and a checkout with unpublished commits:

cargo test --manifest-path rust/Cargo.toml -p tama-cli --test format_fold

The separate real managed-chain journey is tests/release/history/preflight.mjs in Stado's repository, run with node --env-file .build/history-preflight.env --test tests/release/history/preflight.mjs. Its environment file declares STADO_BIN, STADO_TEST_SOURCE_REVISION, TAMA_TEST_RUNTIME_ROOT and TAMA_TEST_SOURCE_REVISION from the candidates under qualification. It runs Stado history and Tama folding through the actual installed dispatcher, uses Git Trace2 ancestry to require history review outside the actual ref transaction, checks final refs/trees/index/upstream and spent admissions, exercises a quoted ref and no-op, refuses stale/legacy/unexecutable cases, then verifies independent Git operation after uninstalling only its isolated hooks. Commands, exit statuses, streams, source identities, executable digests and trace remain under Stado's ignored build area. Missing prerequisites are blocked, never reported passed. Named-defect migration additionally requires the real Oko journeys above; this flow does not substitute for them.
