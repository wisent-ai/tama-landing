tama format fold

Folds rustfmt's form into the unpublished commits that wrote each Rust file. The push gate (check-rust-format) refuses a push whose commits carry Rust files rustfmt would write differently, and the commit review refuses a commit that only reformats, so the formatting belongs inside the commits that wrote those files. tama format fold puts it there.

Invocation

tama format fold [--repository <PATH>] [--json]

Without --repository it folds the checkout the command runs in.

What it does

It reads the branch the checkout has checked out, its head, and the commits between the branch's upstream and that head, oldest first. For each commit it writes out the commit's tree in the checkout's ignored build directory (.build/tama-rust-format), runs rustfmt on every Rust file the commit adds or changes, under that file's edition and the tree's own configuration, exactly as the push gate checks it, and keeps each file rustfmt wrote differently. The commit is then written again on its (possibly folded) parent with the same message, author, committer and dates, its own changes laid on that parent through a private index, and its formatted files in rustfmt's form. A commit after the first folded one is carried onto the folded parent even when it needed no formatting of its own. Commits before the first one that needed formatting keep their identities. A commit's note under refs/notes/attestation is copied to the commit that replaces it.

The branch moves to the folded head only from the head the fold read: a commit made meanwhile refuses the move, the branch stays where it is, and the folded commits are left unreferenced. After the move, every path the fold rewrote follows the new head in the index and in the working tree only where it still held the old content; a change someone staged or made in the working tree is kept as it is. The upstream and every published commit are never rewritten.

Output

One line per rewritten commit, <old> -> <new>: <files>, naming the files that were formatted, or carried onto the folded parent for a commit that needed none. When nothing needed formatting it says so and rewrites nothing. --json prints {"repository": …, "folded": [{"old", "new", "files"}]}.

Refusals and failures

Exit 0 is success, exit 1 a refusal or failure, exit 2 a usage error. Each refusal names its cause:

  • the checkout's head names no branch to fold — the head is detached.
  • <branch> has no upstream to mark what is already published — nothing says which commits are unpublished.
  • the unpublished range … holds merge commits, which a fold does not rewrite.
  • no formatter was run: … — Oko's ruling does not admit running build tools on this product; the ruling is quoted.
  • <branch> moved while the fold ran, so it stays where it is and the folded commits are left unreferenced.
  • A manifest or edition that cannot be read, a scratch directory Git does not ignore, and a Git or rustfmt command that fails are named with their command and output, as the push gate names them.

The real journey tests/format/fold.rs runs the built tama against a published remote and a checkout with unpublished commits:

cargo test --manifest-path rust/Cargo.toml -p tama-cli --test format_fold
