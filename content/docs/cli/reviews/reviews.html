tama reviews

Inspect the results retained by Tama's model review of a commit before it is created (tama hook review-commit) without repeating it, calling a model or changing provider credentials. A push is not reviewed by a model and retains nothing: review-push reads the attestation each commit carries (tama attestation). The Reviews screen reads the same records.

Invocation

tama reviews list [--json]
tama reviews show <id> [--json]
tama reviews harsh record|dispose|show [...]
tama reviews admitted --commit <rev> [--repository <path>] [--json]
tama reviews cutover [--repository <path>] [--json]

The harsh review rounds every commit needs from a reviewer that is not its author are recorded and read with tama reviews harsh. The Harsh-Review-Rounds: line a let-through commit is given joins its message's last paragraph when every line there is a Git trailer, as the Harsh-Review-Attacked: lines are, and starts that paragraph otherwise: Git reads trailers from the last paragraph alone, so a line set apart would leave the attack trailers unread and review-push would refuse the commit for lacking them.

Who made a commit

Git keeps the author a commit names, which every agent session on one machine shares. So when review-commit admits a candidate at commit-msg it keeps what it admitted for the git commit process making it (the process holding the checkout's commit lock, or, with none held, the hook's own parent): the staged tree, the committing session and the rounds line, in <git common dir>/tama-admissions/pending/<git pid>.json, and says on stderr review-commit: admitted tree <tree> as <agent> session <id>'s commit (or as the operator's own commit). A candidate that cannot be kept refuses the commit, since nobody could say afterwards who made it. Only once the same process has moved a ref to a commit carrying that tree does the managed reference-transaction dispatcher's tama hook commit-admission committed "$PPID" keep it as that commit's admission, in <git common dir>/tama-admissions/commits/<commit>.json, and say commit-admission: commit <sha> keeps its admission; at aborted the candidate is dropped. So a candidate that never became a commit (refused by a later hook, a failed write) is no commit's admission, and an amended commit has its own, under its own id and parent. The admission is {commit, parent, tree, committer, rounds, admittedAt, committedAt}. committer is {agent, session, carried}: the agent session whose recorded process runs the commit, or, for a commit started outside every session's process tree, the running session whose recorded edits its index carries (carried true); it is null for the operator's own commit. parent is null for a root commit. rounds is the Harsh-Review-Rounds: line the commit was let through with, null when the declared judge decided alone.

tama reviews admitted --commit <rev> prints committed by <agent> session <id> (or committed by the operator: no agent session made it), commit <sha> (tree <tree>) after <parent>, admitted at <time>, committed at <time> and the rounds line; --json prints the admission itself. --repository names the checkout, the current directory by default. A commit with no admission (made before admissions were kept, with --no-verify, with plumbing, or through hooks that are not the managed dispatcher's, none of which keeps one) is refused with commit <sha> (tree <tree>, parents [<parents>]) has no admission at <path>; a call without --commit is refused with the invocation. The native request reviews/admitted takes {"repository", "commit"} and returns the same admission; the Desktop Reviews screen's Admitted commit panel uses it.

Where admissions start

A commit made before review-commit kept admissions has none, so no rule that a pushed commit carries one can judge it. The first candidate review-commit admits in a repository therefore also keeps, once, the commit at the tip of every local branch then, in <git common dir>/tama-admissions/cutover.json: the file is written beside its place and linked there only where none is kept, and never rewritten. tama reviews cutover prints admissions started at <time>; every commit these tips hold was made before them: and the tips; --json prints {"at", "commits"}. In a repository where review-commit admitted nothing yet it is refused with reviews cutover: review-commit admitted no commit in <path> yet, so no cutover is kept and no pushed commit is judged by its admission, exit 1; an unreadable register is refused naming its path. The native request reviews/cutover takes {"repository"} and returns {"cutover": {"at", "commits"} | null}; the Desktop Reviews screen's Admission cutover panel uses it.

review-push refuses a pushed non-merge commit that no cutover tip holds when it has no admission and no rewrite record (refs/notes/rewritten, which tama format fold and tama history rebase write) naming only replaced commits that have one or that a cutover tip holds: review-push: BLOCKED: <local ref> -> <remote ref>: commit(s) <sha>, … were made after admissions started here (<time>) with no admission from review-commit and stand, by no rewrite record, only for admitted commits: …. A squash made with plumbing, whatever bytes it changed and whether or not the branch it replaced still exists, is refused so. A replaced commit Git has since pruned stands only by its admission. Real journey: tests/review/squash/unadmitted.rs.

Use an exact ID from list. It is a retained exchange identifier, not a repository path. Inspection uses Tama's existing per-user state directory; it accepts no alternate home or arbitrary record path.

Outcome and cause

OutcomeMeaning
passThe reviewer passed this exchange. This is not proof that Git subsequently created the commit.
source_findingA grounded finding refused the commit. detail names the actual finding and required repair.
review_failureThe review operation failed. detail names its Git, provider or protocol cause. This does not establish a source defect.

A missing or malformed result is shown as unreadable, never as a passing review. An exchange still in progress, or one retained before result recording was available, can have an unreadable result; the reader reports the actual file error rather than guessing which condition applies.

Structured results

list --json returns {directory, records}. Each record, also returned by show --json, has {id, directory, result, error}. Exactly one of result and error is non-null. A result is {outcome, detail}: passing reviews have null detail; refusals retain a nonempty cause. The directory identifies the retained envelope and answer.

The CLI exits successfully when every selected record was readable, even when its recorded review refused publication. An unreadable entry makes inspection exit unsuccessfully while preserving all listing rows. A missing or unreadable root refuses the whole operation with its path and operating-system cause; it is not an empty listing.

Refusals

  • Unknown commands or arguments print the supported invocations.
  • A path, parent component, empty ID or normalized alias refuses with invalid retained review id. An ID containing NUL also refuses before filesystem access: NUL cannot be part of an entry name. Native JSON requests report this as invalid input, not an unreadable review record.
  • A missing record remains an unreadable row naming the missing directory. Inspection never creates it.
  • Symbolic-link records and result files are refused instead of intentionally traversed. The reader also refuses non-directory records and non-file results.
  • JSON decode errors retain the result path and parser cause. Unknown outcomes and invalid outcome/detail combinations are not successful records.

Native requests

tama request reviews/list takes an empty object; tama request reviews/show takes {"id":"<retained-id>"}. They return the same listing or record in the normal native response envelope. Per-record read failures stay in error, so one unreadable exchange does not hide the others.

Quickstart: understand a refused commit

  1. Follow installation and first use, then configure a model provider and install the managed Git dispatchers. Inspection itself makes no provider request.
  2. In your own repository, make a normal commit through the installed gate. A refusal prints review retained at <directory>. Do not manufacture a broken commit merely to inspect a failure.
  3. Run tama reviews list, then tama reviews show <id> for that exchange, or select it in Desktop → Reviews.
  4. For a source finding, inspect the named message or staged text. For a review failure such as subscription_reauthorization_required, repair the named provider operation through its documented account flow; rewriting source cannot repair authorization.

The real managed-commit journey exercises inspection against its actual retained refusal and verifies path, native NUL-input and missing-record refusals.
