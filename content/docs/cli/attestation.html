tama attestation

Keeps the attestations an agent records for itself. Every commit carries its own: an attestation that the commit meets the push reviewer's standard, carries no private information and is a general primitive rather than a one-off fix. review-push refuses a push while any commit it adds lacks one that stands, and the commit gate refuses git commit while the commit it builds on lacks one; the tip of a push speaks for no commit under it. On a machine that declared no model (tama model-provider set --none), a session's attestation says its task is finished and the stop gates read it in place of a model's judgement, so a session can end and a commit can be pushed with neither Brama nor any other model installed.

Invocation

tama attestation record --file PATH (--session ID | --commit REV [--repository PATH]) [--json]
tama attestation show (--session ID | --commit REV [--repository PATH]) [--json]
tama attestation list [--json]
tama attestation remove (--session ID | --commit REV [--repository PATH]) [--json]
tama attestation standard (--session ID | --commit REV [--repository PATH]) [--json]

Every verb but list names one subject: a session by its id, or a commit by any revision Git resolves in --repository (the current directory when it is not given). A commit is kept under its full name, so a short and a full spelling find the same record.

  • record judges the JSON document in --file against its subject's standard and keeps it only when it stands. Recording again replaces the kept record; a refused attestation leaves the kept one as it was. Records live under the Tama state root, in attestations/session/<id>.json and attestations/commit/<full commit>.json.
  • show prints the kept record and how it stands against today's standard.
  • list prints every kept record, sessions first, and how each stands today.
  • remove deletes the kept record.
  • standard prints every claim the subject's attestation must confirm, each as attestation: claim <key>: <claim>, then each list that must stay empty as attestation: empty <key>: <why>; with --json, {"kind", "id", "standard": {"required": [{"key", "claim"}], "must_be_empty": [{"key", "why"}]}}.

Quickstart

$ tama model-provider set --none
provider: none
$ tama attestation record --file done.json --session "$SESSION"
attestation: session <session> stands
attestation: recorded at ~/Library/Application Support/Tama/attestations/session/<session>.json
$ git commit -m "second change"   # the commit gate refuses: the commit it builds on carries no attestation that stands
$ tama attestation standard --commit HEAD   # the claims to attest, in words
$ tama attestation record --file first.json --commit HEAD
$ git commit -m "second change"
$ git push            # review-push refuses: commit <sha> needs its own attestation
$ tama attestation record --file push.json --commit HEAD
attestation: commit <sha> stands
attestation: recorded at ~/Library/Application Support/Tama/attestations/commit/<sha>.json
$ git push            # passes
$ tama attestation list

What an attestation holds

{
  "attestations": {
    "<claim key>": {"confirmed": true, "how": "…"},
    "…": {"confirmed": true, "how": "…"}
  },
  "next_steps": [],
  "harsh_senior_review_findings": []
}

Every claim the subject's standard declares must be present with "confirmed": true and a how that explains, in the agent's own words, how the claim holds, in at least the number of words the operator stated (attestation_min_words in the stated-numbers declaration, with his words beside it). Every list the standard names must be present and empty.

A session: standards/task.json

  • read_what_the_user_really_wants — the messages, what they mean beyond their words, and what the user refuses.
  • read_existing_rules_and_earlier_answers — the rules and the user's earlier answers on this subject, none of them broken.
  • wrote_real_tests_that_passed — real tests of the actual product, its success path and refusals, passing.
  • analyzed_how_it_fits_other_tasks — what it unblocks, what it touches, what of the other tasks and defects remains.
  • fixed_the_cause_not_the_symptom — the same failure does not return for the next case.
  • cli_gui_docs_match — the CLI, the GUI and the documentation carry the same behaviour.
  • delivered — committed and pushed, with what a release still needs named.
  • no_blockers_task_fully_closed — nothing blocks the task.
  • nothing_further_is_possible_even_with_operator_work — even with the operator's own work there is nothing further.
  • harsh_senior_review_performed — as a very strict senior engineer who hates AI, what was attacked, what was checked, and why each attack failed.

Lists that stay empty: next_steps (a step that continues the task is the task's work, asked for or not) and harsh_senior_review_findings (every finding means the task is not finished).

A commit: standards/commit.json

The push reviewer's own standard: every pushed message and patch read line by line; no defect; no needless abstraction or duplication; no swallowed error or fallback; no guessed number; no failure hidden by pausing, waiting or retrying; no narrating comment, host, account, date or internal id; tests that exercise behaviour; no commit that only reformats or patches another; documentation that matches the code; and the harsh senior review performed, with harsh_senior_review_findings empty. Two claims answer the operator's own questions about every commit:

  • no_private_information — no line and no message carries private information of ours: no host, account, person, address, secret, token, session or defect id, and no detail of an incident; what it says would be the same in a repository anyone can read.
  • no_one_off_solution — the commit solves no problem of ours alone: it adds or repairs a general primitive a user outside Wisent could run for their own case, not a fix shaped to one of our machines, accounts, runs or incidents.

Every commit, not the tip

review-push lists every commit the push adds over what the remote holds and refuses at the first whose own attestation is missing or no longer stands, with commit <sha>: <reason>; with a model declared, the reviewer reads the push only after every commit is attested. The commit gate in pre-bash refuses git commit while the repository's HEAD, not yet held by the branch's upstream, carries no attestation that stands: BLOCKED: the commit this one builds on, <sha>, carries no attestation that stands (<reason>). Each commit carries its own: attest it with `tama attestation record --file FILE --commit <sha>` …. A repository with no commit yet, and a HEAD the upstream already holds, pass. A record kept before a claim was added no longer stands and names the missing claim.

What is checked needs no model: presence, confirmation, length and the empty lists. Whether the words are true cannot be decided without a model; they stay on record, and a false one is the agent's defect.

Output

record prints attestation: <kind> <id> stands and attestation: recorded at <path> and exits 0; otherwise attestation: <kind> <id> does not stand and every reason on its own line, exit 1, and nothing is kept. show and each list entry print the same lines for the kept record; list with nothing kept prints attestation: no attestation is recorded. remove prints attestation: removed <path>. With --json each verb prints {"kind", "id", "stands", "refusals", "recorded"}; show adds the document under attestation, list prints an array of them, and remove prints {"kind", "id", "removed"}.

Tama Desktop

The Install screen's Attestations section records a chosen file for a session or for a commit in a chosen repository, shows or removes the record the form names, shows the subject's standard (every claim its attestation must confirm, in words, and the lists that stay empty) with its Standard button, and lists every kept record with its verdict and a Remove button. It sends tama request attestation/record with {"attestation": {...}, "session": "<id>"} or {"attestation": {...}, "commit": "<rev>", "repository": "<path>"}, attestation/show, attestation/standard and attestation/remove with the same subject, and attestation/list. The answers are the --json documents above with the same sentences; a refused attestation is an answer ("stands": false), not a failed request. A commit always names its repository, since the Desktop has no working directory to look it up in.

Refusals

  • attestations.<key> is missing: attest "<claim>"
  • attestations.<key>.confirmed is not true: the attestation does not stand while "<claim>" does not hold
  • attestations.<key>.how is missing: explain in your own words how "<claim>" holds
  • attestations.<key>.how explains in N words how "<claim>" holds; the operator asks for at least M
  • <list> names N item(s); <why>: <the items> and <list> is missing: write it as a list, and attest only when it is empty (<why>) — each of these makes record exit 1 with nothing kept.
  • Flags that do not fit the verb, refused with the usage text before anything is read, exit 2: record needs --file PATH: the attestation to judge and keep, name what the attestation attests: a session by its id or a commit by its revision, an attestation is a session's or a commit's, not both: name one of them, a repository names where a commit is looked up, and no commit is named, show reads the kept record, so it takes no --file (and the same for remove), list prints every kept record, so it takes only --json, <verb> is not a verb of tama attestation, <flag> is not an option of this command, <flag> needs a value, <flag> is given twice, and no verb at all.
  • Values that name nothing, or state that cannot be read or written, exit 1: "<id>" is not a session id: a session id is one plain name, neither empty nor a path, <rev> names no commit in the repository at <place>, the attestation <file> cannot be read: <cause>, <file> is not JSON: <cause>, the attestation stands but <path> cannot be written: <cause>, the recorded attestation <path> cannot be read: <cause> or is not JSON: <cause>, <path> is not an attestation record: the directory holds only <id>.json files.
  • no attestation is recorded for <kind> <id> (looked for <path>): record one with `tama attestation record --file FILE --<kind> <id>` — show or remove with nothing kept, exit 1.
  • At a stop gate with no model declared, in review-push for each pushed commit, and in the commit gate: <kind> <id> needs its own attestation, and none is recorded: write it and record it with `tama attestation record --file FILE --<kind> <id>`, or <kind> <id>'s recorded attestation does not stand: <reasons>; a stop hook payload with no session_id is refused as an infrastructure failure, and a commit gate that cannot read Git or the record refuses with BLOCKED: whether the commit this one builds on is attested cannot be read: <cause>.

Tests

tests/task-attestation/ runs the built binary in an isolated home: record.rs (a session attestation recorded, shown, listed, replaced and removed; a missing claim, an unconfirmed and short claim and non-empty lists each refused with nothing kept; every malformed command refused with its cause), no_model.rs (set --none, check refused, a stop gate refusing without and passing with a recorded attestation), push.rs (a real repository's commit refused by review-push without an attestation, an attestation with a finding refused and not recorded, the push passing once one stands, refused again after remove, and passing after the Desktop's attestation/record names the repository; then an attestation missing no_private_information and one missing no_one_off_solution each refused naming the claim, git commit refused by pre-bash while the commit it builds on is unattested, and a two-commit push whose attested tip does not carry the unattested commit under it) and desktop.rs (the Desktop's record, show, list and remove requests with the terminal's sentences).
