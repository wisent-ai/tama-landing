tama provider-config

Prints the hook block an install writes into a provider's configuration: the wiring that makes a Claude or Codex event reach the installed runtime.

Invocation

tama provider-config --provider <claude|codex> --dispatcher <command> [--json]

The registry arrives on stdin, so the caller decides which registry is being described — an install pipes the one it is about to write, and a person can pipe ~/.shared-hooks/registry.json or a source tree's copy. The dispatcher is the command that runs the installed hook dispatcher, pinned Node included; every printed command runs it for exactly one hook id through TAMA_ONLY_HOOK_ID.

Output

Without --json the summary names the provider, the dispatcher, the total number of commands, and each provider event with its matchers:

provider: claude
dispatcher: /opt/homebrew/bin/node --require '…/node-runtime-preflight.cjs' '…/.shared-hooks/run-hook.mjs'
commands: 100
  PostToolUse: Bash
  PreToolUse: Bash, apply_patch|Edit|Write, MultiEdit, Read, …
  SessionStart: compact
  Stop: *
  UserPromptSubmit: *

--json prints the block itself — provider event key to groups of { matcher, hooks } — which is what install_hook_release.py merges into ~/.claude/settings.json and ~/.codex/hooks.json (hook-releases). The event and matcher table is the one tama_hook_tools::registry owns, so a config can never disagree with the registry installed beside it.

Refusals and failures

Each of these exits 1 and writes nothing to stdout:

  • provider-config produced no wiring for <provider>: the registry declares no event this provider supports — the block would have been empty, which is a config that enforces nothing.
  • provider-config does not configure the provider <name>; it configures claude and codex
  • provider-config could not parse the registry on stdin: <detail>, or provider-config requires a registry object on stdin
  • provider-config requires a non-empty --dispatcher command

A missing --provider or --dispatcher prints the usage text and exits 2.
