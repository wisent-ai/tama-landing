tama index repair

Reads a checkout's Git index against its object store, its HEAD and its working tree, and names every entry that would break or falsify the next commit; with --apply it repairs each in place. An index that names an object the store does not hold makes git status, every diff and every commit of the checkout fail, and Tama's commit review replays a session's edits against that index, so one such entry stops every commit of the repository.

Invocation

tama index repair [--repo <checkout>] [--apply] [--json]

Without --repo it reads the checkout the command runs in. The index read is Git's own, or the one GIT_INDEX_FILE names; when that variable is set the answer says so, because it need not be the checkout's own index.

What it reads, and what --apply does

  • Missing objects. Each entry whose object the store does not hold. With --apply an object another checkout of the workspace holds under the same id is copied from there (read with git cat-file blob, written with git hash-object -w, the id checked equal); with none, the path is staged again from its working file, or removed from the index when the working file is gone, and the answer names the staged content as lost.
  • An emptied index. An index with no entry while HEAD tracks files reads every tracked file as staged for deletion, and one plain commit deletes the repository. With --apply it is read back from HEAD (the index only), so every working file keeps its changes.
  • Foreign entries. A staged path HEAD does not track and the working tree does not hold: no edit in this checkout produced it. With --apply it is taken out of the index; its object stays in the store and the answer names it.
  • Dropped entries. A path HEAD tracks, missing from the index, whose working file is present and not ignored. With --apply its entry is read back from HEAD, which loses nothing. A path stopped being tracked on purpose is ignored by then and is left alone.

Foreign and dropped entries are repaired with one git reset -q HEAD -- <paths> with literal pathspecs, which writes the index only. Without --apply nothing is written.

Output

The first line is <checkout>: <n> index entries, <n> naming an object the store does not hold. Then, as each applies: read the index <file> that GIT_INDEX_FILE=<value> names, not necessarily the checkout's own; the emptied index, read back or with the --apply that reads it back; one line per foreign or dropped entry, <path> [<object>]: <foreign|dropped>, read back from HEAD or …, run with --apply to read it back from HEAD; and one line per missing object, <path> <object>: copied from <checkout>, …: <repair>; its staged content is lost or …: missing (run with --apply to repair). With --json the same report as one document: {repository, index, index_variable, entries, missing: [{path, object, copied_from, repair, lost}], emptied: {head_entries, restored}, strays: [{path, shape, object, repaired}], applied}.

Tama Desktop's Index repair panel, under Reviews, sends the same reading as the request index/repair with {"repository": <checkout>, "apply": <bool>}: Read index reads it and Repair index applies.

Refusals

  • tama index needs its verb; tama index repair [--repo <checkout>] [--apply] [--json], and <word> is not a verb of tama index; ….
  • --repo needs a checkout; …, and <word> is not an option of tama index repair; … for any other word or an option given twice.
  • the current directory cannot be read: <cause> without --repo.
  • Git's own refusal, with the command it ran, when the index, the store or HEAD cannot be read, and git ls-files -s gave an entry without a path: … or … without an object: … for an entry it cannot read.
  • A path whose state in the working tree cannot be read is refused naming the path.

Journey

tests/index-repair/emptied.rs runs the built tama on a repository of its own. An emptied index is named with how many files HEAD tracks and stays empty without --apply; with --apply it is read back from HEAD, Git reports no staged change, the working file keeps an edit made after the commit, and a second reading names nothing. A repository whose HEAD names no commit is never read as emptied, and an index read through a GIT_INDEX_FILE naming another file is answered naming the variable and that file, the checkout's own index left whole.
