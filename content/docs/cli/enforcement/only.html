tama enforcement only

Replaces the machine-wide baseline with an operator-owned selection of installed hook ids.

Invocation

tama enforcement only <hook-id>...

Provide one or more ids declared by the installed registry. Known ids include the registry's agent hooks and repository Git hooks. Tama sorts and deduplicates accepted ids before writing them.

Output and state

Success begins Machine enforcement selection saved. Tama writes ~/Library/Application Support/Tama/hook-enforcement.json atomically with mode 0600, mode: "only", the selected ids, the transition time, and the immediately preceding effective mode and ids in previous. A live session may add hooks for itself, but cannot remove an id from this machine selection.

Refusals and failures

An unknown id refuses the entire mutation before any write:

Unknown hook id '<id>'; the installed registry declares <N> hook ids, and the enforcement selection was not changed.

The sentence names the rejected id and the number of unique agent and Git hook ids known to the installed registry.

A hook that cannot run on this machine is refused the same way, before any write, because a selected hook that answers every tool call with a credential error takes the machine away from its agent - including the command that would undo the selection:

Hook '<id>' cannot run on this machine, so nothing was selected and the enforcement selection was not changed. It answered: <the hook's own line>

Tama asks each requested hook once with the activation payload the session path uses, expanding the home directory the registry records literally. A hook whose binary is not installed yet is accepted: it is absent, not broken. Only a hook that runs and answers with an infrastructure failure is refused. tama enforcement preflight shows that exchange for one hook without changing anything.

Other registry or write failures print enforcement: <OS/core error> to stderr and exit 1 without claiming success.

What a machine in only runs

The selected hooks, and nothing else of Tama refuses a call:

  • The core's own admissions around the hooks — the known-operation admission over Oko's open defects, the repeated-call and commit-standing refusals, the verification reservation — and Oko's open-work settling after a prompt or stop, and the adaptive layer's prompt bridge, run only when the selection is all (tama_hooks::enforcement::every_hook_enforced).
  • The OMP adapter asks the core only for an event a selected (or session-enabled) hook answers; every other tool call, tool result, prompt and compaction passes without a core round trip.
  • With no selected stop hook the end of a turn is not assessed, and with no selected before_provider_request hook the text gate neither forces a tool call nor cuts an answer off.
  • A core that cannot answer (it cannot start, crashed, or answers for another catalogue), an unset Git editor environment, and a stop assessment that failed all let the call or the ending go on, with TAMA_HOOK_INFRASTRUCTURE: …; the machine selects only some gates, so … goes on unchecked on the session's status line. Under all each of these still refuses.
  • A hook that crashes or exits nonzero without a decision document is reported and the call goes on, in both modes; only a hook's own refusal blocks.

A hook is waited for, not timed, so a selected hook must be one that answers by itself: a gate that asks a model (block-keychain-prompt-commands, check-merge-deletion-loss) refuses a command not yet judged once a model is declared, and belongs in an only selection only on a machine that wants that.

Taking it back

From the operator's own shell: tama enforcement all or another tama enforcement only changes what every running session enforces at its next call; the emergency disable bypasses every hook at once; and omp config set extensions '[]' removes the OMP adapter from sessions started after it (tama hooks release puts it back).
