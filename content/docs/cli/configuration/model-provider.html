tama model-provider

Chooses the model service Tama's model calls ask — the objective reviewer, the stop review, frustration drafting and adaptive disputes — and checks whether it accepts this machine. Brama is the default; a machine without Brama declares any OpenAI-compatible chat-completions service instead, or declares that it has no model at all.

Invocation

tama model-provider [show] [--json]
printf '%s' "$KEY" | tama model-provider set --origin https://api.openai.com --model gpt-5 [--json]
tama model-provider set --none [--json]
tama model-provider unset [--json]
tama model-provider check [--json]

A machine with no model

Tama does not need Brama, or any model, to hold a session to its rules. set --none writes {"provider": "none"} into the same declaration file, and show then prints provider: none, model: -, declaredIn and judgedBy. From then on:

  • Every deterministic hook enforces exactly as before.
  • A stop gate that would ask a model whether the ending answer breaks its rule reads the session's recorded attestation instead: the task's own JSON statement that it is finished, checked by tama assignment attest. With no attestation recorded the gate refuses and names the command that records one; with one that falls short it refuses with each field's reason.
  • A hook that only asks a model a question about a text (whether it claims a failure, which tests are smoke tests) finds nothing and writes <hook>: no model is declared on this machine, so this question is not read to its log.
  • review-push asks no reviewer: each pushed ref's new tip must carry its own attestation, recorded with tama assignment attest FILE --commit SHA, confirming the reviewer's standard. A tip without one is refused with no model is declared on this machine, so commit <sha> needs its own attestation, and none is recorded: write it and record it with `tama assignment attest FILE --commit <sha>`; one that falls short with each reason. The formatter and stado quality check the dispatcher runs before it still refuse a push.
  • check exits 1 with no model is declared on this machine, so there is no service to check.

unset returns Tama to Brama. Tama Desktop's Model service section sends the same operations: tama request model-provider (the choice and its check; with no model the check says there is no service instead of probing Brama), tama request model-provider/set with {"none": true}, and tama request model-provider/unset. A service and its key are declared only in the terminal, so the key never crosses a request; model-provider/set with any other body is refused with that sentence.

Output and state

set reads the service's API key from standard input only and writes the origin, model and key owner-only (mode 0600) to ~/.tama/model-provider.json; TAMA_MODEL_PROVIDER_PATH names another file. From then on every Tama model call posts to <origin>/v1/chat/completions with that key as its bearer and asks for that model. unset removes the file and Tama asks Brama again. Every verb prints the choice that stands afterwards: provider (brama or openai-compatible), model, and for a declared service origin and declaredIn, as key: value lines or as JSON with --json. The key is never printed.

Refusals and failures

  • set needs --origin URL and --model MODEL (the API key is read from standard input), or --none for a machine with no model — exit 2.
  • --origin must be HTTPS, or HTTP on loopback, with no credentials, query or fragment, and --model must name a model: got "…" and "…" — exit 2.
  • the API key is read from standard input, and standard input was empty — exit 2.
  • no model provider is declared in <file>; Tama already asks Brama — unset with nothing declared, exit 1.
  • <file> names no complete model provider (origin, model and key); declare it again with `tama model-provider set` or remove it with `tama model-provider unset` — a damaged declaration; every model call refuses with the same sentence until it is repaired.
  • With nothing declared, show exits 1 with the route resolver's own sentence when Brama's route cannot be resolved, instead of printing an empty model.
  • the model provider declaration <file> cannot be read: <cause> or <file> is not a model provider declaration: <cause> — every verb, and every hook that reads the choice, refuses with the cause.
  • takes show, set, unset or check; got <verb> — exit 2.

check

Presents the credential of the service in force to its bearer-only GET /v1/models and reports what it answered. That request is not billable and calls no provider. The bearer reaches curl through a --config document on standard input, never through its arguments. Tama Desktop shows the same read as the Model service section of the Install screen.

Identity and credential

For Brama, Tama's identity at the gateway is a Skarbiec consumer, tama by default and TAMA_BRAMA_CONSUMER when set. Its credential is a token minted for that consumer, read from ~/.stado/<consumer>-skarbiec-token or from TAMA_BRAMA_TOKEN_FILE. Mint one with skarbiec token-mint <consumer> --capabilities call:brama#<route>; the grants inside the token decide which routes that consumer may ask for, and Brama learns the client and its routes by introspecting the token at Skarbiec. For a declared service the credential is the key set stored, and no Skarbiec grant is asked.

Brama's address is resolved exactly as clean and the objective reviewer resolve it: TAMA_OBJECTIVE_AUTHORITY_MODEL_ROUTER_URL, STADO_MODEL_ROUTER_URL or BRAMA_URL when one is set; otherwise the fleet route obtained with stado service directory connect brama --consumer <adapter> --json. The adapter is tama by default and TAMA_BRAMA_ADAPTER_CONSUMER when set. There is no public-hostname fallback. A declared service's address is its origin.

The fleet route is remembered in ~/.tama/brama-route/<adapter>.url. When it is absent, one caller holds the adapter's file lock while its own Stado child resolves the address; other callers wait visibly for that result. A successful, structurally valid address is published atomically. Stado spawn, exit, JSON, URL and state-file failures name the actual operation and cause. An unreadable or empty route is not treated as an absent route. Transport failure invalidates the remembered address so the next call resolves it again.

Discovery does not detach a child, discard its error output or use a numeric PID as a liveness record. In a native hook the Stado child inherits the hook's owned lifetime group. Cold discovery can wait on Stado; this is not a millisecond-response guarantee. Stop-review scheduling belongs to the harness adapter, which must keep that work outside its bounded callback. Old .asking and .answer files are no longer used; this change does not claim to terminate children launched by an older installed runtime.

A fleet route this machine cannot hand out or verify — its resolver holds no listener, or declares no adapter for the consumer — does not end the search: Brama is looked for across the fleet through a relay this process owns, stado resolver relay brama --consumer <adapter> --bind 127.0.0.1:<a port stado host free-port-local handed out> --json. Stado reads the directory from the authority, resolves Brama for the consumer and carries each connection over its own SSH session to Brama's host; the relay announces its loopback URL on its first line and lives while the caller holds its standard input, so it ends with the credentials that served one request and its URL is never remembered. When the relay fails too, the refusal carries both causes: the discovery failure and the relay's own. The review gate and every judge on a workstation whose resolver stopped therefore still reach Brama as long as Brama answers on its host and the fleet channel to that host is open.

The route and the relay are both answered by this machine's Stado, so a Stado release that is itself broken, or a machine without Stado, would leave no reviewer for the very push that carries Stado's repair. When stado service directory connect cannot run or refuses, and the relay fails too, Brama is found through the fleet authority's own directory instead: the registry copy the authority last served to this machine, ~/.stado/cache/registry-last-good.json, names Brama's active host (service_directory.services.brama.active_host), its address there (endpoints.<host>.url) and that host's SSH destinations (targets[].ssh, then ssh_fallbacks). Tama takes a loopback port from the operating system and opens a forward with the system SSH client, ssh -T -o BatchMode=yes -o ExitOnForwardFailure=yes -o PermitLocalCommand=yes -o 'LocalCommand=echo tama-authority-forward-ready' -L 127.0.0.1:<port>:<Brama's address> <destination> 'cat >/dev/null', using the account's own SSH identities. The forward announces itself once its listener is bound and ends when its owner closes its standard input, exactly as the relay does; its URL is never remembered. The bearer is still Tama's token file, which the fleet's Brama checks with its own Skarbiec, so a local Skarbiec that does not run is not asked. When this route fails too, the refusal names every cause in order: the route, the relay, then the unreadable or incomplete registry copy (declares no brama service, names no active host, has no endpoint on its active host, declares no SSH destination) or each destination's SSH refusal. The real journey tests/review/route/authority.rs (review_route_authority) pushes through the built tama hook review-push from an isolated home holding only the authority's registry copy and no Stado, against the real reviewer, and requires the commit on the remote.

Output

Text output is ten lines: the provider (brama or the declared origin), the chat endpoint the client would post to, the transport verdict, the probe address with the HTTP status it returned, detail — the number of models offered on success, or the service's own error body — then consumer, token file and route, then what this machine's authority answers about that route on that bearer (for a declared service, not asked), and finally one verdict. --json emits the same fields as one object, including local_grant and verdict. Inspection does not change provider selection or credentials; resolving a cold Brama address can populate the shared route cache.

Reading the verdict

For Brama the verdict line exists because 401 stands for three different states at once: a bearer can be valid at its own authority while the gateway is deployed without the variables that let it ask, and a bare status cannot tell the two apart. The sentences are:

  • the model catalogue accepts this bearer; chat was not tested — the catalogue answered 200. A chat request may still fail at a different proxy, on its route, or at its local capability check. Inspect the actual frustration-drafter outcome in tama rules digest --json before claiming that automatic drafts work.
  • this machine's authority grants the route on this bearer, and the gateway still refuses it — the gateway is not asking this authority. Check that its deployment carries WC_SKARBIEC_URL, BRAMA_SKARBIEC_CONSUMER and BRAMA_SKARBIEC_TOKEN_FILE.
  • this machine's authority does not grant this route to this consumer — issue it with skarbiec grant issue <consumer> --capabilities call:brama#<route> --token-file <path>.
  • the gateway refuses this bearer and this machine's authority could not be asked — the local vault or its CLI is the first thing to repair.

For a declared service: <origin>'s model catalogue accepts the declared key; chat was not tested, or <origin> refuses the declared key with <status>: declare the service again with `tama model-provider set`, or return Tama to Brama with `tama model-provider unset`. Either service: nothing answered at that address when no HTTP answer arrived.

Refusals

check exits 1 unless the service answered 200 through an allowed transport. A missing Brama token exits 1 with no Brama token for consumer <consumer> at <path>: <cause>; mint one with …; an empty file is refused as is empty and a file holding more than one word as does not hold one token. An address off loopback that is not HTTPS, or one carrying credentials, a query or a fragment, is refused by the client before anything is sent. A damaged declaration is refused with the sentence above.

An existing token path that cannot be read instead reports cannot read Brama token for consumer <consumer> at <path>: <cause>. Permission, directory and decoding errors preserve their actual cause; they do not claim the grant is absent or advise replacing it. The real catalogue journey checks a directory-as-token refusal against the observed filesystem error before any network request.

Visible child waits in provider code

block-silent-waits checks added Rust waits through tama hook block-silent-waits, reading the write or edit payload on stdin. A child reap inside the shared stado_wait::blocking API is a visible wait, including a multiline closure, just as a wait inside stado::wait or crate::wait is. A sibling bare child.wait() outside that call remains refused. The decision names the file, operation and offending line; installed Session/Posture surfaces consume that same decision.

The existing silent_waits_refusal journey retains the declared clean candidate, built executable digest, payloads, commands, statuses and decisions. It covers a shared-crate multiline reap, a bare sibling and an unrelated namespace ending in the same spelling. Source acceptance of a wait wrapper does not qualify provider reachability, cancellation or an installed graphical decision.

Chat and catalogue requests validate the transport policy and resolver channel before starting the HTTP client. They disable implicit curl startup configuration, so a user curl configuration cannot silently add retries or redirect handling to the declared request. Catalogue response collection prints the shared visible wait just like chat collection.

If writing a request into the HTTP client's input pipe fails, Tama terminates its owned client and visibly collects its output before returning. The refusal preserves the original input error together with the observed client exit and stderr, or the concrete termination/collection error. Cleanup failure never replaces the primary request failure or becomes a successful empty answer.

Route qualification

The registered model_provider_route journey under tests/model-provider/route.rs invokes the actual built CLI, retains candidate revision, binary digest, command, exit status and output, and checks genuine absent-executable and directory-read refusals. TAMA_TEST_SOURCE_REVISION must identify the clean candidate. Its explicit real-discovery case requires TAMA_TEST_BRAMA_HOME: an isolated, configured home with a real installed Stado, real Brama credentials and no remembered route. It refuses the operator's home, retains the Stado digest and published route, and requires the real catalogue to accept the credential. Catalogue acceptance does not qualify chat, cancellation or the Desktop surface.

The same journey includes the real CLI refusal for a plaintext remote catalogue endpoint. It requires the transport-policy cause before the HTTP response wait and checks that the fixture credential never enters output. This negative case performs no model call and is not proof of a working provider or of interruption cleanup.

The owned-runtime cancellation journey also dispatches the actual model-provider check --json command against a TCP listener that accepts the catalogue request but sends no response. Cancellation must close that real connection, report a cancelled dispatch and leave no running hook. Candidate receipts name the dispatched command as well as the runtime binary; the journey sends no invented provider response and does not qualify a standalone CLI signal handler or a Desktop interaction.
