tama copies list

Reports every second full checkout under the roots you name, with the checkout it duplicates, its apparent size and the state that would refuse its removal, and mutates nothing.

Invocation

tama copies list [--root <PATH>]... [--json]

Inputs and options

OptionMeaning
--root <PATH>Repeatable, and required at least once. Each value is a directory whose checkouts are walked. There is deliberately no default root
--jsonPrints the exact document below instead of the text report. Both modes read the same state

What counts as a copy

The named root and every checkout directly under it are canonical. A checkout deeper than that, with its own .git directory, is a candidate; a checkout whose .git is a file is a linked worktree and belongs to tama worktrees list, so it is counted under linkedWorktrees and never listed as a copy.

For each candidate the command asks git three things: whether its working tree is dirty, whether any commit on a local branch is absent from every remote, and what its origin is. The origin is what pairs a copy with the canonical checkout it duplicates, including the local-path origin a git clone /path/to/repo records.

Output document

Under --json, exactly these fields, with the schema version the whole copies contract is fixed at:

{"schemaVersion":Number,"roots":[String],"copies":[{"path":String,"owner":String|null,"origin":String|null,"bytes":Number,"dirty":Boolean,"unpublished":Boolean,"ownsWorktrees":Boolean,"named":Boolean}],"copyCount":Number,"bytes":Number,"linkedWorktrees":[String],"twins":[{"path":String,"twin":String,"origin":String}],"unreadable":[String]}

roots echoes the roots you passed, resolved. owner is the canonical checkout of the same repository under those roots, or null when this directory is the only checkout of its repository here — which is a refusal on remove until you name it with --only. bytes is apparent size, per copy and summed for the pass. named is false here and only ever true in a narrowed removal document.

twins carries checkouts of one repository that both sit directly under a root; the pass reports them and removes neither. unreadable names every candidate the walk found a .git for and git then refused to answer for: reported rather than dropped, because silence would be the pass claiming it read a checkout it never read.

The same document is served by POST /v1/copies/list with body {"roots":[String]} on the loopback desktop backend (tama serve).

State effect

None. The command walks directories and runs git status, git log and git remote get-url, all read-only, and it has no --apply, no --force, no --except and no --only: those belong to tama copies remove, which is the only leaf with anything to spare, narrow or delete.

Refusal boundary

Passing no --root is a usage error, exit code two:

tama copies needs at least one --root; a machine-wide default would walk directories Tama does not own.

A root that cannot be read contributes nothing rather than ending the pass. This leaf has no other refusal: it never asks whether a copy may be removed, which is tama copies remove's boundary.
