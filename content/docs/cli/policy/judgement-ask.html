tama judgement ask

The model call a gate on a shell command does not make inside its hook. block-one-off-repairs, block-background-execution, block-external-source-edits, block-inline-execution, block-keychain-prompt-commands, block-local-model-training, pre-bash and block-device-level-tests-without-consent judge a command by asking a model through Oko (oko gateway object), and a model call takes longer than a harness waits for a hook: a gate that waited was abandoned and decided nothing, and while Brama or Skarbiec stood unreachable every shell of every session waited with it. So the gate decides a command from the answer already kept for that exact question, and a command not yet judged is refused, never let through, with the request that asks it named.

Invocation

tama judgement ask <request>
tama judgement show <request>
tama judgement attest <request> --choice <declared option> --reason <what was checked>
tama judgement revoke <request>
  • <request> is the path the gate's refusal names: <sha256 of the question>.request.json in the judgement memory (TAMA_JUDGEMENT_MEMORY_DIR, else model-judgements under the Tama state root), holding {"key", "verb", "arguments"}: the whole question and the oko gateway call that asks it.
  • It runs that call here, outside every hook, keeps the answer beside the request under the question's hash with the seal Tama makes under its login-keychain key, and prints it. The question the answer is kept under is read from the --prompt, --name and --schema the call sends the model, never from the request's own key. Oko is started with none of the asking shell's environment, only HOME as the user database records it, so no variable redirects its model route. The answer is kept only when the process that gave it is the Oko CLI (ai.wisent.oko.oko-cli) signed under an Apple-issued certificate of the team that signed this tama, as the kernel reads the running code while it is still Tama's child: a program reached as Oko through TAMA_OKO_CLI or PATH that is not that Oko answers this one call and decides no later one, and why is said on stderr as soon as its code is read. The gate reads the kept answer when the same command is run again, and only with a seal that verifies; an answer the gate's reading does not accept is taken back so the next ask goes to the model again.
  • The command runs only Tama, so a gate whose question is unanswered lets it through (the programs the judge stands on).

Output and refusals

  • The answer the model gave, as one JSON object, exit 0.
  • judgement: the judgement request <path> cannot be read: <cause> or … is not one: <cause>, exit 1.
  • judgement: the judgement request <path> is kept under a question other than the one its arguments ask the model, so its answer would decide another call; nothing is asked, exit 1. judgement: a judgement request asks `oko gateway object`, and this one asks `<verb>` and judgement: the judgement request names no --prompt|--name|--schema for the model, exit 1.
  • A failed answerer signature or durable answer write fails with its original cause. The common review boundary returns unavailable, not a successful answer accompanied only by a warning. A failed process or rejected answer remains the primary failure when it occurred first.
  • judgement: <cause> when the question went unanswered — no model declared, Oko absent, the gateway refusing, a judge Oko recorded as not answering — exit 1.
  • show, attest and revoke print their JSON inspection, statement or removal result on success. A refused operation prints judgement: <cause> and exits 1. An unknown verb, extra argument for ask/show/revoke, or missing or misplaced --choice/--reason for attest prints the judgement usage on stderr and exits 2.

One failure path, independent of the provider

Every failed schema-bound review crosses the same recording boundary. This includes an unavailable service, missing executable, failed process, unreadable model declaration, malformed or rejected answer, corrupt retained state and caller-attribution errors; there is no branch that recognizes only Brama or a particular HTTP status. The original cause remains intact. If keeping the request or failure also fails, the command reports that recording operation and its cause beside the original failure, rather than replacing it.

show returns the exact question and requested schema, its latest failure, the retained failures in observation order, and the current caller's attestation. Each failure records its cause, whether this review permits a local statement, the observed Unix time in milliseconds, the caller when identified, and a separate attributionError when identification failed. Failures are appended beside the request as <hash>.failures.jsonl; a later failure does not erase an earlier dependency refusal. Snapshot, history and local-decision reads are independent: failureError, historyError and attestationError name a failed read without hiding the records that remain readable. An unreadable part is null, not an invented empty history. Invalid record types and records for another question are refused with their path and cause. If the previous snapshot cannot be read while recording a new failure, priorFailureError retains that separate cause. Unknown eligibility is represented by attestable: null: the observed cause remains readable, but only an explicitly eligible review can authorize an attestation.

Functionality an open defect breaks is refused before execution

Oko's defects operations bind names the functionality an open defect breaks: a command path (the program and its command words, as oko asks ask) or a tool that is not a shell. Tama's common pre-tool dispatch reads Oko's open snapshot locally and refuses every call that reaches it, with any arguments, from any directory, the program found anywhere, before any tool starts and regardless of the model provider or tool family. Only the defect's owner is admitted, and only while its declared work for the operator's current instruction is that defect (tama task scope set --session <owner> --defect <id>, read from ~/.tama/task-scope/<session>.json by the same reader block-off-task-work uses): owning the defect while declaring other work is refused like any session, a declaration written for an earlier instruction authorises nothing after a newer one arrives until the owner declares again, and a declaration or captured instruction that cannot be read refuses every tool with TAMA_HOOK_INFRASTRUCTURE naming its path and cause. Oko's defects operations check --session <owner> answers that owner with allowed: false and allowedWhileDeclared: true, because Oko does not hold the declaration. No model or network request runs in this gate.

The refusal sends the caller where the repair belongs. A defect Oko sorted as the symptom of another is followed through the snapshot to the deepest root still open, and the reason names that root, its title and its owner with the instruction to repair that, not this, and carries the root's repair in its document; the caller is told not to investigate the failure again. Each reason says what releases the call: the revision a repair is claimed at, which stays refused until that repair is published and the defect closes, or that no repair is claimed yet. A repair claim alone does not lift the refusal; the defect must leave the open snapshot, fixed by a published release or withdrawn. When any ancestor in a symptom's root chain has closed, its functionality is let through even while intermediate symptoms remain open, so that call proves whether the ancestor's repair repaired the symptom, and Oko's operations check lists it to verify. A missing, malformed or stale snapshot refuses every tool naming the path and cause.

Inspect and manage the same records in Oko Desktop → Defects → Functionality blocked by defects and Defects nobody has sorted, or with Oko's operation commands. The real journey is Oko's tests/defects/operations/journey.rs, which drives this dispatcher with the candidate Tama binary. A declaration or test definition is not evidence that the installed runtime exercised this path.

The open snapshot is admitted only with Oko's publication receipt, defects.open-identity.json beside defects.json (the same extensions follow OKO_DEFECT_REGISTER). Oko writes it under its register lock after publishing the snapshot and command grammars. It identifies the register and snapshot by device, inode, length and nanosecond modification/change timestamps. Tama compares that receipt with the current register and the opened snapshot file: equal or newer modification times do not make a stale snapshot current. A missing, unreadable or mismatched receipt refuses ordinary calls with TAMA_HOOK_INFRASTRUCTURE, its path and the published and observed identities when they differ.

When this publication cannot be validated, the exact standalone command oko defects snapshot, optionally followed by --json, still reaches ordinary hook evaluation so the admission boundary cannot prohibit its own snapshot repair. Other hooks and permissions remain in force. No wrapper, redirect, substitution or additional shell command receives that recovery admission. Regeneration changes no defect standing and releases no binding. After copying a register, regenerate its snapshot at the new location rather than copying the old receipt.

Explicit local review, not an invented model result

A content-review consumer may explicitly permit an attestation for its exact question. After reading the failure with show, state one of its declared options and what was actually checked with attest. The statement is bound to that question and the recorded calling session; outside an agent session it is identified as the operator's statement. A different question or caller cannot consume it. Retrying the original operation reads the statement and labels it as attestation, never independent model review. revoke removes only the caller's local statement; it does not remove a sealed model answer or the failure history.

Only questions whose consumer permits this alternative accept it. A negative model verdict is not replaced. Consent, authorization, credentials and a successful external operation cannot be supplied by a local statement. An undeclared choice, blank checked statement, missing failure, mismatched request or already-answered model question refuses without changing the decision. Storage and attribution failures remain errors, not permission to continue.

A recorded attestable: null means eligibility is unknown, not that the question was classified as requiring original authority. Inspection keeps the observed failure cause in either case. Only explicit eligibility permits a local decision; unknown eligibility authorizes none and must not change the request, recorded failure, history or local decision.

Native interface and desktop

In Tama Desktop, open Install plan → Review failures and alternatives, enter the request file and choose Read review and failure. The review section remains available even when the installation plan is unread, loading or failed; inspecting a retained review does not require a successful installation-plan read. The screen shows the same latest cause, earlier attempts and attribution/storage errors. Record local attestation is enabled only for an eligible question with a declared choice and a checked statement. Withdraw local attestation removes the current caller's statement, including a corrupt statement that cannot be decoded for display. These actions use judgement/show, judgement/attest and judgement/revoke through the native request protocol, calling the same product implementation as the CLI rather than interpreting shell output.

The native request interface rejects invalid UTF-8 and malformed JSON before dispatch, naming the operation and the actual decoder error. Event write or flush failures are reported as delivery failures, never a successful command exit. The desktop shows snapshot, history and attestation errors separately; a damaged history does not conceal a readable latest cause, and a damaged snapshot does not conceal readable historical attempts.

Attestation inspection validates the record and its answer, not only JSON syntax. Valid JSON with missing or wrongly typed fields, another question or source, an empty checked statement, or an undeclared choice is returned as attestation: null with its own attestationError. The readable failure and history remain available to the desktop, and Withdraw local attestation can remove the damaged statement without decoding it first.

Starting an inspection or local-statement operation clears the previously displayed inspection. While it runs, the section names the step in progress: recording, withdrawing, or reading the review record. A successfully answered record or withdrawal operation has its own acknowledgement, separate from the following inspection; withdrawal includes the backend's removed value. A refusal begins with the step and operation that failed, for example Review failure and alternative [judgement/show]: …, so a refused read after a recorded statement is not mistaken for a refused judgement/attest or judgement/revoke. If the following inspection fails, the acknowledgement remains visible alongside the actual read failure instead of presenting the earlier statement or eligibility as current. Reading the request again obtains the actual saved state; the failed refresh does not undo or repeat the mutation. Starting another operation or changing the request clears the acknowledgement.

Real qualification

tests/model-judgement/attestation.rs, included in model_judgement_unanswered, drives the actual candidate CLI, native request interface and hook against isolated real state. It covers explicit decision consumption and withdrawal, undeclared-choice refusal, an absent dependency, corrupt local decisions and failure snapshots, readable records beside a damaged history, retention of a damaged previous snapshot as a separate cause, malformed native input, and a recording failure that must not hide the primary error. Its reports retain source revision, candidate binary digest, commands, exact input bytes, exit statuses and output under Cargo's test directory. No provider answer or external service is simulated; these local journeys do not establish successful remote model inference.

The unknown-eligibility journey reads the same null eligibility and actual cause through CLI and native inspection, refuses a local decision through both interfaces, and checks that the request, failure and history bytes and inspected decision state remain unchanged. Its diagnostic assertions use the observed cause, not a pinned phrase that invents an authority requirement. The journey definition alone is not a qualification result.

Quickstart

$ # a shell command is refused:
block-one-off-repairs: TAMA_HOOK_INFRASTRUCTURE: … this call has not been judged yet, and the gate does not wait for the model inside its hook: `tama judgement ask …/model-judgements/3f1c….request.json` asks it now and keeps the answer, and the same call is then judged at once
$ tama judgement ask …/model-judgements/3f1c….request.json
{"choice":"PASS","reason":"…"}
$ # the same command now runs, decided by the kept answer

For a local content review whose consumer explicitly permits attestation, REQUEST below is the exact file named by the original refusal. Read its question first; do not copy a statement about another command.

tama judgement show "$REQUEST"
tama judgement attest "$REQUEST" --choice PASS --reason "The reviewed printf command prints literal text and runs no supplied program source."
# Retry that exact original command; its review is now labelled attestation.
tama judgement revoke "$REQUEST"
