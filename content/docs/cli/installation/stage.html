tama stage

Stage a session's recorded text edits without taking other changes merely because they share a file. Tama reads completed tool receipts, reconstructs their deltas and lets Git merge those deltas into a private index. It publishes that index atomically only when every selected transition succeeds. It does not edit working files, create a commit, compile source or install a product.

Invocation

tama stage --session <session> [--repo <checkout>] [--json] [--inspect]

--session names a retained session, not a caller-supplied patch. --repo selects the checkout; without it the current directory selects the repository. --inspect computes the same candidate without publishing it. Inspection may write Git objects and ignored scratch files, but leaves the actual index unchanged. --json returns the structured result.

Example: shared file, separate changes

tama stage --session <your-session> --inspect
 tama stage --session <your-session>
 git commit -m 'Preserve the recorded operation cause'

Run these as separate commands. The commit guard checks the resulting index, not a future index that an earlier command on the same shell line might produce. Whole-path commits, --all, --include and pathspec-file commits refuse because they can import working-tree hunks after that inspection. Existing unrelated staged entries are preserved by staging; they must not be included in your commit. The guard refuses an entry or hunk not established by your receipts even when you edited another part of the same file.

Git's commit-msg hook (tama hook review-commit) reads the same ownership from the index Git is about to commit, however the commit was spelled: git commit -a, an alias, sh -c "git commit …" or a script. The committing session is the one whose recorded agent process (pid in its session record under the session-control root) is an ancestor of the hook, read one process at a time with ps -o ppid= -p. A process ps no longer finds ends the walk; a ps that fails saying why (a sandbox or policy refusing it) refuses the commit with ps -o ppid= -p <pid> failed (<status>): <its words>; the process tree this command runs in cannot be read, since ending the walk there would read an agent's commit as the operator's. When such a session commits, every staged entry must be established by its receipts exactly as staging would produce it; otherwise the commit is refused before history changes with review-commit: commit refused before history changed: the staged index is not only <agent> session <session>'s recorded edits: <cause>, or, when the session's transcript cannot be found, this commit runs in <agent> session <session>, whose transcript cannot be found, so its staged index cannot be read against the session's recorded edits. An index, a Git command or receipts that cannot be read are not reported as another session's change: the commit is refused with whether the staged index is only <agent> session <session>'s recorded edits cannot be read: <cause>, and the shell-line guard with BLOCKED: whether `<command>` commits only this session's recorded edits cannot be read: <cause>. A commit no recorded session's process tree holds, the operator's own, is not read for ownership; that includes a commit an agent starts outside its own process tree (detached with nohup, setsid or a double fork, or handed to another daemon), which this reading does not attribute to it. A commit made with --no-verify or with plumbing (git commit-tree) runs no hook and is read only by the shell-line guard.

Evidence and supported transitions

The transcript must identify the requested session. A successful result must match its recorded invocation. Text edits use complete oldText/newText snapshots. A full-file write reporting only resolvedPath refuses: its arguments establish the requested content, but cannot prove whether it created a file or overwrote another session's untracked work. The receipt must establish the before-state or explicit creation. Recorded creation and deletion are distinct from an empty file. Missing snapshots never turn path ownership into whole-file ownership.

A result may contain one file receipt or a changes array of complete file receipts. Each member is bound to the same successful tool call and validated before publication. A write with an explicit op and the corresponding snapshots uses the same transition reader; resolvedPath supplies only its location, never evidence of creation. Invalid or empty batches refuse rather than silently dropping edits.

Independent text changes merge; conflicting content or creation/deletion refuses the operation. Every proposed delta must still be present in the working tree. Symlinks, unresolved index entries, non-UTF-8 content and unsupported transitions refuse with the affected file. Text receipts do not authorize mode changes. Existing file modes remain unchanged; new file mode comes from Git's observation of the real file.

Output and diagnostics

{"session":String,"repository":String,"paths":[String],"calls":[String],"tree":String,"applied":Boolean}

paths names the index entries changed by this operation; calls identifies the successful edit receipts used. tree is the candidate Git tree, not a build or verification verdict. Repeating a successful operation reports no remaining unstaged deltas. Staging preserves unrelated index entries, so the candidate tree alone does not assert that the whole index belongs to this session.

An absent transcript, invalid session identity, unmatched result, missing snapshot, stale edit, overlap, index lock, unavailable Git command or filesystem failure exits nonzero and names the failed operation and cause. Git's stdout and stderr are retained in its failure. Failed staging does not publish the private index. A held lock is not removed or retried. Scratch lives under the checkout's ignored .build/tama-stage, isolated by index path. A scratch path that is not ignored or resolves through a symlink refuses. Whether the scratch is ignored is read with git check-ignore on its path name, without the literal pathspec magic the index operations use, because check-ignore refuses that magic; a GIT_LITERAL_PATHSPECS in the caller's environment does not reach it either.

Desktop and native interface

Open Reviews → Session-owned staging, enter the session and checkout, then choose Inspect changes or Stage session changes. The screen shows paths, receipt calls, candidate tree and the exact refusal. It calls the same implementation through tama request stage, with body {"session":String,"repository":String,"inspect":Boolean}. This is the native request protocol, not a shell invocation of the staging command.

Real qualification

tests/shared-checkout/commit.rs invokes the actual CLI against real retained session receipts and Git trees, using a separate index inside the canonical checkout. Set TAMA_STAGE_CASE to a retained capture containing repository, session, unprovenSession, baselineTree, expectedTree, conflictTree and files. The capture must contain independent changes by different sessions in a shared file, batched file transitions and an overlapping index tree. unprovenSession identifies an actual session containing a write without before-state for this repository. No transcript or provider response is manufactured. Missing capture is a failed prerequisite, not a passing test.

The journey checks inspection without mutation, exact session-only staged bytes, repeated staging, overlap and missing-provenance refusals, preservation of the operator's index and working files, and retains revision-bound command streams, exit statuses and observed tree identities.

tests/shared-checkout/hook.rs (cargo test --test shared_checkout_commit_hook) reads the same capture: it stages the captured session's hunks into an isolated index with the built tama stage, then runs the built tama hook review-commit over it as Git's hook would, with a session record naming the test process as the session's agent process and an attested message. The session's own hunks are not refused for ownership; the capture's conflicting tree is refused naming the session and the foreign index. The operator's index and working files are compared afterwards and the outputs are retained under Cargo's test directory.
