tama stage

Stage a session's recorded text edits without taking other changes merely because they share a file. Tama reads completed tool receipts, reconstructs their deltas and lets Git merge those deltas into a private index. It publishes that index atomically, holding every path whose change it could carry; a path whose change it cannot carry is left out and named with its cause under omitted, and a failure of the run itself (an unreadable transcript, the index lock, a Git failure) publishes nothing. It does not edit working files, create a commit, compile source or install a product.

Invocation

tama stage --session <session> [--with <session>]... [--task <task>] [--repo <checkout>] [--path <file>]... [--from-head] [--json] [--inspect]

--with, repeatable, names a session that wrote the session's files together with it: a reviewer that amended the author's hunk, a session whose formatter rewrote it. Each named session's recorded edits of the paths the session itself edited are read into one run with the session's own, ordered by the time each transcript recorded the edit's result, so the file the named sessions left together is staged; their edits of other paths are not staged. A line no named session wrote still stands nowhere in that run and is refused or left out as before. A published staging keeps the authors beside the staged index (authors.json in the checkout's .build/tama-stage/<index>), and the commit check reads the same run for the committing session, so its commit is admitted for exactly those bytes; a staging without --with removes the record. Naming the staged session itself refuses (--with <session> names the session being staged; …), as does an edit whose result carries no recorded time (edit <call> of <path> has no recorded time, so it cannot be ordered among its co-authors' edits). The native request takes the same list as "with":[String], and Desktop's Session-owned staging panel takes it one session per line.

--task names an Oko task the staged session took over from a stopped session named with --with. Nobody but the session leading the task can commit what its predecessor wrote, so each named session that held the task, by the task's claim history (oko tasks show <task> --json, current.claimHistory[].from), contributes every path it edited in the checkout, not only the paths the staged session edited too; named sessions that never held it stay co-authors of the shared paths only. Oko must show the task claimed by the staged session (--task <task>: Oko shows the task claimed by <other>, not by <session>; …, or claimed by nobody), at least one named session must have held it (--task <task>: none of the sessions named with --with (…) held the task; its claim history is […]), and no recorded agent process of a predecessor may still run (--task <task>: session <session> still runs (<agent>, process <pid>); its edits are its own until it ends, so ask it to commit them or to hand them over); --task with no --with refuses. A published staging keeps the task in authors.json beside the co-authors, and the commit check asks Oko and the process table again, so the commit is admitted only while the session still leads the task and the predecessor still does not run. The native request takes it as "task":String, and the Desktop panel has a field for it.

--session names a retained session, not a caller-supplied patch. --repo selects the checkout; without it the current directory selects the repository. --path, repeatable, stages only the session's recorded edits of the named files (relative to the checkout, or absolute inside it): a session that made several unrelated changes in one checkout stages each as its own commit, and a file another session changed in between no longer holds the others back. A named file the session never edited is refused as --path <file> names no recorded edit of this session in <checkout>; the index is unchanged, and an absolute path outside the checkout as --path <file> is outside the checkout <checkout>: …. Without --path every recorded edit is staged. --inspect computes the same candidate without publishing it. Inspection may write Git objects and ignored scratch files, but leaves the actual index unchanged. --json returns the structured result.

--from-head reads the staging index from HEAD (git read-tree HEAD on the private index) before the session's changes are carried onto it. An index read while an older HEAD was checked out would otherwise take back every commit that landed since; with --from-head it carries only the session's change, and entries staged by other means are not kept. A HEAD Git cannot read into the index is refused as cannot read HEAD into the staging index: <cause>, and nothing is published.

Example: shared file, separate changes

tama stage --session <your-session> --inspect
 tama stage --session <your-session>
 git commit -m 'Preserve the recorded operation cause'

Run these as separate commands. The commit guard checks the resulting index, not a future index that an earlier command on the same shell line might produce. Whole-path commits, --all, --include and pathspec-file commits refuse because they can import working-tree hunks after that inspection. Existing unrelated staged entries are preserved by staging. An entry or hunk your receipts do not establish passes only when no other session that still runs recorded it: the guard refuses the work of a running session, as the next paragraph describes, and takes over the work of sessions that stopped.

Git's commit-msg hook (tama hook review-commit) reads the same ownership from the index Git is about to commit, however the commit was spelled: git commit -a, an alias, sh -c "git commit …" or a script. The committing session is the one whose recorded agent process (pid in its session record under the session-control root) is an ancestor of the hook, each parent read from the kernel for that one process (proc_pidinfo with PROC_PIDTBSDINFO on macOS, /proc/<pid>/stat on Linux), so a sandbox that refuses to start ps changes nothing. A record names its process only while the process now at that pid started before the record file was last written: a session that ended leaves its record behind, and the kernel hands its pid to the next process that asks, so a process at the pid that started later (by the same kernel reading, against the boot time in /proc/stat on Linux) is another process and the record is left out. A record whose write time or whose process's start cannot be read refuses the commit with that cause. A process the kernel no longer has ends the walk; any other failure refuses the commit naming the kernel's answer and ending the process tree this command runs in cannot be read, since ending the walk there would read an agent's commit as the operator's. When such a session commits an index that is exactly its own recorded edits, the commit passes. An index that is more than that, or one that cannot be read against its receipts, is the work of other sessions as well: it passes when it carries no recorded edit of another session that still runs, and the committing session takes that stopped work over. Otherwise the commit is refused before history changes with the staged index carries recorded edits of sessions that still run, and a running session's work stays its own until it ends: <agent> session <session>, …, and the shell-line guard with BLOCKED: `<command>` stages recorded edits of sessions that still run, which stay theirs until they end: …; a running session whose recorded edits cannot be read against the index is named with that cause. An agent that sits idle with its process alive counts as running, so its edits stay its own until its process ends. When the committing session's transcript cannot be found, the commit is refused with this commit runs in <agent> session <session>, whose transcript cannot be found, so its staged index cannot be read against the session's recorded edits.

A commit no recorded session's process tree holds is read by what it carries. That is the operator's own commit, or one an agent started outside its own process tree (detached with nohup, setsid or a double fork, or handed to another daemon). Every session whose recorded agent process the kernel still has is asked whether some staged path holds exactly what its recorded edits make of that file. A commit carrying no running session's edit is the operator's and is not read for ownership. A commit that carries one is read against that session as if it had started it, and passes when the whole index is that session's edits; otherwise it is refused with this commit was started outside any agent session's process tree but carries running sessions' recorded edits, and is no one session's alone: <each session's finding>. A detached commit that stages only another session's recorded edits therefore reads as that session's commit. A commit made with --no-verify or with plumbing (git commit-tree) runs no hook and is read only by the shell-line guard.

Evidence and supported transitions

The transcript must identify the requested session. A successful result must match its recorded invocation. Only the result of a tool the hook vocabulary names as changing files (the harness's edit and write tools, a patch, a structural edit, a rename, move or delete) is a receipt: a read of a file or of a directory also reports the resolvedPath it read, and is no edit. Text edits use complete oldText/newText snapshots. A full-file write whose result reports only resolvedPath is read from its own content argument, every byte it left in the file; it observed no before-state, so its base is the session's own earlier state of that path when the session touched it before, and otherwise what the file held in the index being staged (in the commit check, what HEAD held). Its whole content is then the session's change, and the working-tree check below still requires those bytes to be in the file. A write result with neither an op nor a content argument refuses, naming the call. Recorded creation and deletion are distinct from an empty file.

A result may contain one file receipt, or a changes or perFileResults array of file receipts, one per file a call changed. Each member is bound to the same successful tool call and validated before publication; an empty array names no file and refuses nothing. A write with an explicit op and the corresponding snapshots uses the same transition reader. An update receipt that keeps no oldText/newText (the edit tool keeps only its numbered diff for a large file, such as a lockfile) is read by applying that diff to the path's state before it: the bytes the session's latest earlier receipt of the path left, or, for its first edit, what HEAD holds there. The diff's parts (the runs of lines between its empty lines) are placed one by one: a part stands where every one of its kept and removed lines reads in that state exactly as the diff shows it, at the numbers it shows, or, when the lines above it moved since the edit was made (another session's commit landed in HEAD, or another session's uncommitted lines stood in the file then), at the one such place after the part before it that is nearest to those numbers, and its added lines move with it. A part that reads so nowhere after the part before it gives that path alone its cause, the numbered diff of <path> does not apply: line <n>, shown as "…", with the lines the diff shows around it, reads so nowhere after line <m> of the state before the edit; one that reads so at two places equally near names both (… reads as shown at lines [<a>, <b>], equally near, so which one the edit changed cannot be told); and so does a path whose earlier receipt was refused or deleted it. A receipt missing the text its operation needs refuses its own path only (edit <call> of <path> (<op>) carries no <field>, so its bytes cannot be established). Real journey: tests/shared-checkout/numbered.rs (target shared_checkout_numbered, TAMA_STAGE_NUMBERED_CASE naming a capture with repository relative to the capture file, session and staged) stages a retained session whose receipts keep only numbered diffs onto the checkout's HEAD in an isolated index, requires each captured path staged and the commit guard to admit the result, and compares the operator's index and the working files afterwards.

The pre-write edit admission keeps immutable input bytes in tama-edit-snapshots under the repository's common Git directory, bound to the session, tool-call identifier and relative path. When the same invocation later has a successful numbered receipt, staging and commit inspection use that captured input rather than assuming the preceding receipt or HEAD still describes the file. This preserves intervening formatter changes without assigning them to the edit. A failed invocation authorizes nothing. Repeated admission of the same call must observe the same bytes; different input, an unreadable or malformed snapshot, an identity mismatch, non-text input for a numbered edit, or an update whose snapshot records no file refuses with the call, path and actual cause. Snapshot persistence failures refuse the edit before its tool runs.

Older calls without pre-write captures retain the recorded-history reconstruction: with named co-authors, numbered diffs are reconstructed only after their receipts have been ordered together by the recorded completion times. A later edit can therefore use the complete state an earlier co-author's successful receipt left, even when that state is not in HEAD. This does not supply an unrecorded intervening change: a diff that still cannot be applied is left out with cannot reconstruct edit <call> after receipt <prior-call>: <cause>, or names HEAD (no earlier receipt of this path among the named authors) as its baseline. Staging, native staging requests and commit ownership inspection share this reader; current working-file bytes are never substituted for missing historical evidence.

The retained capture for shared_checkout_numbered also accepts with, the co-author session identifiers, and omitted, a map from paths to their observed reconstruction causes. The journey stages the selected paths into its isolated index, checks that refused paths retain their exact HEAD bytes, and invokes the commit guard over the result. Staging and guard streams and exit statuses are retained beside the isolated run directory as JSON reports; preservation checks and removal of the isolated directory still run after a failure. A passing refused-path check does not qualify that path's missing source transition as repaired.

A part's outer kept lines are context the edit tool showed from the file as it read then, and in a file several sessions write some of them can be another session's uncommitted lines, which the session's own state does not hold. A part that reads nowhere as shown is read again with its outer kept lines left out, fewest first, from either end, and stands where what remains reads at one nearest place; the lines left out are not replayed (the state's own lines stand there), so another session's lines are never written by this session's change. Its removed lines and the kept lines between its changes are never left out, so a part whose change itself meets another session's lines keeps its cause. A part that shows only kept lines (the edit tool sometimes shows a lone line of context after the last change) changes nothing, so it is neither placed nor replayed and never refuses the edit. When the same number of left-out lines lets it read in more than one way the path is left out with … reads as shown once <n> of the kept lines around it are left out, but in more than one way, so which lines the edit changed cannot be told. A path whose earlier edits could not be read names the first such edit once: <path> has no known state since its edit <call>: <cause>.

A receipt of a path the repository ignores and does not track, such as a commit message or a note a session wrote under the checkout's ignored build directory, is part of no commit: git check-ignore on the receipts' path names reads which paths those are. Such a path is neither staged nor refuses staging, and the commit hook does not read it either, whatever its receipt holds, so a notes file several sessions append to never refuses a commit of the session's tracked files. A check-ignore that cannot read the paths refuses, naming the command and Git's stderr.

A file a session's own shell command wrote has no edit receipt: a lockfile a resolver rewrote, a generated source, the lockfiles of many checkouts one tool rewrote from one directory. The commit hook reads such a staged path as the session's when the working file last changed while one of the session's successful shell commands ran, between the transcript's record of the call and the record of its result as the file system times the file, and the index holds exactly the bytes the working file holds. Where the command ran does not decide it. A staged path that one of its commands wrote but whose staged bytes are not the file's is refused with staged path <path> is not the bytes the session's command <call> left in the working file; stage the file as that command wrote it; one that no receipt and no command of the session explains is refused with staged path <path> has no successful before/after edit receipt in <transcript>, and no shell command of the session was running when the file last changed. A commit whose session made no edit receipt in the checkout at all is read the same way, path by path; tama stage still refuses a session with no receipt in the checkout, since it stages only receipts.

Independent text changes merge; a file whose change overlaps another change to it, or whose creation or deletion meets another change, is left out and named under omitted with its cause, and the others are staged. Every proposed delta must still be present in the working tree. A file the session created and the index does not hold is present when every line the session staged stands in the working file in the same order: another session's lines added around and between them since stay in the working file, unstaged, for that session to stage. One whose own lines another session changed or removed since is left out (recorded changes to <path> are no longer present in the working tree: its lines no longer all stand in the working file in order; <path> is a file the session created and the index does not hold, so its later edits cannot be staged without its creation): its later edits started from the file with the other session's lines in it, which the index does not hold. Symlinks, unresolved index entries, non-UTF-8 content and unsupported transitions are named with the affected file. Staging keeps each existing file's indexed mode; a new file's mode comes from Git's observation of the real file.

A checkout whose index file is absent starts staging from HEAD (git read-tree HEAD); Git reads a missing index as empty, and staging onto that would stage the deletion of every tracked file. Only a repository whose HEAD has no commit yet starts from an empty index. An index file that holds no entry while HEAD holds files (emptied by some command) would read every tracked file as gone too; staging and inspection refuse it before reading any path: the index <index file> of <checkout> holds no entry while HEAD holds <n> file(s), so staging onto it would stage the deletion of every tracked file; nothing was staged. Find what emptied it …, restore it from HEAD with `git -C <checkout> read-tree HEAD` …, and stage again. When the caller's GIT_INDEX_FILE chose that file, the refusal says so after its path ((GIT_INDEX_FILE=<value> chose it, not the checkout's own index; unset it if that is not meant)): a shell that kept the variable from another checkout's private index reads every checkout's index as a fresh, empty file. Publishing reads the staged index against the one it replaces (the checkout's index file, or HEAD's files when there is none): a path the replaced index held that the staged one dropped while its file is still on disk was never staged by a session, since a staged deletion removes its file, so nothing is published and the run says the staged index of <checkout> holds <n> path(s) where the index it replaces holds <m>, and <k> of the dropped paths are still files on disk (first: <path>) ….

A file's mode is not a text edit, so no receipt carries it: the commit hook reads a staged mode against the working file instead. A staged mode that differs from HEAD's stands when it is the mode the working file holds, which is what git add or git update-index --chmod=+x|-x <path> stages; a change of mode alone is the checkout's own state and is read as no session's work, so restoring a dropped executable bit commits. A staged mode that is neither HEAD's nor the working file's was written into the index by hand (update-index --cacheinfo with a mode typed in) and refuses the commit: staged mode <mode> of <path> is neither HEAD's (<mode>) nor its working file's, so it was written into the index by hand; stage the mode the file holds with git update-index --chmod.

A session's change of a file is carried onto the file as it stands now, hunk by hunk: git diff --no-index --unified=0 cuts what one edit saw and left into hunks, and each hunk is placed where the lines it replaces stand: of the places they stand, the one whose surrounding lines read most like the edit's own (the lines before the hunk and after what it removes, compared outward until one differs), then the nearest to where they stood once the hunks before it are placed. Lines another session wrote around, above or right beside it, uncommitted when the edit was made or committed since, stay where they are and are not read as a conflict, and a hunk next to a repeated line (a closing brace, a blank line) is placed by the text around it. A hunk that only adds lines stands next to a line it followed or preceded; when the lines it adds already stand between the very lines they went between, it is already carried and is not added a second time, so a session's added function in a file other sessions also changed reads as present. A hunk whose lines stand nowhere but whose result does is already carried, and a removal whose lines stand nowhere is done. A hunk that stands nowhere after the hunk before it, and whose result stands nowhere either, was taken by another change; one that stands at two places alike in their surroundings and equally near cannot be placed. Either refuses that run, naming the hunk: session edits cannot be carried onto <path>: the edit's hunk after line <n> stands nowhere after line <m> of the file now, and neither does what it writes; the index and working tree are unchanged, or … stands at indexes [<a>, <b>] of the file now, equally near and alike in the <k> line(s) around them; …; a creation or deletion over another change refuses as creation or deletion overlaps another change to <path>: the state it is replayed onto holds <n bytes|no file>, the edit found <n bytes|no file> and left <n bytes|no file>; the index and working tree are unchanged. When the session's whole run of edits of a path is no longer in the file, because another session later undid an older one of them, the path is staged from the newest run of its edits whose change is still there: starting from each later edit in turn (from the file as that edit saw it), the edits from there on are replayed, and the first such run present in the working file is staged, saying stage: <path> staged from its edit <call> on; the older edits are no longer in the file: <cause>. Older edits another session undid are superseded, never brought back. A path none of whose runs is present, down to its newest edit alone, is left out with the newest edit's cause. The commit hook admits a staged path that its whole change, or any such newer run, applied to HEAD gives, and refuses with the cause only a staged path no run accounts for.

Output and diagnostics

{"session":String,"repository":String,"paths":[String],"omitted":[{"path":String,"cause":String}],"calls":[String],"tree":String,"applied":Boolean}

paths names the index entries changed by this operation; calls identifies the successful edit receipts used. tree is the candidate Git tree, not a build or verification verdict. The text output ends with No unstaged recorded text changes remain. only when nothing was staged and nothing was left out, as when a successful operation is repeated; when nothing was staged but some changes were left out it says Nothing was staged: <n> recorded change(s) remain unstaged, left out above with their causes. Staging preserves unrelated index entries, so the candidate tree alone does not assert that the whole index belongs to this session.

A file that cannot be staged is left out and named with its cause in omitted while every other file is staged: recorded edits that cannot be replayed, a file the session moved or removed or whose change another session overwrote (recorded changes to <path> are no longer present in the working tree: carrying it would make line <n> "<text>" where the file holds "<text>", naming the first line where carrying the change would alter the working file, or … carrying it would delete the file, … the working file is gone), one another session rewrote past the session's change (the numbered diff of <path> does not apply: …), a path Git will not take such as one under .git (Git did not prepare a new entry for <path>), and an overlap with another session's hunks. The text output lists each as left out <path>: <cause>; Desktop shows them in a Left out of this staging panel. A long session therefore commits the rest of its work while one file stands apart.

An absent transcript, invalid session identity, unmatched result, missing snapshot, index lock, unavailable Git command or filesystem failure exits nonzero and names the failed operation and cause; a stale edit or an overlap of one path is not a failure of the run, it leaves that path out (above). Git's stdout and stderr are retained in its failure. Failed staging does not publish the private index. Only staging that publishes takes Git's index lock (.git/index.lock); a held lock is not removed or retried. --inspect (and Inspect changes) and the commit gate's check of staged changes are reads: they take no index lock, so one that ends early (its reader closed the pipe, a signal) leaves no lock behind and never blocks the next staging. Scratch lives under the checkout's ignored .build/tama-stage, isolated by index path; a read works in its own read-<pid> directory there and removes it when it ends, naming one it cannot remove (staging read scratch <path> remains: <cause>). A scratch path that is not ignored or resolves through a symlink refuses. Whether the scratch is ignored is read with git check-ignore on its path name, without the literal pathspec magic the index operations use, because check-ignore refuses that magic; a GIT_LITERAL_PATHSPECS in the caller's environment does not reach it either.

Index entries whose object is missing

tama index repair [--repo <checkout>] [--apply] [--json]

An index that names an object its repository's store does not hold makes git status, every diff and every commit of the checkout fail, and the commit gate's replay of a session's edits refuses on it. Staging never writes such an entry: every entry Tama writes is preceded by hash-object -w and checked with cat-file -e, refused as the object <id> for <path> is not in this repository's store: …. tama index repair reads the index (Git's own, or the one GIT_INDEX_FILE names) and the store once each and names every entry whose object is missing. With --apply each is repaired: an object another checkout of the workspace holds under the same id is copied from there and its id checked; with none, the path is staged again from its working file (or removed from the index when the file is gone) and the answer says its staged content is lost. Text output: <repository>: <n> index entries, <m> naming an object the store does not hold, then per entry <path> <id>: copied from <checkout>, …: restaged from the working file; its staged content is lost, …: removed from the index; its staged content is lost or …: missing (run with --apply to repair). --json prints {"repository","index","index_variable","entries","missing":[{"path","object","copied_from","repair","lost"}],"emptied","strays","applied"}. A verb or option it does not take is refused with its usage; a Git command that fails is named with its words. Oko's per-pass probe index-missing-object finds such entries in every checkout and notes them on their class.

The same command names an index that holds no entry while HEAD tracks files. Such an index makes every tracked file read as staged for deletion, and one plain commit would delete the repository; no writer leaves it on purpose. Text output adds the index holds no entry while HEAD tracks <n> files, so every tracked file reads as staged for deletion (run with --apply to read the index back from HEAD), and --json carries "emptied": {"head_entries","restored"} (null otherwise). With --apply the index is read back from HEAD with git read-tree HEAD, which writes the index only, so the working files and every change they hold stay as they are. A repository whose HEAD names no commit, or tracks no file, is never read as emptied. The answer names the index file it read ("index") and, when GIT_INDEX_FILE is set, its value ("index_variable"); text output then adds read the index <file> that GIT_INDEX_FILE=<value> names, not necessarily the checkout's own, so an index read through a variable left from another checkout is seen before it is called emptied or repaired.

It also names the entries of an index that belong to no state of its checkout, which is what an index overwritten by another repository's index, or filled with staging of work this checkout does not hold, leaves behind. A foreign entry is a staged path HEAD does not track and the working tree does not hold: a commit would add a file nobody here has. A dropped entry is a path HEAD tracks, missing from the index, whose working file is present and not ignored: a commit would delete a file the checkout still has. A path taken out of tracking on purpose (git rm --cached beside a .gitignore line) is ignored and is not named. Text output adds <path> <object>: foreign, run with --apply to read it back from HEAD or <path>: dropped, …, and --json carries "strays": [{"path","shape","object","repaired"}]. With --apply both are read back from HEAD in one git reset -q HEAD -- <paths> with literal pathspecs, which writes the index only: a foreign entry leaves the index while its object stays in the store under the id the answer names, and a dropped entry gets HEAD's content back while its working file keeps every change. An emptied index is named whole, as above, and not entry by entry. Staged changes whose files the checkout holds are ordinary staging and are not named.

Desktop and native interface

Open Reviews → Session-owned staging, enter the session and checkout, then choose Inspect changes or Stage session changes. The screen shows paths, receipt calls, candidate tree and the exact refusal. It calls the same implementation through tama request stage, with body {"session":String,"repository":String,"inspect":Boolean,"paths":[String],"with":[String],"task":String,"fromHead":Boolean}; paths is optional and, when given, selects files as --path does, with is optional and names co-author sessions as --with does, task is optional and names the task taken over as --task does, and fromHead is optional and reads the staging index from HEAD first as --from-head does. This is the native request protocol, not a shell invocation of the staging command.

The Index repair panel below it takes a checkout path; Read index and Repair index send tama request index/repair with body {"repository":String,"apply":Boolean}, the same reading as tama index repair, and show the index file read, a warning naming GIT_INDEX_FILE when that variable chose it, the entry counts, an emptied index and each missing entry as the text output says it. A failure is shown and reported under tama.index.repair.

Real qualification

tests/shared-checkout/commit.rs (cargo test --test shared_checkout_commit) invokes the actual CLI against a retained capture of real session receipts, using a separate index inside the canonical checkout. Set TAMA_STAGE_SUFFIX_CASE to a capture of the suffix journey's form (repository, session, staged); every tree is read at run time from the checkout's HEAD, so a later edit by any session leaves the capture usable. This journey, selection.rs and hook.rs stage something and read it, so they take only a capture whose staged names at least one path; a capture whose paths are all accounted (several sessions wrote them and the capture cannot say which outcome is right) is the suffix journey's alone and is refused by these three as naming no staged path. No transcript or provider response is manufactured. A missing capture is a failed prerequisite, not a passing test.

The journey checks that inspection leaves the isolated index unchanged, that staging stages every captured path and that staging again changes nothing, and that an index whose entry for one captured path (one HEAD holds) is empty, where the session's change cannot stand, leaves that path out under omitted with its cause, keeps that entry and stages the rest. Whatever happens, the operator's index and the captured paths' working files are compared and the isolated directory is removed; the harness retains each command's streams, exit status and source identity, and the observed trees and failures are retained beside them.

tests/staged-prefix/shapes.rs (cargo test --test staged_receipt_shapes, TAMA_STAGE_SHAPES_CASE naming a capture with repository relative to the capture file, session, written, ignored and readSession) reads actual sessions' receipts: each file a session created with the harness's whole-file write is staged with --path into an isolated index started from HEAD and must hold exactly the working file's bytes; an inspection of the whole session must name none of the files it wrote under ignored paths, neither staged nor left out; and an inspection of a session that read a directory of the repository and edited files there must end successfully, the read being no edit. The operator's index and the captured files are compared and the isolated directory removed afterwards.

tests/shared-checkout/selection.rs (cargo test -p tama-cli --test shared_checkout_selection) reads a capture of the suffix journey's form (TAMA_STAGE_SUFFIX_CASE: repository, session, staged) and stages onto the checkout's HEAD in an isolated index, so the capture names no tree a later edit makes stale: it stages the session's edits with --path naming the first staged path and requires every staged path to be that file, then names a file the session never edited and requires the refusal naming it, the isolated index unchanged by that refusal, the operator's index unchanged throughout, and removes its isolated index afterwards.

tests/shared-checkout/continued.rs (cargo test --test shared_checkout_continued, TAMA_STAGE_CONTINUED_CASE naming a capture with repository relative to the capture file, session and continuedFile) reads a session OMP moved to a new transcript: the moved transcript is found under OMP's session root by its parentSession, and the journey records itself as the session's agent process and holds that transcript open as OMP does. tama stage --path of a file the session created only after the move must hold its working bytes in an isolated index started from HEAD, the commit guard must admit it, and the same index with the file rewritten to bytes no session recorded must be refused; with the transcript let go, as when the session's process has ended, staging finds the moved transcript as the newest of the session's and stages the file again. The operator's index and the file are compared and the isolated directory removed afterwards.

The earlier-owned-checkpoint regression is tests/staged-prefix/checkpoint.rs: cargo test --manifest-path rust/Cargo.toml -p tama-cli --test staged_prefix_checkpoint -- --ignored --nocapture. Set TAMA_STAGE_PREFIX_CASE to a retained capture with source (repository, session, baselineTree, expectedTree), prefixReport, prefixTree, foreignPrefixTree, foreignExpectedTree, conflictTree, conflictedFile and files. The prefix report must be the actual earlier successful staging output for that session and checkout, with applied: true and the same prefix tree; an inspection or handwritten response is not a staged checkpoint. The retained transcript must contain subsequent owned edits. All trees and receipts come from genuine sessions in the canonical checkout, so the capture is taken when such a staging happens and is valid only until the checkout moves past those trees.

The regression starts only its isolated index at that observed checkpoint and requires the later complete owned tree. A separate phase starts with another session’s non-overlapping change in the same shared file and requires that change to survive alongside the later owned edit. A real overlapping entry must instead remain unchanged and be named under omitted with its cause. The operator’s actual index and captured working files are checked after qualification failure as well as success; isolated-index cleanup is attempted either way. Actual Git command streams, candidate CLI identity and source patch, prior staging output, transition trees, failures and cleanup observations are retained. A failure to preserve state, clean up or retain the report cannot pass. This does not authorize foreign hunks or change the commit gate’s ownership baseline.

tests/shared-checkout/hook.rs (cargo test --test shared_checkout_commit_hook) reads a capture of the suffix journey's form (TAMA_STAGE_SUFFIX_CASE): it stages the captured session into an isolated index started from the checkout's HEAD with the built tama stage, rewrites the first staged path in that index to bytes no session recorded (its working file and one line more), then runs the built tama hook review-commit over it as Git's hook would, with a session record naming the test process as the session's agent process and an attested message. The hook must refuse, naming the session and that the staged index is not only its recorded edits; ownership is read before the harsh-review rounds, so no round is needed for that refusal. Whatever happened, the operator's index and the captured paths' working files are compared and the isolated directory is removed. That the session's own staged index is admitted is the suffix journey's commit-guard step.

tests/shared-checkout/suffix.rs (cargo test --test shared_checkout_suffix -- --ignored, TAMA_STAGE_SUFFIX_CASE naming a retained capture with repository relative to the capture file, session, staged, omitted and accounted; commit.rs, hook.rs and selection.rs read the same form and resolve repository the same way) reads an actual session whose older edit another session undid, or whose change another session also made, identically, right beside lines of its own: inspection must stage each staged path, leave each omitted path out with its cause, and stage or leave out with its cause each accounted path. It then stages the session with the built tama stage into an isolated index started from HEAD in the capture's ignored build area and asks the built commit guard (tama hook pre-bash on git commit -F, with the session's real transcript and the isolated index as Git's index) whether that index is only the session's recorded edits: the guard must admit it, ending normally with no decision, though the session's whole change no longer replays; a refusal or any other ending fails the journey. The independent harsh review review-commit also requires of a real commit is not this journey's subject. Whatever happened, the operator's index and the working files of every captured path (staged, omitted and accounted) are compared, the isolated directory is removed and each command's raw result, with every failure in the order it happened, is retained in .build/stage-qualification/suffix-commit-<pid>.json.

tests/coauthors/staging.rs (cargo test --test coauthors_staging, TAMA_STAGE_COAUTHOR_CASE naming a capture with repository relative to the capture file, session, with and shared) stages the session into an isolated index started from HEAD: without --with each shared path must be left out with a cause; with it each must be staged, the index must hold the tree the staging reported and, at each shared path, an entry that is not HEAD's, and the built commit guard must admit the index; a shared path rewritten to its working file plus a line no named session recorded must be refused by the guard as not only the session's recorded edits, naming the session and the path (a crash or another refusal fails the journey).

tests/coauthors/takeover.rs (cargo test --test coauthors_takeover, TAMA_STAGE_TAKEOVER_CASE naming a capture with repository relative to the capture file, session leading the task now, the stopped predecessor that held it, task, at least one taken path only the predecessor edited, a real foreignTask the session does not lead and a real unheld session that never held the task) reads the real Oko: with --with <predecessor> alone the taken paths must be neither reported staged nor changed in the index from HEAD's entries; with --task each must be reported staged, the index must hold the reported tree and a non-HEAD entry at each, and the built commit guard must admit the index; with foreignTask, or with unheld named instead, staging must be refused with its cause and leave the index's tree as it was. The operator's index and the taken paths' working files are compared and the isolated directory is removed whatever happened. A predecessor that still runs is refused before staging (still runs); no journey makes a running predecessor that held a real task.

tests/staged-tree/admitted.rs (cargo test --test staged_tree_admitted, TAMA_STAGED_TREE_CASE naming a capture with repository relative to the capture file, session and tree) reads a tree an author staged by hand and was refused on: a later own change of a file without the session's earlier ones, or an edit whose receipt keeps only the numbered diff of a file other sessions also changed. The tree is read into an isolated index in the checkout's ignored build area and the built commit guard, with the session's real transcript and no model declared, must admit it; the operator's index is compared and the isolated directory removed whatever happened.
