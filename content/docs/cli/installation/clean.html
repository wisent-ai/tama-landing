tama clean

Scans target repositories, asks Brama for one patch per repository per round, applies it with git apply, rejects rule-gaming, and re-scans until clean or the round limit is reached.

Invocation

tama clean (--repo <path> | --tree <dir> | --owner <gh-owner> | --me) [...]
           [--model <brama-route>] [--max-rounds <n>] [--skip <fragment>]
           [--note <text>] [--dry-run] [--json] [--hook <path>] [--clone-dir <dir>]

Target, hook, clone, and JSON options match find-violations. --model takes a Brama route, not a provider model name: Brama decides which provider answers it, holds the credentials, and the default route is -best. The default maximum is three rounds. --skip is repeatable, --note adds an operator instruction, and --dry-run prints the brief without asking for a patch.

Where the model comes from

Every Tama feature that needs a model calls Brama, the one authenticated provider-neutral gateway. No provider CLI is involved: earlier rounds spawned codex exec or kimi -p <brief> --yolo, one of which is not installed on an operator machine and the other refuses that argument pair, so a round exited at once and the loop reported unchanged violation counts round after round.

The address is resolved in this order: TAMA_OBJECTIVE_AUTHORITY_MODEL_ROUTER_URL, STADO_MODEL_ROUTER_URL or BRAMA_URL when one is set; then stado service directory connect brama --consumer <adapter>, which works the address out from where Brama is placed and who is asking; then the public hostname. Brama binds loopback on the host it is placed on, so the correct address differs on every machine and is never reconstructed from a host name.

The credential is a Skarbiec token minted for Tama's own consumer — tama by default — read from ~/.stado/<consumer>-skarbiec-token. The token carries its own call:brama#<route> grants and its own expiry, and Brama learns the client and its allowed routes by introspecting it at Skarbiec, so no vault item name, field name or signing secret is configured here. Run tama brama-check to see which address this machine resolves and what the gateway answers.

TAMA_CLEAN_AGENT_CMD replaces the model step with a command of your own, run in the repository with the brief in TAMA_CLEAN_BRIEF. That is how a round is pointed at a local agent harness or a test double.

Output and state

A round journals its model route, exit and violation count, and holds a per-repository lock. Text output reports CLEAN, remaining findings, or LOCKED (another clean in progress); JSON returns results and discovery problems. Unresolved, locked, or discovery-problem results exit 1.

Refusals and failures

A round that cannot act ends the run and records why in rounds[].rejected instead of repeating the same failure for every allowed round: an unreadable credential, a gateway that refuses the client, a patch that git apply rejects, and a target that is not a Git repository — a patch has nothing to apply to there — are all reported by their own sentence.

A round that leaves more to fix than it found is rejected too: its own patch is undone exactly — nothing it did not write is touched — and the next brief is told what got worse. That gate exists because one round split an oversized module into ten files no crate declared, so the compiler never saw them, the build stayed green, and the violation count went from 54 to 62 while the run reported success.

Setting the disable variable to 1 writes tama clean is disabled (TAMA_CLEAN_DISABLED=1), performs no cleanup, and exits 0. A route containing whitespace, an empty option value, a --max-rounds value below 1 or not a number, missing targets, and unknown arguments print usage and exit 2. Missing hook, repo, and tree paths use the same exact ... not found: <path> refusals as the scanner. Rule-gaming rounds are rejected and fed into the next round rather than accepted as clean.
