tama brama-check

Reports which Brama address this machine resolves, whether it passes the client's own transport policy, and what the gateway answers to a bearer-only GET /v1/models. That request is not billable and calls no provider.

Invocation

tama brama-check [--json]

Output and state

Text output is four lines: the chat endpoint the client would post to, the transport verdict, the probe address with the HTTP status it returned, and detail — the number of models offered on success, or Brama's own error body. --json emits the same fields as one object. No credential value is printed on either surface. The command writes no state and calls no provider.

The address is resolved exactly as clean and the objective reviewer resolve it: TAMA_OBJECTIVE_AUTHORITY_MODEL_ROUTER_URL, STADO_MODEL_ROUTER_URL or BRAMA_URL when one is set; then stado service directory connect brama --consumer operator; then the public hostname.

Reading the answer

200 means the gateway accepts this client's bearer, so a chat request that still fails is being refused for its agent signature or its model route, not its identity. 401 means the gateway does not know this bearer: it is in neither the boot table it read at start nor the authority that issued it, and the credential is repaired at that authority. 503 means the identity upstream is unavailable, which is the gateway's dependency and not this client's credential. 426 means the peer is neither loopback nor an approved HTTPS terminator.

Refusals and failures

Exits 1 unless the probe answered 200 through an allowed transport. A credential store that cannot be read exits 1 with brama-check: Skarbiec read <item>/<field> via <endpoint> as <consumer> failed, which names the item, the store and the consumer identity but never a value. An address off loopback that is not HTTPS, or one carrying credentials, a query or a fragment, is refused by the client before anything is sent.
