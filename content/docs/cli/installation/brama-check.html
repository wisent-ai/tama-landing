tama brama-check

Reports which Brama address this machine resolves, whether it passes the client's own transport policy, and what the gateway answers to a bearer-only GET /v1/models. That request is not billable and calls no provider.

Invocation

tama brama-check [--json]

Identity and credential

Tama's identity at the gateway is a Skarbiec consumer, tama by default and TAMA_BRAMA_CONSUMER when set. Its credential is a token minted for that consumer, read from ~/.stado/<consumer>-skarbiec-token or from TAMA_BRAMA_TOKEN_FILE. Mint one with skarbiec token-mint <consumer> --capabilities call:brama#<route>; the grants inside the token decide which routes that consumer may ask for, and Brama learns the client and its routes by introspecting the token at Skarbiec. No vault item name, field name or signing secret is configured in Tama, and none is printed by this command.

The address is resolved exactly as clean and the objective reviewer resolve it: TAMA_OBJECTIVE_AUTHORITY_MODEL_ROUTER_URL, STADO_MODEL_ROUTER_URL or BRAMA_URL when one is set; then stado service directory connect brama --consumer <adapter>, where the adapter is operator by default and TAMA_BRAMA_ADAPTER_CONSUMER when set; then the public hostname. The adapter selects an address, never an identity — the identity travels in the token.

Output and state

Text output is nine lines: the chat endpoint the client would post to, the transport verdict, the probe address with the HTTP status it returned, detail — the number of models offered on success, or Brama's own error body — then consumer, token file and route, then what this machine's authority answers about that route on that bearer, and finally one verdict. --json emits the same fields as one object, including local_grant and verdict. The command writes no state and calls no provider.

The route is best, Brama's own selector for the strongest subscription-backed model, and TAMA_OBJECTIVE_AUTHORITY_MODEL_ROUTE overrides it. The local answer comes from skarbiec grant verify <consumer> brama --action call --field <route> --token-file <path>, which is the half of the question that can be answered without the gateway.

Reading the answer

The verdict line exists because 401 stood for three different states at once, and on 2026-09-11 that ambiguity cost a day: the bearer had been valid at its own authority the whole time, while the gateway was deployed without the variables that let it ask. The four sentences are:

  • the gateway accepts this bearer — status 200; a chat request that still fails is refused for its route, not its identity.
  • this machine's authority grants the route on this bearer, and the gateway still refuses it — the credential here is correct and the gateway is not asking this authority. Check that its deployment carries WC_SKARBIEC_URL, BRAMA_SKARBIEC_CONSUMER and BRAMA_SKARBIEC_TOKEN_FILE: without all three the gateway admits only boot-table clients and refuses every workload token, whoever issued it.
  • this machine's authority does not grant this route to this consumer — issue it with skarbiec grant issue <consumer> --capabilities call:brama#<route> --token-file <path>. A grant whose field is not a route Brama serves is the same defect wearing a credential's clothes.
  • the gateway refuses this bearer and this machine's authority could not be asked — the local vault or its CLI is the first thing to repair.

503 means the identity upstream is unavailable, which is the gateway's dependency and not this client's credential. 426 means the peer is neither loopback nor an approved HTTPS terminator.

Refusals and failures

Exits 1 unless the probe answered 200 through an allowed transport. A missing token exits 1 with no Brama token for consumer <consumer> at <path>; mint one with …; an empty file is refused as is empty and a file holding more than one word as does not hold one token. An address off loopback that is not HTTPS, or one carrying credentials, a query or a fragment, is refused by the client before anything is sent.
