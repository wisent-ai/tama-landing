tama install

Installs Tama-managed user-global Git dispatchers for pre-commit and pre-push, preserving a pre-existing unmanaged hook once as .before-tama.

Before every push, repo-githooks/rust/pre-push invokes tama hook check-rust-format. For each non-deleted pushed ref it checks the referenced commit's tree using a private Git index and read-tree/checkout-index under the checkout's ignored .build/tama-rust-format/ directory, finds its tracked Cargo manifests, asks Cargo for their workspace roots and runs cargo fmt --all --check --manifest-path <Cargo.toml> once per workspace, including registered tests outside the crate directory, then removes the snapshot. A commit without tracked Cargo manifests needs no Rust check. This works without a Wisent release manifest or Stado installation. Declare .build/ in the repository's ignore policy; the gate refuses non-ignored scratch storage. No clone, branch checkout or change to the caller's index is made.

The formatter's file diffs and concrete failure reach Git's stderr. The working tree is not read: formatting that exists only uncommitted cannot qualify an unformatted commit, and another session's uncommitted edit in the same checkout cannot refuse a formatted one. Any pushed revision is checked, whether or not it is checked out. The gate changes no working source files. A missing committed root formatter configuration uses rustfmt's built-in defaults within the snapshot, never an uncommitted ancestor configuration. A workspace outside the snapshot is refused.

For products whose .wisent-release.json also declares a fmt quality gate, the dispatcher then runs stado quality check. Brama's push reviewer follows the formatting checks. A release install writes the same dispatcher. Graphical Git clients invoke the same hook and receive the same refusal and file diagnostics.

Example: a registered test needs formatting

If a push reports Diff in tests/harnesses/payload.rs, format the workspace that registers that test, commit the result, then push again:

cargo fmt --all --manifest-path rust/Cargo.toml
git add tests/harnesses/payload.rs
git commit -m "Format registered harness test"
git push

check-rust-format: push refused: commit <commit>: <operation and cause> and the formatter's diff identify the pushed commit and its files. Other refusals name an unreadable manifest, unresolved revision, failed Git export operation, unignored scratch path, escaping workspace or cleanup failure. A cleanup failure is retained alongside a formatter failure. Fix that cause; the remote branch is not updated by a refused push.

The real journeys tests/review/format.rs and tests/review/installed.mjs push through actual Git, Cargo/rustfmt, the managed dispatcher and the real review and LFS dependencies. They check that uncommitted formatting cannot repair an unformatted commit, and that a formatted commit can be pushed while another session's source and invalid formatter configuration remain unchanged. Remote refs and transferred LFS bytes establish the final state; command logs and source identities are retained. These definitions are not an executed qualification.

cargo test --manifest-path rust/Cargo.toml -p tama-cli --test review_format -- --ignored --nocapture
node --test tests/review/installed.mjs

Run only when qualification is permitted. The Cargo journey uses its built candidate; the installed journey records the actual sealed runtime identity. Both require Git LFS and authorized Brama review access; unavailable real dependencies are failures, not skipped passes.

Invocation

tama install [--git-hooks-path <path>] [--home <path>]
             [--set-git-config] [--no-git-config] [--json]

--git-hooks-path chooses the dispatcher directory. Otherwise Tama uses global core.hooksPath, falling back to ~/.config/git/hooks. --home controls home expansion and the Git configuration environment. --set-git-config writes global core.hooksPath; --no-git-config wins when both flags are present. --json selects structured output.

Output and state

Tama creates the hooks directory, writes executable managed dispatchers, and may create pre-commit.before-tama and pre-push.before-tama. Output names the resolved hooks path, both installed targets and whether Git global configuration changed.

Release activation and connection status

tama hooks release connects the managed dispatchers to global core.hooksPath after installing the sealed runtime. Publishing a repo-githooks file alone does not connect it to Git. Activation preserves an existing Git LFS hook as pre-push.before-tama; the dispatcher replays the original push arguments and ref input to that hook after formatting and review succeed. The sealed runtime's binaries lead its PATH.

tama hooks status
tama hooks status --home /path/to/home --json

Status reports the configured user-global directory, each dispatcher, whether the Rust gate is referenced and present, and the preserved original hook path. The same descriptions appear in Desktop's installation plan. This is a wiring inspection, not a successful push claim. Repository-local core.hooksPath overrides are outside this user-global report.

If the runtime installs but connecting Git fails, release activation refuses and names that operation and its cause. If a foreign hook and its .before-tama backup contain different content, installation refuses instead of overwriting either version. Resolve that hook-chain conflict before activating again. An emergency-disabled dispatcher remains protected from implicit reactivation.

Refusals and failures

Filesystem and process errors are written to stderr and exit 1. When requested Git configuration returns nonzero, Tama reports Git's stderr, or exactly git config failed when Git produced no message. Without --set-git-config, the command deliberately leaves Git configuration untouched.
