tama install

Installs Tama-managed user-global Git dispatchers for pre-commit and pre-push, preserving a pre-existing unmanaged hook once as .before-tama.

Before every push, repo-githooks/rust/pre-push invokes tama hook check-rust-format. For each non-deleted pushed ref it checks the referenced commit's tree using a private Git index and read-tree/checkout-index under the checkout's ignored .build/tama-rust-format/ directory, finds its tracked Cargo manifests, asks Cargo for their workspace roots and runs cargo fmt --all --check --manifest-path <Cargo.toml> once per workspace, including registered tests outside the crate directory, then removes the snapshot. A commit without tracked Cargo manifests needs no Rust check. This works without a Wisent release manifest or Stado installation. Declare .build/ in the repository's ignore policy; the gate refuses non-ignored scratch storage. No clone, branch checkout or change to the caller's index is made.

The formatter's file diffs and concrete failure reach Git's stderr. The working tree is not read: formatting that exists only uncommitted cannot qualify an unformatted commit, and another session's uncommitted edit in the same checkout cannot refuse a formatted one. Any pushed revision is checked, whether or not it is checked out. The gate changes no working source files. A missing committed root formatter configuration uses rustfmt's built-in defaults within the snapshot, never an uncommitted ancestor configuration. A workspace outside the snapshot is refused.

For products whose .wisent-release.json also declares a fmt quality gate, the dispatcher then runs stado quality check. Brama's push reviewer follows the formatting checks. A release install writes the same dispatcher. Graphical Git clients invoke the same hook and receive the same refusal and file diagnostics.

Example: a registered test needs formatting

If a push reports Diff in tests/harnesses/payload.rs, format the workspace that registers that test, commit the result, then push again:

cargo fmt --all --manifest-path rust/Cargo.toml
git add tests/harnesses/payload.rs
git commit -m "Format registered harness test"
git push

check-rust-format: push refused: commit <commit>: <operation and cause> and the formatter's diff identify the pushed commit and its files. Other refusals name an unreadable manifest, unresolved revision, failed Git export operation, unignored scratch path, escaping workspace or cleanup failure. A cleanup failure is retained alongside a formatter failure. Fix that cause; the remote branch is not updated by a refused push.

The real journeys tests/review/format.rs and tests/review/installed.mjs push through actual Git, Cargo/rustfmt, the managed dispatcher and the real review and LFS dependencies. They check that uncommitted formatting cannot repair an unformatted commit, and that a formatted commit can be pushed while another session's source and invalid formatter configuration remain unchanged. Remote refs and transferred LFS bytes establish the final state; command logs and source identities are retained. These definitions are not an executed qualification.

cargo test --manifest-path rust/Cargo.toml -p tama-cli --test review_format -- --ignored --nocapture
node --test tests/review/installed.mjs

Run only when qualification is permitted. Set TAMA_TEST_SOURCE_REVISION to the exact committed candidate for the Cargo journey; it refuses a different revision or edited tracked source and retains the executable digest before the first push. The installed journey records the actual sealed runtime identity. Both require Git LFS and authorized Brama review access; unavailable real dependencies are failures, not skipped passes.

Reviewing the committed file, not only the patch

The reviewer receives every new commit's message and patch, followed by complete UTF-8 text for its changed files. Each source record names the commit, path, Git object and mode. Imports, persisted fields and guards outside a diff hunk remain visible. Source comes from immutable Git objects, never uncommitted files; merge-parent changes are deduplicated by path in the resulting commit. Deleted content remains in the patch. Binary blobs and submodule references are explicitly identified without claiming to review omitted contents.

A failed Git read or unreadable path metadata refuses the review with its operation and cause. A malformed or unavailable reviewer response is not a source verdict and cannot authorize the push. A source finding must name the actual commit and file; a missing line in a patch does not establish that it is absent from the file. Command-line and graphical Git pushes use this same dispatcher and diagnostic stream.

Every finding is confronted with the commit it names

A BLOCK is a findings document: BLOCK: {"findings":[{"commit","path","quote","problem","require"}]}, where quote is one line copied from that path at that commit. The hook reads each named path at the named commit (git show <commit>:<path>) and keeps a finding only when the quoted text is there, whitespace runs aside; a finding on a commit that is not being pushed, on a path that commit does not hold, with no quote, or with a quote the file does not contain is set aside and named in the refusal as set aside, not in the commits: <commit>:<path> "<problem>": <why>. A refusal with a grounded finding reads the reviewer refused the push: followed by one line per finding: <commit>:<path> at "<quote>": <problem> Required: <require>.

When no finding is grounded, the reviewer is asked once more with the findings it made, why each was set aside, and the complete text of every path it named as its commit holds it. A PASS there passes the push; a grounded finding refuses it as above; findings that are ungrounded again refuse the push as the reviewer alleged text the commits do not contain, twice, and found nothing verifiable; the push is not let through unreviewed, with each finding set aside listed. A BLOCK that is not the findings document is refused as the BLOCK reason is not the findings document the review asks for (<parse error>); nothing passes on a reviewer's word the commits do not bear out, and nothing passes unreviewed.

Every exchange is retained under Tama's state directory (~/Library/Application Support/Tama/review-push/<instant>-<pid>-<local object>/ on macOS): envelope.txt is what the reviewer read, answer.txt its verdict, grounding.txt the findings set aside, and reassessment-envelope.txt, reassessment-answer.txt and reassessment-grounding.txt the second round when one ran. result.json records outcome as pass, source_finding or review_failure, and detail retains the actual refusal or failure. The refusal names the directory: review retained at <directory>. The real source-refusal test requires source_finding on the actual pushed commit; unavailable review or ungrounded allegations cannot satisfy that case.

Grounded source findings ask the caller to repair the unpublished commits. Git-read, transport, protocol and ungrounded-review failures ask the caller to repair the named review operation or dependency instead: a failed review does not establish a source defect. Both still refuse publication. A failure retaining the outcome also refuses; it cannot become a successful review.

The real review_push journey uses Git, Node and the configured reviewer. It first runs and pushes a module whose new test uses an existing import outside the diff, despite a conflicting uncommitted edit; then it commits the genuinely missing import, observes Node fail, and requires the review to refuse that commit without changing the remote ref. It retains command outputs, exit statuses, remote state, candidate revision and binary digest beneath Cargo's build directory.

cargo test --manifest-path rust/Cargo.toml -p tama-cli --test review_push -- --ignored --nocapture

Set TAMA_TEST_SOURCE_REVISION to the exact candidate and run only when qualification is permitted. The journey requires a real configured model provider and Node; an infrastructure refusal is not a passing source-refusal case. Source-context inclusion does not by itself qualify the reviewer's factual accuracy or an installed runtime.

The separate real outage journey requires the configured reviewer actually to refuse with subscription_reauthorization_required. It changes no provider configuration, creates only an isolated Git fixture, and verifies review_failure, the actual dependency cause, an unchanged remote and an unchanged candidate. Run it only in that declared failure condition and when qualification is permitted; it is not part of the healthy-review journey:

cargo test --manifest-path rust/Cargo.toml -p tama-cli --test review_unavailable -- --ignored --nocapture

Invocation

tama install [--git-hooks-path <path>] [--home <path>]
             [--set-git-config] [--no-git-config] [--json]

--git-hooks-path chooses the dispatcher directory. Otherwise Tama uses global core.hooksPath, falling back to ~/.config/git/hooks. --home controls home expansion and the Git configuration environment. --set-git-config writes global core.hooksPath; --no-git-config wins when both flags are present. --json selects structured output.

Output and state

Tama creates the hooks directory, writes executable managed dispatchers, and may create pre-commit.before-tama and pre-push.before-tama. Output names the resolved hooks path, both installed targets and whether Git global configuration changed.

Release activation and connection status

tama hooks release connects the managed dispatchers to global core.hooksPath after installing the sealed runtime. Publishing a repo-githooks file alone does not connect it to Git. Activation preserves an existing Git LFS hook as pre-push.before-tama; the dispatcher replays the original push arguments and ref input to that hook after formatting and review succeed. The sealed runtime's binaries lead its PATH.

Each dispatch stores Git's ref input in a private, uniquely allocated directory under Tama state: ~/Library/Application Support/Tama/git-dispatch on macOS, or $XDG_STATE_HOME/tama/git-dispatch on other Unix hosts (~/.local/state/tama/git-dispatch when that variable is absent). It does not use the system temporary directory. Normal completion, refusal, and handled termination remove that dispatch's input and directory; allocation or input-write failure refuses the Git operation before any chained hook runs.

Reviewer HTTP diagnostics report measured DNS lookup, TCP connection, TLS, first-response-byte and total transfer times, alongside the actual status and Brama cause. A fast readiness response is not evidence that the authenticated review request answered quickly, and a degraded gateway is not evidence that every route is unavailable. No inferred outage, successful process or empty model reply authorizes an unreviewed push. Malformed response JSON retains its parser cause; absent or non-text normalized content names the exact field.

tama hooks status
tama hooks status --home /path/to/home --json

Status reports the configured user-global directory, each dispatcher, whether the Rust gate is referenced and present, and the preserved original hook path. The same descriptions appear in Desktop's installation plan. This is a wiring inspection, not a successful push claim. Repository-local core.hooksPath overrides are outside this user-global report.

If the runtime installs but connecting Git fails, release activation refuses and names that operation and its cause. If a foreign hook and its .before-tama backup contain different content, installation refuses instead of overwriting either version. Resolve that hook-chain conflict before activating again. An emergency-disabled dispatcher remains protected from implicit reactivation.

Refusals and failures

Filesystem and process errors are written to stderr and exit 1. When requested Git configuration returns nonzero, Tama reports Git's stderr, or exactly git config failed when Git produced no message. Without --set-git-config, the command deliberately leaves Git configuration untouched.
