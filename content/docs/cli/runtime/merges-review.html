tama merges review

The damage review of branch merges already on main. It reads every checkout under the root, lists each merge on main's first-parent line since the date whose subject is the branch merger's own (Merge <branch> into main), and reports what each one left on main today: files over the line limit it added or grew, and paths it carried back after main had deleted them. Whether the merged source compiles is the release build's answer, not this reader's.

Invocation

tama merges review --root <PATH> --since <YYYY-MM-DD> [--json]

Inputs and options

OptionMeaning
--root <PATH>Required. The directory whose checkouts are walked; there is no default root
--since <YYYY-MM-DD>Required. Merges on main's first-parent line from this date on are reviewed
--jsonPrints the document below instead of one text line per merge

What it prints

One line per merge, as text:

<repository> <commit> <branch>: clean|DAMAGE; over the limit: <files>; carried back: <paths>
<repository>: unreadable: <git's error>

A file over the limit is one the merge added or grew past the line limit and that is still over it on main today; a carried-back path is one main had deleted and the merge re-added. A merge the branch had already landed as an equivalent commit is marked already in main as an equivalent commit. This command changes nothing.

Output document

Under --json, one row per merge; a checkout git could not read is a row with error. The desktop's Merges screen receives exactly this document, so the two cannot disagree:

[{"repository":String,"commit":String,"branch":String,"oversized":[String],"revived":[String],"damaged":Boolean},{"repository":String,"error":String}]

Exit status

Zero when no merge left damage; one when any did, in both text and JSON form, so a scheduled run fails on the finding. A wrong invocation — a verb other than review, an unknown option, or a missing --root or --since — prints the usage and exits two.
