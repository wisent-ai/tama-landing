tama request

Answers one Tama Desktop request and exits: the JSON body on stdin, NDJSON events on stdout. Tama Desktop runs one tama request process per operation, so no Tama process stays running between two operations and no port is opened.

Invocation

tama request <operation> [--root <release-path>]

<operation> names one operation from the table below. --root selects the sealed hook release the operation reads; the desktop passes the release bundled into the app. The body is read from stdin to its end before anything runs, and an empty body is {}, so an operation that takes no fields needs no input: tama request coverage < /dev/null.

The justification operations reuse tama justify validation and registry transactions. They use the process's home and runtime transcript directory; a request cannot choose another home or transcript source. Recording requests reject unknown fields, and none of these operations issues capabilities, enables hooks or starts Cua Driver.

Output and state

stdout carries only NDJSON events. A bounded operation prints exactly one:

{"type":"response","status":<status>,"json":{…}}

status is 200 for an answer, and json is the document the matching command prints. Any other status is a refusal named in HTTP's vocabulary — 400 a request the operation refuses, 403 an operation disabled on this machine, 404 an unknown operation, 500 a failure while it ran — and its json is {"error": "<one sentence>"}, the product's own refusal, verbatim.

A streamed job (violations/scan, violations/clean) prints its own output as it happens, then one result:

{"type":"log","stream":"stdout"|"stderr","chunk":"…"}   (zero or more)
{"type":"result","status":<exit-code>,"json":{…}}       (exactly one, last)

The result's status is the exit code the command would have ended with — for a scan, 1 means violations were found, not that the scan failed — and json is its document. A job refused before it starts prints one response instead. The process exits 0 after a 200 response, 1 after any other response, and with the job's own status after a result. Tama keeps no state of its own for a request; the operation writes what the matching command writes, and cleanup may modify the requested repository.

Refusals and failures

  • No operation: request requires an operation, exit 2, nothing on stdout.
  • A second positional argument: unexpected request argument: <argument>, exit 2.
  • Any option but --root: unknown request option: <option>, and missing value for --root for a bare --root; both exit 2.
  • An unknown operation: a 404 response, unknown operation: <operation>.
  • A body that does not parse: a 400 response, request body is not valid JSON.
  • Unreadable stdin: failed to read the request body from stdin: <reason> on stderr, exit 1, nothing on stdout.
  • A missing HOME for the build and justification operations: a 500 response, HOME is not set.
  • Policy import requires a nonempty sourcePath and a supported bundle. Invalid input returns the core refusal; conflict and rejected results remain structured documents with no partial writes.
  • A reader that closes stdout ends the process at its next event. Tama Desktop ends the whole process tree when a scan or cleanup is cancelled or the app quits.
