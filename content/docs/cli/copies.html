tama copies

Opens the command group that reports and removes the second full checkouts under roots you name, because a repository copy is a checkout of a repository you already have that git knows nothing about.

Invocation

tama copies <command>

Commands:
  list   [--root <PATH>]... [--json]                     Every second full checkout under the roots
  remove [--root <PATH>]... [--except <PATH>]... [--only <PATH>]... [--apply] [--force] [--json]  Remove them; previews unless --apply

<command> is required and must be one of the two linked leaves below.

Command tree

  • tama copies list [--root <PATH>]... [--json] — every second full checkout under the roots.
  • tama copies remove [--root <PATH>]... [--except <PATH>]... [--only <PATH>]... [--apply] [--force] [--json] — remove them; previews unless --apply.

The noun this group owns

block-repository-copies refuses two nouns, and until this group existed only one of them could be reclaimed:

  • A linked worktree is a checkout whose .git is a file pointing into the owning repository's .git/worktrees/<name>. Git tracks it, and tama worktrees removes it.
  • A repository copy is a second checkout with its own .git directory, which a clone of a local path or a recursive copy produces. The original knows nothing about it, so no git worktree command reaches it — and until 2026-09-09 no command did. On the machine this group was written for, that meant an 8.4 GiB clone of one upstream in backends/.work/content-platform-upstream-https and 45 nested checkouts holding 24 GiB in total, none of them reachable by any product surface.

A pass reports every linked worktree it crosses and never removes one, so a clean copies pass cannot read as "one checkout per repository" when it is not.

What a pass proves before deleting anything

A copy goes by deleting its directory, which git cannot undo and no remote can restore, so each candidate is judged first. In this order, one sentence each:

  • uncommitted-changes — git status --porcelain prints something.
  • commits-not-on-remote — git log --branches --not --remotes prints something, so history exists only there.
  • no-origin-remote — nothing to compare against.
  • no-canonical-checkout — no checkout of the same repository sits under the roots given, so this directory is the only one here. --only is how an operator answers that one.
  • owns-linked-worktrees — deleting it would orphan git's records in .git/worktrees; remove those first with tama worktrees remove.

A candidate git will not answer for at all is reported under unreadable and never removed.

--except and --only are remove options, and never both

--except spares one copy: it is not removed, not counted as removable, and never produces a refusal. --only narrows the pass to the paths it names and accepts them as removable even when they are the sole checkout of their repository here — every refusal that protects history still applies to them. They are two answers to the same question, so a command carrying both is a usage error, and so is a value that matches no copy the pass found.

Two checkouts of one repository, both at the top

Two directories directly under a root can share an origin: on this machine Wisent/wisent-compute and Wisent/stado are both checkouts of github.com/wisent-ai/stado. A pass reports that pair and removes neither, because which one to keep is the operator's call and a sort order would have deleted 69 GB of the tree the product is built from.

--root has no default, deliberately

--root is repeatable and required at least once on both leaves. Omitting it is a usage error, not a full-machine walk:

tama copies needs at least one --root; a machine-wide default would walk directories Tama does not own.

The named root itself is a canonical checkout, never a candidate: naming one repository as the root reports the clones inside it, not the repository.

Discovery and authority

tama_violations::repo_discovery's discover_every_checkout_deep(root) walks every checkout under each root, including the ones the owning repository ignores, and unlike the content scan it also walks vendor, target, build, .build and dist — a pass whose purpose is finding second checkouts cannot inherit a speed list that hides them. node_modules, Pods, SourcePackages and checkouts stay pruned: what lives there is a package manager's working state, which it re-resolves. Git is then the authority on each candidate: status, unpublished commits, and its origin remote.

Output and state

The group itself performs no action and takes no options. list and a bare remove mutate nothing; only remove --apply deletes anything, and it is all-or-nothing: a pass with any refusal outstanding removes none of the copies it selected. Both leaves print a text report by default and an exact JSON document under --json, and both are also reachable on the loopback desktop backend as POST /v1/copies/list and POST /v1/copies/remove (tama serve), which is what the Copies screen of Tama Desktop drives.

Refusals and failures

Exit 0 is success, exit 1 is an operational failure or a refused --apply, and exit 2 is a usage error — a missing or unknown leaf, a leaf invoked without --root, --except together with --only, or either of them naming a path this pass did not find. Each leaf page carries its own exact refusal sentences.
