tama assignment attest

Reads a task's own attestation that it is finished and says whether it stands. On a machine that declared no model (tama model-provider set --none), this is what the stop gates read in place of a model's judgement, so a session can end and its work can be accepted with neither Brama nor any other model installed.

Invocation

tama assignment attest FILE [--session SESSION_ID | --commit SHA] [--json]

FILE is one JSON document. With --session an attestation that stands is recorded for that session under the Tama state root (attestations/<session>.json), which is where the stop gates look for it; one that does not stand is never recorded. Without --session or --commit the command only reads.

A pushed commit

With --commit SHA (any spelling Git resolves in the current repository) FILE attests that commit against the push reviewer's standard, declared in push_attestations.json: every pushed patch read line by line; no defect; no needless abstraction or duplication; no swallowed error or fallback; no guessed number; no failure hidden by pausing or retrying; no narrating comment, host, account, date or internal id; tests that exercise behaviour; no commit that only reformats or patches another; documentation that matches the code; and the harsh senior review, with harsh_senior_review_findings empty. Each claim is explained in at least the operator's stated number of words. One that stands is recorded under push-attestations/<full sha>.json, where review-push reads it for each pushed tip when no model is declared; the output says FILE attests commit SHA. --session and --commit together are refused.

What an attestation holds

{
  "attestations": {
    "read_what_the_user_really_wants": {"confirmed": true, "how": "…"},
    "…": {"confirmed": true, "how": "…"}
  },
  "next_steps": [],
  "harsh_senior_review_findings": []
}

The claims are declared in rust/crates/tama-hook-tools/src/ports/task_attestation/attestations.json, and every one must be present with "confirmed": true and a how that explains, in the agent's own words, how the claim holds, in at least the number of words the operator stated (attestation_min_words in the stated-numbers declaration, with his words beside it):

  • read_what_the_user_really_wants — the messages, what they mean beyond their words, and what the user refuses.
  • read_existing_rules_and_earlier_answers — the rules and the user's earlier answers on this subject, none of them broken.
  • wrote_real_tests_that_passed — real tests of the actual product, its success path and refusals, passing.
  • analyzed_how_it_fits_other_tasks — what it unblocks, what it touches, what of the other tasks and defects remains.
  • fixed_the_cause_not_the_symptom — the same failure does not return for the next case.
  • cli_gui_docs_match — the CLI, the GUI and the documentation carry the same behaviour.
  • delivered — committed and pushed, with what a release still needs named.
  • no_blockers_task_fully_closed — nothing blocks the task.
  • nothing_further_is_possible_even_with_operator_work — even with the operator's own work there is nothing further.
  • harsh_senior_review_performed — as a very strict senior engineer who hates AI, what was attacked, what was checked, and why each attack failed.

Two lists must be present and empty. next_steps: a step that continues the task is the task's work, asked for or not, so it is done before attesting. harsh_senior_review_findings: every finding of that review means the task is not finished.

What is checked needs no model: presence, confirmation, length and the empty lists. Whether the words are true cannot be decided without a model; they stay on record, and a false one is the agent's defect.

Output

An attestation that stands prints assignment attest: FILE attests a finished task (and recorded at <path> with --session) and exits 0. Otherwise every reason is printed on its own line and the exit status is 1. --json prints {"file", "finished", "refusals", "recorded"}.

Tama Desktop sends the same reading as tama request assignment/attest with {"attestation": {...}, "session": "<id>"}; the answer is {"finished", "refusals", "recorded"} with the same sentences. A refused attestation is an answer, not a failed request.

Refusals

  • attestations.<key> is missing: attest "<claim>"
  • attestations.<key>.confirmed is not true: the task is not finished while "<claim>" does not hold
  • attestations.<key>.how is missing: explain in your own words how "<claim>" holds
  • attestations.<key>.how explains in N words how "<claim>" holds; the operator asks for at least M
  • <list> names N item(s); <why>: <the items> and <list> is missing: write it as a list, and attest only when it is empty (<why>)
  • the attestation FILE cannot be read: <cause>, FILE is not JSON: <cause>, --session needs the session id, unknown option <flag> and the attestation stands but was not recorded: <cause> — exit 1.
  • At a stop gate with no model declared: session <id> recorded none: write it and record it with `tama assignment attest FILE --session <id>`, or session <id>'s recorded attestation does not stand: <reasons>; a hook payload with no session_id is refused as an infrastructure failure.

Tests

tests/task-attestation/ runs the built binary in an isolated home: attest.rs (a complete attestation, a missing claim, an unconfirmed and short claim, non-empty lists), no_model.rs (set --none, check refused, a stop gate refusing without and passing with a recorded attestation), push.rs (a real repository's commit refused by review-push without an attestation, an attestation with a finding refused and not recorded, then the push passing once one stands) and desktop.rs (the Desktop operations). The claims and the word minimum are read from the product's own declarations.
