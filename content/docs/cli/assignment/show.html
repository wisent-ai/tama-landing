tama assignment show

Prints one session's newest operator instruction verbatim together with Oko's current task ledger, then records that both were read. A question about the task is not itself a replacement task, and a session summary is not a source of task state.

Invocation

tama assignment show --session SESSION_ID [--json]

--session is required. --json prints the instruction fields and Oko's report under ledger. The readable form also prints the open defects of the products the session declared with tama task scope set, each with its id, product, title and Oko's repair plan (or the oko defects plan command when none is written), and then the standing rules. The defect list is the one the Stop guard holds the turn to, less the defects an open oko blockers entry carries, so a session reads the register before it records a defect again or leaves a known one untouched. When Oko cannot be read the section says so and names the failed call. The stop refusal names the companion tama from its own installed release, so its recovery command does not select an older executable from PATH.

A defect recorded with found_in naming this session is listed, and holds the Stop guard, whatever product it is filed under: the session that recorded it has just been told what to repair. A session with no declared repository still sees those.

After the defects it prints the work other sessions declared on the same repositories: every tama task scope set declaration of another session that shares a repository with this one's and names a task or a defect, newest first, as date, session, shared repositories, task or defect, the operator's words. Work assigned in a parallel or earlier session is the operator's work too, so it is in front of the session before it answers that a task is not on its list. A session that declared nothing sees no such section.

After the standing rules it prints the operator's rulings from Oko's ruling register (oko rulings list): for each task or defect he decided, the newest ruling, with its session and message number and his words. The same block is what inject-operator-rules puts in front of a session when it starts or resumes after compaction, so a session knows what he already decided before it asks him. An existing ruling register that cannot be read or decoded refuses restoration with its path and cause; a missing register remains the documented initial state with no recorded rulings.

Standing-rule restoration is required, not a diagnostic substitute. If oko tasks rules --all --json cannot run, fails or returns an invalid report, or the ruling register cannot be read, tama hook inject-operator-rules exits unsuccessfully, emits no context payload and writes TAMA_HOOK_INFRASTRUCTURE: cannot restore operator rules for SessionStart: <operation and cause> to stderr. The readable assignment command propagates that same failure and writes no successful read receipt. A successfully read empty ledger remains distinct from an unavailable ledger; standing rules without required rulings are not complete restored context.

tests/operator-rules/distinct.rs covers real-ledger replay, a genuinely absent Oko executable, a real filesystem refusal when a directory is selected as the ruling-register file, and malformed JSON in an isolated ruling register. Refusal cases run the built hook, retain commands, exit status, stderr and the observed operating-system or parser cause beside the source revision, and check that no replacement or partial context is emitted. Evidence setup refuses a modified tracked source tree. Ruling-register journeys require a successful read of the real Oko ledger and never alter the operator's register. Run qualification only when authorized; source changes do not establish that an installed provider or graphical session has restored its rules.

The reading asks Oko's registers for open items only, each in one call: the session's task ledger (oko tasks --session ID --read-only --json), the open defects of every product (oko defects list --open --json, so the closed and withdrawn records never travel), the standing rules (oko tasks rules --all --json) and the rulings. It never reads a record one at a time, and it never cuts itself off: a reading that is slow names, on stderr, the Oko call it is waiting on (OKO_TRACE_REQUESTS). The real test is tests/assignment/show_registers.rs (cargo test -p tama-cli --test assignment_show_registers, with TAMA_TEST_ASSIGNMENT_SESSION naming a session whose instruction this machine captured): it runs both forms against the machine's own Oko, checks that the open-defects section names exactly the defects oko defects list --open holds, and writes each form's wall time to its report beside the source revision.

Output and state

Each session has its own captured instruction and separate read receipt under the Tama state root. TAMA_ASSIGNMENT_STATE selects a base filename for this namespace, not a shared assignment file. An older machine-wide record is not adopted as another session's instruction. The capture preserves whitespace, and even an identical instruction submitted in a new turn requires a new read.

The reader calls oko tasks --session SESSION_ID --read-only --json. TAMA_OKO_CLI selects a different Oko executable; OKO_TRANSCRIPT_INDEX_PATH, when declared, is passed as --db. Oko reads the selected transcript and the shared ledger's recorded classifications, evidence and relations as the signed-in member. A local transcript alone does not replace those shared records. Human-attributed OMP steering is an operator message; runtime steering is not. See Oko's task reader for the supported command group and refusal details.

A successful read exits 0 and writes a receipt only after delivering the output. The receipt binds both the captured turn and the Oko report. block-stale-assignment reads Oko again before allowing the turn to end: a new instruction, changed task state or changed selected index invalidates the receipt. One session cannot acknowledge another, and a slow read cannot overwrite a newer instruction.

Code authors and later batch tests

Writing code ends with commit, push and an accepted oko tasks submit handoff. Oko retains separate author and qualification states: an unmet acceptance check or recorded blocker keeps the task open even after a handoff is accepted. Tama reads that state through the existing ledger; it does not demand a per-task build or treat queued tests as passed. The later Stado batch covers the accumulated revisions. Failed qualification reopens the affected task, so the next ledger read again reports executable work. oko tasks qualification refreshes recorded results without starting a build. A commit string alone is not an accepted handoff or a successful qualification.

Refusals and failures

  • An unknown command, unknown option, missing session or missing option value exits 2 and explains the required invocation.
  • A missing or unreadable instruction exits 1 and names the session; check record-current-assignment. Another session's record is never a fallback.
  • An unavailable Oko executable, unknown session, unreadable index or transcript, failed process or invalid report exits 1. The diagnostic identifies the actual operation and error. A failed standing-rule read is not converted into an empty rule list or a successful readable assignment.
  • A new instruction arriving during the read requires another read. Failed output delivery or receipt writing exits 1 without acknowledging the new state.
  • The stop guard refuses when it cannot verify the current state, rather than accepting a stale receipt. With no captured instruction it preserves the existing no-record policy; a stop event without a session identifier is refused.
