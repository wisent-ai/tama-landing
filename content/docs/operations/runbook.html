Runbook

Something refused — which sentence are you holding, what does it mean, and what do you check next? Every heading below is an exact string from this repository's sources or a state you can reproduce; each entry says where the sentence comes from, what it is really telling you, and the first read-only command to run. Attribution tooling is in scripts; the executed evidence for the integrity entries is in the two walkthroughs.

Bundled Tama hook release failed its integrity check

Raised by install_hook_release.py before any write, whenever the release tree no longer digests to its recorded releaseId (concepts/seal). You meet it during a runtime install, an emergency disable (which installs session controllers), or a re-enable. The message names no file on purpose — it is a gate, not a report.

First command:

python3 Scripts/report_hook_release_integrity.py <release-root>

It prints the sealed and actual digests and two attribution lists: files the digest covers but the installer never installs (build residue such as Python bytecode — drift, but innocent), and files written after sealedAt (the suspects). A mismatch with no newer file is a permission change or a deletion — the digest covers mode bits (walkthrough-verify-release). Never repair a release tree in place: reinstall the same verified app artifact (operations).

Installed Tama hook release failed its integrity check

The second, identically worded gate: after the content-addressed copy to hooks-runtime/releases/<id>, that tree must digest to <id>. The installer already deleted and recopied a stale pre-existing tree before checking, so meeting this sentence means the fresh copy failed — a filesystem-level problem (full disk, interference mid-copy), not stale state.

First command:

python3 Scripts/verify_installed_releases.py

It digests every installed tree against its directory name, marks current, and answers which of the two identically worded failures an emergency enable would hit (second gate: intact / second gate: DRIFTED -- install would refuse). Executed with both answers in walkthrough-runtime-status.

Installed and loaded releases disagree

Not an error string — a Posture reading: Installed release and Loaded release differ, or the Session screen warns The runtime is serving a stale registry. A live session keeps executing the release it loaded at start; installing a new one does not restart anybody (concepts/posture).

First command:

tama-cli sessions

A lagging session shows a loaded count against a different registered count, or an old release id in --json. The repair is the session-scoped Enable all hooks, which binds an override to the installed release and checksum and schedules one runtime reload after the active turn settles (concepts/session-enable). The Session screen shows the pending state until the transition completes; rejection, timeout (The agent runtime did not acknowledge the session-control request before the deadline.), or session exit (The agent session ended before the session-control request completed.) is a reported failure, never assumed success.

Tama found only legacy v1 session records. Reinstall the verified bundled runtime, then stop or resume the affected agent session to publish v2 state.

From SessionControlClient when discovery finds no live v2 record but a v1 record exists. v1 records cannot satisfy the v2 agentId contract and are deliberately not migrated (operations). Do what the sentence says, in that order — the reinstall updates the supervisor, the stop/resume republishes state.

Unknown hook id '<id>'; the installed registry declares <N> hook ids, and the enforcement selection was not changed.

From tama enforcement only. The requested id is absent from the installed registry's unique agent-hook and Git-hook ids, so Tama refused the entire selection before writing state. The existing machine selection still applies.

First command:

tama list --json

Use the registry's exact ids, then retry the complete intended selection.

Tama could not read the machine enforcement selection: <core error>. Falling back to all hooks.

From tama enforcement status. The state file was readable neither as a valid ai.wisent.tama.hook-enforcement.v1 document nor as its required shape. Dispatchers choose the safe all-hooks fallback; the status command reports that effective state and exits 1 rather than hiding the damaged record.

tama enforcement status --json

Inspect readError before replacing the operator-owned file through tama enforcement all or a corrected only command.

enforcement: <OS/core error>

From a failed tama enforcement only or tama enforcement all write. The registry or atomic state transition failed, and no success is claimed.

Read the effective retained selection before retrying the operator mutation.

At least one hook must remain selected. Choose Select all hooks, or add another hook first.

From the Hooks inspector when the selected row is the sole member of only mode. An empty only selection is invalid; the desktop leaves the machine state unchanged and offers the two valid directions named in the sentence.

The generated launcher refuses (exit 66)

~/.local/bin/tama-agent fails closed before starting a session: Tama Node.js runtime preflight is missing: <path>, Tama requires its validated Node.js executable: <path>, Tama session supervisor is missing: <path>, or Tama requires Python 3 for the universal session runtime. The first two mean the installed runtime under hooks-runtime/current moved or a pinned Node was removed — reinstall the runtime rather than editing the launcher; the pinning contract is in hook-releases.

BLOCKED: repository copies are forbidden. 'git worktree add' makes a second checkout; work in the existing checkout instead. Remove existing worktrees with 'tama worktrees remove --root <PATH> --apply'.

From the block-repository-copies hook (tama-block-repository-copies), on a blocking pre_tool_use:bash binding, when the command you were about to run is git worktree add. It means the tool call was refused before git ran: no new checkout exists, and the repository you are already in is unchanged.

The ban exists because a second checkout is a second, divergent state of the same repository. Work done in it is invisible in the checkout you review, its build artifacts are counted twice, and nobody prunes it: on this machine the boot volume has 12.4 GiB free of 1.8 TB, while one project tree holds 519 GB and one agent scratch root (~/.stado/work) holds 1568 entries and 178 GB. There is no size at which a second checkout becomes correct, so the hook refuses the creation rather than reporting the growth.

First command:

tama worktrees list --root <PATH>

That is read-only. It answers whether worktrees already exist under the root you name, and the second half of the sentence — tama worktrees remove --root <PATH> --apply — is how you remove the ones it found (cli/worktrees/remove). Then do what the sentence says: make the change in the existing checkout, on a branch, in place.

BLOCKED: cloning a local repository makes a copy of it. Work in the existing checkout at <source> instead.

From the same hook, when the refused command is a git clone whose source is a local path rather than a remote URL. <source> is that local path — the checkout you already have, which the hook names so you do not have to look for it. Cloning a remote is untouched; this is only about copying a repository that is already on the disk.

The ban exists because a local clone is the same divergence as a worktree without git even knowing the two are related: the copy has its own .git directory, so no repository owns it, no git worktree list reports it, and tama worktrees remove cannot remove it. Since 2026-09-09 a copy that already exists is not a directory you have to find by hand either: tama copies walks the tree for it and refuses to delete one that carries uncommitted changes, commits absent from every remote, or no origin to compare against.

First command:

tama copies list --root <PATH>

Run it on the root holding <source> to see the copies that already exist there (cli/copies/list), then work in <source> itself.

BLOCKED: recursively copying a git repository makes a copy of it. Work in the existing checkout instead.

From the same hook, when the refused command is a recursive copy (cp -r, or an equivalent recursive copy) whose source is a git repository. It means the copy never started; nothing was written to the destination.

The ban exists because the result is a directory tree containing a .git directory that git has no record of and no repository owns. It also copies whatever the working tree happened to contain, including untracked and ignored build output — the reason the four largest sub-trees of one project directory on this machine are 72 GB, 68 GB, 50 GB and 47 GB. What already exists is inventoried and removed by tama copies, under the refusals on its remove page.

First command:

tama copies list --root <PATH>

It confirms which checkouts under that root are copies of something else (cli/copies). If you wanted a copy for a throwaway experiment, make it a branch in the existing checkout instead; if you wanted an archive, produce one file with git archive rather than a second repository.

BLOCKED: cannot tell whether <source> is a git repository, because the path is not literal. Pass the real path so the copy can be checked, or work in the existing checkout instead.

From the same hook, on a recursive copy whose source is not a literal path — the token carries a $ or a backtick, as in cp -r "$REPO" dest. <source> is that operand exactly as you wrote it, unexpanded, because that is all the hook was handed; nothing was copied, the refusal lands before the copy starts.

The check exists because the hook reads the command text, not the shell's expansion of it, while answering "is this source a checkout?" means looking at the source on disk. Proven live on 2026-09-09, in a session with this hook loaded and enabled: cp -r "$REPO" dest offered the literal $REPO, which stats as nothing, so the copy check found no .git and the copy went through — while the same command written with a literal path was refused. An agent putting paths into variables is ordinary, so failing open left the ban decorative.

First command:

tama worktrees list --root <PATH>

Passing the real literal path is the way through: the copy is then checked and judged on what is actually there. That is deliberate — the guard cannot prove that a source it cannot examine is not a checkout, so it refuses rather than guessing. If the literal path is a checkout, the other three sentences apply: work in it, in place.

tama worktrees does not know the worktree <path>; --except takes the path of a worktree this pass would otherwise remove.

From tama worktrees remove, exit 2, when a value you passed to --except matches no worktree the pass would otherwise consider. <path> is your value. It means nothing was removed and nothing was previewed: the usage error ends the pass before any selection is acted on.

The check exists because --except is how you keep one worktree while removing the rest, so an unrecognised path must not be ignored — an ignored typo would silently remove the one worktree you named to protect. Comparison is canonicalised, the same way a main worktree path is compared, so a relative path or a symlinked parent still matches; a path under a root you did not name does not, because the pass would never have considered it.

First command:

tama worktrees list --root <PATH>

That is read-only. It prints the exact paths of the linked worktrees this pass can see under the root you name; copy the one you meant into --except and run the removal again (cli/worktrees/remove).
