Desktop application

The SwiftUI app is the canonical human interface: one window, one sidebar of destinations grouped by the decision the operator came to make, one screen at a time. Authorization removes destinations instead of rewriting them — a signed-out or under-privileged operator sees fewer rows, never dead ones.

Authorization tiers

  • No credential. Welcome, sign-in guidance, and the explicit read-only inspector: the bundled catalog, its validation, and the declared install plan. No session monitoring starts and nothing is mutated.
  • Authenticated with an accepted role. A current owner, admin, or member role in the selected Wisent organization constructs the mutation-capable model; unknown or absent roles are denied. Explicit confirmation and macOS approval still gate each mutation.

There is no separate setup gate: navigation is available during setup, and guided first use runs alongside as a signed journey that records tama.hasCompletedSetup only against visible evidence (desktop/setup). Setup is considered complete only while the evidence still holds: valid bundled catalog, installed runtime, hooks not globally disabled, privileged backend Enabled, and at least one live session whose installed and loaded release identities match, with equal nonzero hook counts, under kernel-gated system policy.

Posture is the headline screen: the desktop product version and source revision, the hook release the build carries, the release the installed runtime records, and the release each live runtime loaded — plus the most recent blocking decision across sessions with its hook id and reason. The destructive Disable all hooks action lives here behind a confirmation that states exactly what stops working (enforcement-control).

Session polls live session records once per second while authorized. It shows each session's runtime status, capability and grants, and every recent semantic decision. Its only mutations are Enable a hook in one live session and Enable every registered hook and reload that session; the screen itself states that it can never disable a hook or issue, extend, or revoke a capability.

Violations scans the repository chosen in the sidebar's Repository in view — an existing local Git checkout owned by the current user; anything else is refused before the scanner runs. Scan is read-only and stoppable; Repair is a separate confirmed action that lists what a headless agent would edit and rescans afterwards (onboarding).

Settings shows local enforcement (runtime installed/bypassed, the privileged backend status with Approval settings and Full Disk Access shortcuts) and the build identity, and owns the confirmed Deactivate everything teardown.

How the app reaches the sealed CLI

Reads and jobs that belong to the sealed CLI — coverage, install plan, MCP snippet, policy bundles, enforcement, hook warming, violation scan and cleanup, worktrees, copies, builds and justifications — each run one process: tama request <operation> --root <bundled release>, with the request body on stdin. It prints NDJSON on stdout and exits once it has answered, so no Tama process stays running between two operations and no port is opened. A bounded operation prints one response event carrying its status and document; a long-running job (violations/scan, violations/clean) prints log events with its own output and one result event carrying the exit status and document. A refusal is the product's own sentence in an {"error": "…"} envelope, surfaced verbatim. Cancelling a scan or cleanup, or quitting the app, ends that process and everything it started. The full contract is tama request; the full command surface is cli.

A process-launch refusal identifies the requested native operation and the selected executable path, alongside the launch failure. The same contextual failure reaches the screen and the existing failure-reporting path.

A bounded refusal keeps the backend's own sentence and also names the native operation, response status and document, process exit status, process standard error and both streamed channels. The screen and failure reporter receive the same labelled exchange; an error envelope does not discard earlier output.

A response received where a streamed job was requested, or a job result received where a bounded answer was requested, is a protocol mismatch. Its error retains the native operation and the completed exchange instead of discarding the unexpected document and process output.

When a violations scan or cleanup ends with a rejected job status, its consumer reports that failure before returning the same error to the screen. The report and screen retain the operation, terminal document, process exit and all observed output together. A scan that reports findings with its documented finding status remains a valid report, not a failed operation.

A cleanup request failure is submitted before its final rescan starts. If that scan also fails, its failure is reported independently and the screen keeps both causes. The failed rescan cannot prevent the cleanup report, and the screen does not resubmit errors already reported by the native transport. User cancellation remains separate from failure reporting.

The native-client refusal journey first persists an isolated no-model declaration, then submits an unknown operation through both bounded-answer and job consumers. It retains each backend refusal with its operation, response document and process exit, and checks that the saved declaration has not changed. It uses the real backend executable, not generated replies.

The violations screen and its client share the native command selection for scan, cleanup and the final rescan. Production keeps the bundled sealed release. An isolated qualification journey can supply an explicit real backend command through the same construction path, without changing the application's release root or substituting a backend. Authorization and failure reporting are unchanged. Reporting does not await delivery during normal screen operations. Diagnostic callers can await the reports already issued: each attempt is registered before reporting returns and settles when the intake answers or transport ends. Settlement is not acceptance; a refused or unreachable intake also settles. An intake-delivery journey must wait for the application's actual reports to settle, then inspect the real intake's persisted failure journal. It checks that each failed operation has exactly one accepted envelope and that its detail equals the value produced by WisentErrors' canonical detail builder from the complete screen diagnostic, including every observed output channel. The envelope's documented detail builder removes only surrounding whitespace; all interior diagnostic content must survive. Qualification uses the resolved SDK's builder, not a second normalization rule, and retains the raw screen diagnostic and persisted journal separately. A screen error or a separately posted closing marker does not establish either delivery or exact cardinality. Qualification records the reporter dependency actually resolved by the candidate, not only its current source checkout.

In Reviews → Review failure and alternatives, eligibility and the recorded failure's cause are separate facts. Unknown eligibility authorizes no local decision; an explicitly ineligible failure requires its original authority. An eligible question with no declared decision options cannot receive a local attestation. If no readable latest failure is available, the screen says that eligibility has not been established rather than claiming the operation needs original authority. Latest-failure, history and local-statement read errors remain separately visible. These explanations do not change which actions are enabled, and a local statement is not an independent model review.

The maintained streamed-job journeys require a completed real scan to exit normally with its reported status. A separate signal journey starts the actual request process and sends SIGKILL at its observed launch, without task cancellation or a replacement executable. It retains the signal delivery, Foundation termination reason, status, complete exchange and process-absence probe after settlement. This checks termination-reason propagation, not a terminal-result/signal-number collision or graphical interaction. These test definitions are not execution evidence: qualification requires a retained, source-bound run.

Before writing request input, the client enables Darwin's per-pipe SIGPIPE protection and reads the flag back. If protection cannot be verified, it reports both fcntl results and their observed errno values instead of writing to an unprotected pipe. A protection, write or close failure ends that request's process tree, while the native operation and underlying cause remain labelled alongside the process's other output. Completion waits for input delivery to settle, process exit and both output streams to close; an input failure cannot be hidden by an otherwise successful terminal event.

The client reads each output pipe through Foundation's throwing read API, with chunks sized from the host's memory page size. A read failure retains the native operation, stream and actual Foundation cause, stops the failed request and settles that stream; the other stream's output is still retained. Output-read failures refuse the exchange even if it contains a successful terminal event.

Output-read and event-protocol refusals carry a transport failure distinct from a screen's document-decoding failure. The transport reports the former once at tama.backend.output or tama.backend.protocol; screen models retain the same diagnostic without submitting it again. Consumer schema and formatting failures still reach the failure reporter where they surface. Process-exit disagreements likewise keep their tama.backend.exit origin rather than being reported a second time as a review-screen failure.

Cancellation waits for the owned request process to exit and for input delivery to settle. Cancellation cleanup cannot close the output readers until both handlers have been installed. An exit observed during reader setup remains pending until registration finishes, so setup never installs a handler on a handle already closed by cancellation. After exit and registration are observed, it closes the local output readers and records their settlement without waiting for inherited writers to reach EOF. Only then does it resume the caller as cancellation, not a backend launch failure. Output-reader cleanup runs outside the log callback, so cancellation from that callback cannot reenter its output-delivery lock. Input and output failures still retain their causes and drain the remaining streams; they are not reclassified as user cancellation.

Native job consumers receive a local lifecycle notification with stream process, chunk launched and the actual process identity after launch and before output readers are registered. This notification describes process launch, not backend output or readiness. A consumer may cancel from that notification; cleanup waits for reader registration and process exit. Consumers can also observe validated stdout and stderr log events before the job finishes. Log callbacks carry the observed process identity, stream and chunk and run in output order outside the request-state lock, so a consumer can cancel after receiving actual output without a timer. Neither a launch notification nor output is a success verdict: the terminal result, process exit and pipe failures still decide the final outcome. The CLI's underlying NDJSON event contract is unchanged.

A successful bounded answer is accepted only after its request process exits normally and successfully. A streamed job must also exit normally, with the status in its terminal result; a scan reporting findings with the matching failure exit remains a valid scan report. Termination by signal is refused even if the signal number equals the terminal status. The result is refused before the screen decodes or applies its document. The error names the operation, expected and observed statuses and actual Foundation termination reason, and retains the terminal document and every observed output channel. No-answer diagnostics retain that termination reason too. It is reported at tama.backend.exit, not as a JSON decoding failure.

If the request body cannot be encoded as JSON, the operation is refused before a backend process starts. Values JSON cannot represent, such as NaN or infinity, are refused by a validity check before Foundation's encoder is called; this avoids an Objective-C exception that Swift cannot catch. If encoding a valid object fails, the original Foundation cause is retained. Both refusals name the native operation on the screen and in the existing failure-reporting path. Neither replaces persisted backend state.

If a native response cannot be decoded into the screen's expected document, the error identifies the native operation and retains the decoder's context, including the missing field or mismatched type and its coding path, alongside the response document, process exit and observed output channels. Formatting failures retain that exchange too. Neither replaces the underlying cause with the operating system's generic localized sentence. Job failures retain the native operation, terminal result document, process exit status, process standard error and both streamed output channels, separately labelled. The presentation adds no character cutoff and does not discard one channel because another is nonempty. If the request process exits before answering, its own standard error is also retained in full. Those bytes are decoded together after the stream closes, so a UTF-8 character split between pipe reads is not replaced or lost. At stdout EOF, a final JSON event without a newline is handled before the stream closes; an invalid final fragment retains its decoder cause. If no answer arrives, the error identifies the native operation and process exit status and keeps unreadable stdout events, process standard error and streamed job output from both channels separately labelled. Unknown event types and log events with missing or unknown stream names are retained as protocol errors, not silently discarded or mislabelled as standard output. An answer requires an integer status and an explicit json document; a Boolean or fractional status is not an exit code, and an absent document is not an empty answer. The first terminal event remains the recorded answer: any later event is retained as a protocol error rather than replacing that answer or extending a finished job. Unreadable events refuse the native exchange even when another event carries a successful response or job result. The screen and failure reporter retain the operation, terminal document, exit status and all observed channels together. A malformed event or missing terminal event does not hide an earlier cause. These are diagnostics of the actual response, not evidence that the operation succeeded.

Privileged backend

Register privileged backend (in Settings) registers the ai.wisent.tama.system-policy daemon through ServiceManagement and activates the ai.wisent.tama.network-filter System Extension with a socket-filter configuration. Status is reported as macOS sees it — Enabled, Requires administrator approval, Network filter requires approval, Not registered, explicit partial-setup states, or a restart-required message — and approval-pending is never treated as success. Deactivation attempts filter removal, daemon unregistration, and extension deactivation independently and reports every failure together.
