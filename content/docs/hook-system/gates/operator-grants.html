Operator grants: deletion, host change and vault write

Three gates refuse an action by default and let it run only on the operator's own words: block-unauthorized-deletion, block-unauthorized-host-change and block-unauthorized-vault-write. Each decides without a model, without the network and without a lock another session can hold: it reads the tool payload, a few local files and, only when a grant could cover the call, the operator's messages in the session transcript.

block-unauthorized-deletion

A gate on bash, eval and edit calls that refuses a deletion outside a checkout's Git-ignored .build/ or target/ folder. A deletion is read from:

  • the operands of rm, unlink, rmdir, shred, srm and trash, every command of the line as the shell runs it (through sh -c and wrappers);
  • git rm (not --cached) and git clean (not -n), read in the folder -C names; a git clean naming no path deletes in its whole folder;
  • the starting points of a find with -delete or -exec rm;
  • the local destination of rsync --delete and the sources of rsync --remove-source-files;
  • a hashline section's REM and a patch's *** Delete File:;
  • in evaluated code, os.remove, os.unlink, os.rmdir, shutil.rmtree, fs.rm, fs.unlink and their kin with a written string path, and a shell line run as !rm ….

A path is judged where it really lies: its folder with links and .. resolved, then its own name. It needs no grant when it, or a folder above it, is named .build or target and git check-ignore -q answers that its checkout ignores that folder. A path that does not exist deletes nothing and passes. A glob is judged by the folder before its first expanded part. A relative path on a line that also runs cd or pushd is judged in every folder the line may run it in. Every tracked file, every test file among them, lies outside an ignored folder, so its deletion is always refused.

A target that cannot be read is refused like one outside: a path the shell computes (rm "$X"), a deleting method of an object (path.unlink()), operands xargs hands over, a cd -. Only a grant naming the exact command lets such a call run.

The refusal begins BLOCKED: unauthorized deletion: this call deletes <paths> outside a checkout's Git-ignored .build/ or target/ folder, or names what it deletes cannot be read: <cause>, and ends with how the operator's words become a grant.

block-unauthorized-host-change

A gate on bash calls that refuses a command changing what runs on a host:

  • stado product install, stado release local install;
  • stado service restart|ensure|deploy|bootout;
  • launchctl bootout|bootstrap|kickstart|load|unload|stop|kill|remove|enable|disable;
  • systemctl restart|stop|start|reload|try-restart|reload-or-restart|kill|enable|disable|mask;
  • kill, pkill and killall of any process that does not descend from the session's agent process (TAMA_SESSION_OWNER_PID), read from ps -A -o pid= -o ppid= and, for a selection by name, pgrep; a job (kill %1), signal 0 and a listing pass;
  • any of these handed to another host through stado host exec, where every signal counts.

The refusal begins BLOCKED: unauthorized host change: and names each change, for example `stado product install` changes what runs on the host or `kill`: process 4242 was not started by this session (it does not descend from agent process 911).

block-unauthorized-vault-write

A gate on bash, eval, ssh, edit, multiedit and notebook calls that refuses a change to a live secret store: a file tool writing a *.vault.json, *acquisition-scopes.conf, *-skarbiec-token or *skarbiec.audit.jsonl outside a temporary folder; a skarbiec subcommand that changes stored material (set, delete, token-mint, seal-directory and the rest), on the store its --vault, -f, --vault-file or SKARBIEC_VAULT_FILE names; and a stado credentials command that stores, deletes, moves, mints or grants (put, rm, migrate, item put|delete|restore|reclaim|rename|upgrade, item retag --tags, token mint|sync|register, scopes sync, grant add|consolidate|rebind|revoke|renew, vault sync, vault retire|move --apply, seed enrol). The commands are read on every route a call runs one by: a bash line, the remote line an ssh tool call runs on another host, and the shell lines an eval program hands a shell (bash -c '…' inside the code), so neither route carries a change the shell would be refused (journey tests/vault-write/routes.rs, target vault_write_routes). Reading a store is never gated. The refusal begins BLOCKED: unauthorized vault write:.

More gates on the operator's word

Three gates, declared and not selected, admit one exact call on a grant of the same registry:

  • block-osascript (--kind osascript) refuses a bash, eval, hub or REPL call that runs osascript, read from the words the call runs and through any shell handed a line: AppleScript drives the operator's applications outside every other gate, and driving one goes through the CUA route he grants. Text that only names the program passes. Journey tests/osascript/refusal.rs.
  • block-consent-switches (--kind consent-switch) refuses a call that sets a variable Tama reads as the operator's own consent or as turning its gates off — DEVICE_HOOK_EDIT_APPROVED, DEVICE_LEVEL_TESTS_APPROVED, DEVICE_SUBAGENT_SPAWN_APPROVED, DEVICE_LEVEL_AUDITS_APPROVED, LOCAL_MODEL_TRAINING_APPROVED, TAMA_CLEAN_DISABLED, AGENT_STRUCTURED_CAPABILITY, TAMA_DISABLED_HOOKS, TAMA_ONLY_HOOK_ID — as a command prefix, an env operand, through export, declare, typeset, setenv or launchctl, or named in an evaluated program. The variables stay the operator's, set in his own shell; an agent's consent is his word recorded as a session capability or a grant. Reading one (echo $NAME) passes. Journey tests/consent-switches/refusal.rs.
  • block-unowned-failures (--kind unowned-failure, its action the failed command line), a Stop gate, refuses ending a turn while a call of a Wisent product (a program named as a workspace repository or the product its .wisent-release.json declares) failed or never answered since the operator's newest message, has not succeeded since, and no open defect in Oko's snapshot binds it. The way out is the repair, or oko defects record … --blocks and tama task scope set --defect. The hook runner keeps such a failure after the session changes a file (marked changed, and no longer refused as a repeat), so a write no longer forgets it. Journey tests/unowned-failures/stop.rs.

The grant

All three read ~/.shared-hooks/operator_action_grants.json (schema ai.wisent.tama.operator-action-grant.v1; TAMA_ACTION_GRANTS names another file), written by tama justify record --kind deletion|host-change|vault-write. A grant counts for a call only when all of these hold:

  • it names the gate and the session the call runs in;
  • its subject is a word of its quote and of every action it lists;
  • its actions hold the call's exact command, or every path the gate found in it;
  • its quote stands word for word in an operator message: a role: user record the operator wrote (attribution user) in the session's own transcript when the session is the operator's, else in the transcript its parentSession chain ends at. A subagent's own user messages are its supervisor's words and never count; its supervisor's operator does. The OMP adapter names each session's transcript in the payload as transcript_path; without it the transcript is found by the session id in its file name or its header.
tama justify record --kind deletion --session <this session id> \
  --quote 'usun ~/old-notes/scratch.txt' --subject scratch \
  --action /Users/me/old-notes/scratch.txt

Where it comes from

Source: rust/crates/tama-hook-tools/src/ports/block_unauthorized_deletion/, block_unauthorized_host_change/, block_unauthorized_vault_write/ and the shared operator_grant/; declarations under hook-declarations/. Agents deleted the operator's test approvals and tracked test files, installed an uncommitted Stado over running ones and restarted services, and wrote a live vault, with nothing to stop them; these gates are mechanical so that cannot happen without his word.
