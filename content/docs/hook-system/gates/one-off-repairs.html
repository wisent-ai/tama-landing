One-off repairs: block-one-off-repairs

A gate on pre_tool_use:bash (tama-block-one-off-repairs) that refuses three repairs made by hand against live machine state and names, in each refusal, the product command that owns the outcome. Every refusal starts BLOCKED: one-off repair by hand., goes to stderr, and exits 2 before the command runs; a command the gate lets through prints nothing.

Why it exists

On 2026-09-19 Oko's one-off repair detector (oko-cli transcripts one-offs) read the week's native harness files: 243 commands in 21 sessions changed live state by hand instead of through a product path. Three shapes had no gate at all — 12 service cycles, 26 grants minted from the shell (the one on 2026-09-18 written to the replica the vault owner overwrote within the hour) and 18 binary copies, nine of them cp .build/debug/oko-cli ~/.stado/bin/oko-cli. Each fixed one machine once and was gone at the next sync, image refresh or build. The operator's answer to the fix plan was "to napraw to".

What is refused, and the route each refusal names

Refused commandThe route the refusal names
launchctl kickstart|bootout|bootstrap|unload|load|stop|start|kill|disable|enable|remove, systemctl restart|stop|start|reload|kill|try-restart, kill <pid>, pkill, killall stado service restart <NAME>, stado service refresh-image <LABEL> --if-needed; a unit that must change is redeclared with stado service deploy|update.
skarbiec grant ensure|issue|add|widen|replace|revoke|rotate, skarbiec token-mint|token-revoke|reclaim — a vault written past Stado, so nothing records the grant and the next replica sync removes it stado release catalog declare-publisher <PRODUCT> --owner <VAULT HOST> --client <HOST> for a release publisher, stado service grant-sync for a service, stado credentials grant item-read for one read on the owner, stado credentials token mint for a bearer; each records against the owner's vault and each passes this gate. Oko's detector still lists a hand-typed stado credentials token mint as credential-by-hand for the judge; it is not refused, because it is the product's own route.
cp, install, mv or ln -s whose last argument is under ~/.local/bin, ~/.stado/bin, ~/.oko/bin, ~/.cargo/bin, /usr/local/bin or /opt/homebrew/bin (with ~, $HOME and /Users/<name> read as the same home) oko-cli install for Oko, stado product update <PRODUCT> --surface cli for a catalogued product, stado release install-local for a delivered release, stado host reconcile --apply for a host behind its declaration.
mv, cp, install or ln landing under a hook root, and rm, chmod, truncate or chown naming a path under one: ~/.shared-hooks, the installed Tama/hooks-runtime release, ~/.claude/hooks, ~/.config/tama/hooks. On 2026-07-31 a session renamed ~/.shared-hooks/block_browser_usage.sh to .paused, ran what that gate forbids and renamed it back; the write gate reads write and edit payloads, not a shell rename, so nothing refused it tama enforcement only <hook-id>… and tama enforcement status decide what this machine runs; a hook's source is changed with tama adaptive repair <hook-id> --patch-file <path> and DEVICE_HOOK_EDIT_APPROVED=1 tama adaptive apply <proposal-dir>; the installed release is rebuilt with DEVICE_HOOK_EDIT_APPROVED=1 tama hooks release.
psql, sqlite3, mysql, mariadb, duckdb or clickhouse-client whose quoted statement begins with insert, update, delete, drop, alter, truncate, upsert, grant, revoke or create. The statement is read from the original command — quoted text is blanked everywhere else, and a statement is exactly a quoted argument — and only after the program itself parses as a database client, so a sentence naming psql still runs nothing The command that owns those rows: oko-cli transcripts reindex and oko-cli transcripts tasks … for Oko's catalogue, a service's own CLI for its store. A change of shape belongs in a migration that ships with the product and runs on every host, not in one shell.
sleep, with any interval: time passed by hand in place of an outcome observed. A session on 2026-09-21 ran sleep 420 before reading one rollout and sleep 240 before retrying a publication; either read could as easily have returned the state from before the wait The command that owns the outcome reports it: stado job watch <ID> --follow to a terminal state, stado release doctor <PRODUCT> --target <HOST> for one rollout verdict, stado release status <PRODUCT> for the register of attempts, stado space report <HOST> for a host's own reading. Where no such read exists, the missing read is the defect to build.
stado space reclaim: a sweep that frees one host this once. The same session ran it three times in one day and the host was back under its watermark after the next builds What a host reclaims on its own is declared: stado space cleaners <HOST> --declare <CLEANER> adds the stage, stado space watermark <HOST> sets the level the janitor measures against, stado space work-root <HOST> says where the fleet's work may accumulate. stado space report <HOST> reads without changing anything.
stado release submit: a release built from whatever the shell's working copy happens to hold, at the moment somebody typed it, so the next commit needs the same person again A recipe builds every new commit: stado builds add --name <RECIPE> --repo <URL> --branch main --command <BUILD> --artifact <PATH> --platform <PLATFORM>, stado builds enable <RECIPE> to start the control-plane poller, stado builds status <RECIPE> to read its per-platform jobs, stado builds run <RECIPE> to enqueue one now. Bytes a recipe already qualified are promoted with stado release promote, and a publication that stopped part-way is continued with stado release resume <ID>.

What passes

Reads of the same programs: launchctl list|print|blame, kill -0 <pid> and kill -l, skarbiec grant list|show|verify, any invocation carrying --help, a query or a schema read (sqlite3 ~/.oko/index.sqlite "SELECT COUNT(*) FROM sessions", sqlite3 … .schema), a copy out of an install or hook root (cp ~/.stado/bin/oko-cli .build/before, cp ~/.shared-hooks/registry.json rust/target/registry-before.json), a read of either (cat ~/.shared-hooks/registry.json, ls -la ~/.shared-hooks), and a copy between build directories. The command is read the way a shell reads it — cut at separators outside quotes, quoted text and here-document bodies blanked, env, sudo, nohup and timeout stepped over — so grep 'launchctl kickstart' notes.md and a commit message that mentions skarbiec grant ensure run nothing and are allowed, while cd ~ && timeout 60 skarbiec grant issue … is still a grant. The reads that replace a wait pass with everything else: stado job watch <ID> --follow, stado release status, stado space report <HOST>, stado builds run <RECIPE> and stado release resume <ID>.

Where the refusal comes from

Source: rust/crates/tama-hook-tools/src/ports/block_one_off_repairs/mod.rs; binary: src/bin/block/ownership/block_one_off_repairs.rs; the real-binary test that holds each command to its exit status and route: rust/crates/tama-hook-tools/tests/one_off_repair_guard.rs; the declaration the registration reads: hook-declarations/block-one-off-repairs.json. The detector that counts the same shapes after the fact, across every stored transcript, is Oko's transcripts one-offs (categories service-cycle, credential-by-hand, binary-copy, data-by-hand, and live-config-edit for a hook's own file); a refusal here is recorded there as refused by hook. Registration is two commands: DEVICE_HOOK_EDIT_APPROVED=1 tama hooks declare --file hook-declarations/block-one-off-repairs.json for the catalogue entry, the registry entry and the reseal, and DEVICE_HOOK_EDIT_APPROVED=1 tama hooks release for the binary and the installed release.
