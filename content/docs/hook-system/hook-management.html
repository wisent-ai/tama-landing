Hook management

Tama stores hook source and structured configuration, exposes the CLI and MCP catalogue, and carries the runtime paths that enforce approved policy. The repository is never runtime state: logs, transcripts, credentials, shell profiles, local settings, caches, and machine-specific state stay outside it.

Source of truth

  1. shared-hooks/registry.json declares hook ids, events, commands, blocking status, runtime placement, and provider adapters.
  2. shared-hooks/catalog-metadata.json carries durable category, lifecycle, purpose, rationale, and side-effect metadata.
  3. tama-core reads those structured sources for the Rust CLI, MCP server, desktop catalogue snapshot, and product checks.

Do not duplicate a hook description in a command or prose file. Update the structured catalogue, then inspect it through tama list --json, tama show <hook-id> --json, or the matching MCP tools.

One rule, one hook

A hook is the unit the machine selection can switch, so a script holding several unrelated rules cannot be half-enforced. pre_write_edit.sh held three: the file-line limit, the folder-file limit, and the new-file justification requirement, so an operator who wanted the two limits without the third had no way to say it. They are three hooks now — block-oversized-files, block-crowded-folders and require-new-file-justification — each with its own script, sharing the payload preamble in write_payload_env.sh, and each registered through register-hook.mjs so the catalogue and the seal stay consistent.

Write a new rule as its own hook. When an existing script grows a second rule an operator might want separately, move it out the same way: the code is moved, never deleted, and tama enforcement only decides what runs.

Each native hook evaluates only its own rule. The common Tama engine reads the registry and selects and executes the event's hooks. The former cross-hook policy sweeps have been removed: a repository-copy refusal is attributed to block-repository-copies, rather than appearing as a refusal from the background-execution or CUA hook that happened to run first.

Repository layout

  • shared-hooks/, codex-hooks/, and claude-hooks/ contain archived hook source and the shared registry.
  • repo-githooks/ contains project Git entrypoints.
  • rust/crates/tama-core/ is the catalogue and validation library.
  • rust/crates/tama-cli/ is the supported CLI implementation; rust/crates/tama-mcp-server/ exposes catalogue operations.
  • rust/crates/tama-adaptive/ owns the runner, symbolic policy, immutable telemetry, feedback bridge, and repair doctor.
  • adaptive/policy.json is the frozen symbolic tier and autonomy policy.

Catalogue commands

tama list
tama list --json
tama show block-git-hook-bypass
tama show block-git-hook-bypass --json
tama validate --json
tama install-plan --json

The install plan separates agent runtime adapters, editor coverage, the MCP server, user-global Git dispatchers, repository Git entrypoints, and operating-system policy. An installed surface proves only its declared scope; Tama does not infer native Kimi, arbitrary editor-save, or device-wide coverage.

Installation and repository cleanup

tama install writes the user-global pre-commit and pre-push dispatchers only. It preserves existing hooks and changes global Git configuration only when explicitly requested. It does not activate every agent, editor, MCP, or operating-system integration.

tama find-violations scans tracked and untracked-but-not-ignored repository files through the real pre-write policy without changing them. tama clean gives the structured report to a bounded model worker and rescans under the same hooks; generated lock and registry files stay outside that repair loop.

tama vocabulary-report --repo <path>... answers the other question about the same files: not which file breaks a rule, but which keyword lists exist and how many places write each one. find-violations reports one finding per file, which is what a gate needs and the wrong shape for a repair — the same six words in four files get fixed four times and drift apart again. The report groups every flagged run by its word set, prints each set with all of its sites, most-copied first, and reads the same keyword-provenance.json declarations the guard reads, so a declared vocabulary does not appear. It writes nothing; --json gives the same grouping with a site and copy count.

MCP tools

  • list_hooks lists structured catalogue entries.
  • show_hook returns one hook and its event bindings.
  • read_hook_source reads the archived source for one hook.
  • validate_hooks checks catalogue consistency.
  • find_violations returns the same structured repository report as the CLI.

Changing a hook

  1. Place source under the owning archive directory.
  2. Record the catalogue entry, then write the registry entry, in that order. tama-record-hook-metadata writes the catalog-metadata.json entry — category, purpose, rationale, and side effects: 
    tama-record-hook-metadata [--check] --category C --description D --why W --side-effects S [--status S] <catalog-metadata.json> <hook-id>
    --status defaults to active; the entry carries status, category, description, why and sideEffects in that order; a repeat run reports that the catalogue already records the id and writes nothing; --check writes nothing and exits non-zero when the entry is absent or differs, naming the field that differs; refusals exit 2. It never opens registry.json. Then shared-hooks/register-hook.mjs writes registry.json — identity, event, command, blocking mode, runtime placement — and reseals it. That order is not a preference: before it writes anything register-hook.mjs reads the catalogue and refuses a hook with no entry there, printing catalog-metadata.json has no entry for <id> and exiting 2. The registry catalogue takes its category, purpose, rationale, and side effects from the metadata entry, so those are written once.
  3. Exercise the real runtime path that claims enforcement. Synthetic payload replay, mocks, and dry-run-only evidence do not prove live blocking.
  4. Keep commits limited to hook source, structured catalogue/configuration, and applicable product checks. Exclude runtime state, credentials, logs, profiles, and caches.

Adding a hook with one command

The steps above are what the two tama hooks commands run, in that order, so a new or changed hook does not need a shell file written for the occasion. Describe the hook once, as data in the repository under hook-declarations/<id>.json:

{
  "id": "block-one-off-repairs",
  "category": "shell discipline",
  "description": "…", "why": "…", "sideEffects": "…",
  "command": "$HOME/.local/bin/tama-block-one-off-repairs",
  "events": [{ "event": "pre_tool_use:bash" }]
}

Then the repository half, which records the catalogue entry, writes each registry binding it does not already have, reconciles the sources and reseals:

DEVICE_HOOK_EDIT_APPROVED=1 tama hooks declare --file hook-declarations/<id>.json

And the machine half, which builds every native hook the registry names from origin/main — never from the working tree, because a shared checkout carries other sessions' uncommitted edits and a live gate is code that was reviewed and pushed — installs the binaries whose bytes changed, then stages, seals and installs the live release:

DEVICE_HOOK_EDIT_APPROVED=1 tama hooks release --enforce <hook-id>[,<hook-id>…]

--enforce adds those ids to this machine's selection and keeps the ones already chosen; without it the selection is left alone and the command says so. --dry-run prints the plan, needs no consent and changes nothing: the hooks it would build, and whether the selection would change. A repeat run installs only what differs. Both halves refuse without DEVICE_HOOK_EDIT_APPROVED=1 and the refusal prints the exact command to run, in the checkout, outside any agent session.

Why a gate decided what it decided

A verdict nobody can read is a verdict nobody can repair, and the way that used to be answered was a throwaway program that read the same transcript a second way — the shape of repair these rules forbid, and one the write gate refuses outright. So the reading belongs to the gate. Each hook binary takes the payload it is given on stdin and answers about it; with --explain it prints what it read and decides nothing:

echo '{"session_id":"<id>","last_assistant_message":"<text>"}' \
  | tama-block-unprompted-topics --explain

For block-unprompted-topics that is the transcript it found, how many records it read, how many terms the operator's own words and this turn's results ground, the most ungrounded paragraph the session already accepted, and every block of the message with its counts and the words that have no provenance. A hook that answers this way is also a hook whose cost is visible: the same guard rebuilt the whole session's vocabulary at every assistant message until 2026-09-20, which is quadratic, and at 17 MB it spent minutes deciding nothing at all. Its test now judges a long session in milliseconds, so the regression is a failing test rather than a gate everybody waits for.

A release also installs the two programs a machine runs beside its hooks, from the same build: tama-run-hook, the engine a provider dispatcher executes, and tama-cli itself. Until 2026-09-20 nothing installed the engine at all, so the copy in ~/.local/bin kept whatever build last happened to write it — on one machine six days behind the engine the sealed release was already running, which is how a fix can be live on one path and absent on the other.

Which checkout a tama hooks command reads is decided in this order: an explicit --root, then TAMA_ROOT, then the first directory at or above the working directory that holds shared-hooks/registry.json. The path compiled into the binary is the last resort, and it has to be: the installed CLI is built inside the release's export tree, which the release deletes when the build ends, so before 2026-09-20 every tama hooks run from the installed copy refused with names no hook binary of ours against a directory that no longer existed.

Both the plan and a finished release now print where the sealed runtime on this machine was built from, read from native-hook-binaries.json: the revision, and whether the checkout held uncommitted changes when it was staged. The hook binaries a release installs come from origin/main, but the sealed runtime is staged by a script that compiles the working tree, and this checkout is shared — on 2026-09-20 the live engine carried "dirty": true, so the gates enforcing policy contained code nobody had committed. The fact was recorded and never shown; now every release says it out loud.

Warming the hook binaries

A hook binary that has never been executed still owes macOS its first-run work: the system assesses the executable's signature before it runs, that assessment reaches Apple over the network, and XProtect scans the image. Measured on 2026-09-20, the first run of a freshly installed tama-block-delegating-own-work took 147 seconds and every run after it took under 5 milliseconds. At the time each binding carried a number of seconds and the engine killed the hook at it, so a cold cache refused a finished turn with block-delegating-own-work timed out after 10s — a refusal nobody wrote.

The engine no longer counts seconds. A hook is waited for and its own answer decides the event, because the number was a guess at how long an answer may take and the hook killed at it reported a failure it never had. Nothing in the registry carries a timeout, and no run is killed for being slow: a slow gate is found by what it costs, not replaced by a verdict it never gave. Waiting is not free, though — 147 seconds inside a live event is 147 seconds somebody sits through — so the first-run cost is paid deliberately, outside the event.

tama hooks release runs every binary the registry names once, right after installing, and prints what each one cost. Run the same step on its own when binaries arrived another way, or to see where this machine stands:

tama hooks warm
tama hooks warm --only <hook-id>[,<hook-id>…] --json

Each line carries the state, the measured milliseconds, the hook id and the path: warm ran and exited, missing is a registry entry with no binary at that path. The summary names the binary that cost the most, which is the one to look at. The command exits non-zero when a binary is missing, because a live event would have nothing to run. --json prints one document with the same rows plus warmed and unusable counts and the slowest hook with its slowestMs. An id the registry does not name is refused by name and exits 2.

The run is inert: each binary receives an empty JSON object on standard input, which every hook reads as "no input, decide nothing", and HOME points at a scratch directory inside the checkout's ignored build tree, so a hook that writes state writes it there. No consent variable is required, because nothing about the machine's policy changes.

Tama Desktop carries the same step: the Hooks screen shows a Hook binaries panel with a Warm hook binaries button, the count it warmed, and a row for every binary that was slow or could not run. Both surfaces call the same POST /v1/hooks/warm route on the local backend and read the same document.

Owner consent for a hook change

Hook source and structured configuration are protected at device level. Inside an agent session block-hook-config-edits-without-consent refuses any payload that would create or edit them, and the refusal names what lifts it: DEVICE_HOOK_EDIT_APPROVED=1, exported by the owner in their own shell, outside the session. Three places read that one variable — the hook itself, tama adaptive apply, and tama adaptive install — so a session capability, a renamed path, or a patch applied beside the guard is a bypass rather than a route, and this page is the route.

For a live hook the supported route is a validated proposal:

tama adaptive repair <hook-id> --patch-file <path>
DEVICE_HOOK_EDIT_APPROVED=1 tama adaptive apply <proposal-dir>

repair validates the supplied candidate and prints the proposal directory; apply writes the proposed file to the live path after copying the current one into the adaptive state directory's backup/. Validation is evidence-driven: a hook with no labeled corpus case inside a validated closed telemetry segment is refused as insufficient-evidence, so a guard the operator questioned by name which the feedback bridge never labeled yields no proposal to apply. In that state the archived source in this repository and the file at the live path are changed by the owner directly, with the same variable exported, because they are two separate files and installing one is not editing the other.

Either way the hook's own acceptance check is what decides, run against the exact path being trusted: a passing candidate says nothing about the installed copy. An agent stopped by this gate owes the operator the exact command block rather than a description of it, and jeden copy - puts that block on their clipboard.

What counts as running a writer

The guard reads a shell payload the way a shell does. A payload is cut into commands at ;, |, & and newline only where those characters are outside quotes, so a sentence that names a writer inside a quoted argument — an evidence message, a commit body, a report of a refusal — runs nothing and is allowed. A token with spaces in it is an argument, not a program or a path, for the same reason.

What still refuses: the writer as the command's program or script argument, including a quoted path (node 'shared-hooks/generate-configs.mjs' --apply); tama install, tama enforcement only|all and oko-cli hooks install|pull read from the program the command starts, with env, sudo, nohup and timeout stepped over; the same command inside an executor's argument (bash -lc "tama enforcement all"); and a command substitution, which is code even inside double quotes (echo "$(tama install)").

Reporting runs stay allowed and always did: tama enforcement status, generate-configs.mjs without --apply, seal-registry.mjs --check, oko-cli hooks install --preview. On 2026-09-16 the cut happened before the quotes were read, so a semicolon inside a quoted evidence message split the argument in half and the sentence arrived as command words: the guard refused an honest report of its own refusal. A rule nobody can satisfy by doing the right thing is a rule that gets worked around.

Repairing a recorded hook source

register-hook.mjs derives a hook's source from its command: it takes the executable, drops the tama- prefix, turns hyphens into underscores, and looks for that stem as a sibling script or as a flat rust/crates/tama-hook-tools/src/bin/<stem>.rs. A guard whose source sits in a nested directory — src/bin/block/repo/block_repository_copies.rs, for instance — matches none of those candidates, so the writer falls back to recording the hook's own command, the installed binary path, as its source. Registration still succeeds and says nothing about it.

The next seal is where it surfaces. seal_hook_release.py packages every source outside the managed hook directories and refuses the whole release with External hook source is missing for the first one it cannot open (scripts). Until the entry is repaired no hook release can be sealed at all, and sealing is the step that puts a fixed hook on a machine. block-repository-copies hit exactly this the moment it was registered.

Repair the entry, then reseal the registry:

tama-reconcile-registry-sources [--check] [--out PATH] <registry.json>
node shared-hooks/seal-registry.mjs

The reconciler recognises a source that names an installed hook binary, derives the stem the way the writer does — drop tama-, hyphens become underscores — and repairs the entry when exactly one tracked file is named <stem>.rs; no match or several is reported and nothing is written. A source that already resolves is left alone. --check writes nothing and exits non-zero on the first stale entry, which is what a repository gate runs. The reseal is required, not optional: the catalogue checksum covers the whole document, so a rewritten source leaves the registry unsealed until shared-hooks/seal-registry.mjs runs.

Security rules

Never commit settings, environment files, shell profiles, logs, transcripts, credentials, private keys, session cookies, or Keychain exports. Hook archives may contain forbidden patterns by design, so any bypass for the Tama source repository must be explicit and scoped.
