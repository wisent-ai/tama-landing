Enforcement control

Tama has three machine enforcement states, and their ownership is explicit. The normal baseline runs every registered hook. An operator can narrow that baseline to a durable machine-wide selection, or use the confirmed emergency switch to bypass it completely. A live session can only add hooks to the machine baseline; it can never remove one. There is no per-session disable (core-contracts).

The three machine states

StateOwner and directionHooks that run
All hooksOperator baseline; tama enforcement all restores the strongest machine policyEvery registered hook
Selected hooksOperator; tama enforcement only <hook-id>... narrows the machine baselineThe ids in hook-enforcement.json, plus ids enabled by the current session
Emergency bypassOperator; the confirmed emergency switch weakens policy to none at machine scopeOnly generation-bound ids explicitly enabled by the current session

The durable selection remains recorded during an emergency bypass, but it enforces nothing while that bypass is active. Re-enable removes the bypass and the selected machine policy takes effect again. Missing hook-enforcement.json means all hooks; malformed or unreadable state reports the failure and falls back to all, never none.

Session records

Supervised runtimes publish one file per live session under ~/Library/Application Support/Tama/session-control/ (directory mode 0700), schema ai.wisent.tama.session-control.v2. A record carries agentId, sessionId, a 64-hex controlKey, pid, cwd, livenessMode (process — the pid must be alive — or heartbeat — updatedAt within heartbeatTTLSeconds, clamped to 5–3600), globallyDisabled, disabledHookIds, enabledHookIds, the override's emergencyChangedAt generation binding, the session's capability (issuer, nonce, release and checksum binding, lifetime, expiry, remaining uses, and per-tool grants), runtime status (installedReleaseId, loadedReleaseId, catalogChecksum, registered/loaded hook counts, unknown hook ids, enforcementMode, machineEnabledHookIds, reloadRequired, reloadPending, registryLoadError), and semanticRuntime — the sequence of recent events with each decision, the blockedHookId, and the reason string. Tama only reads these records; invalid, legacy-v1, or stale ones are ignored.

Session-scoped enable

The desktop writes a private request file <controlKey>.<requestId>.request.json (mode 0600) into the same directory — operation set-hook with hookId and enabled: true, or enable-all — and polls for the matching <controlKey>.<requestId>.response.json for up to 10 seconds. The supervisor validates the envelope against the exact session identity tuple, applies accepted state atomically, and answers with the authoritative session record; rejection, malformed identity, session exit, or timeout is an actionable failure, never optimistic success.

Enablement semantics compose the machine state and the session state:

  • normally, every hook in the all-hooks baseline runs;
  • in machine selection mode, the selected ids run and enabledHookIds can add hooks for this session, but cannot remove a machine-selected hook;
  • during a global emergency disable, one-hook enable may add the id to enabledHookIds only when its preflight and persisted override are bound to the active emergency state's exact, nonempty changedAt. The machine selection is bypassed, and the session record publishes that binding as emergencyChangedAt.

The one-hook allowlist and generation binding are retained in the private override and OMP session history, so they survive a reload or resume of that same session while the emergency generation is unchanged. A fresh global disable changes changedAt and invalidates prior or legacy allowlists and capabilities. The supervisor clears them before publishing state; neither the desktop nor tama-cli sessions treats a stale id as enabled.

enable-all is different. Outside emergency disable it binds an override to the installed release and catalog checksum and awaits the shared runtime reload; concurrent identical requests coalesce. A failed state update restores the preceding override. While global emergency disable is active, enable-all is refused with global-emergency-disable-active; it cannot turn the emergency allowlist into every hook.

The Session screen and Hooks inspector use the same live facts: during emergency disable, per-hook Enabled means membership in the generation-validated enabledHookIds. Otherwise it means membership in the all-hooks or selected machine baseline, plus any session enable. A rejected mutation remains a visible failure rather than changing the displayed status optimistically.

Inside an OMP session, the bundled adapter exposes the same control plane as session tools: tama_hook_runtime_status, tama_set_session_hook, tama_enable_all_session_hooks, tama_request_session_capability, and tama_reload_hook_runtime. Session hook disablement is prohibited there too.

Common hook runtime and harness adapters

Tama owns registry loading, hook execution, enforcement selection and reload. Harness adapters translate their incoming events and outgoing decisions; they do not implement another copy of the hook rules. The native tama-run-hook library and binary share the same execution loop.

The one-event interface remains tama-run-hook <event> <agent-id>, with the payload on standard input. Claude receives the canonical decision and exit code 2 on a policy block. Codex receives its existing minimal block response and exit code 0; a passing Codex decision produces no stdout. Those are adapter differences, not different policy evaluations.

The installed run-hook.mjs entrypoint is a process transport to hooks-runtime/current/bin/tama-run-hook, not a second evaluator. It preserves stdin, stdout, stderr, exit status and signals. Failure to start the native engine, or a registry startup failure, exits 1 with TAMA_HOOK_INFRASTRUCTURE; it does not fall back to a JavaScript policy engine or report a passing policy decision.

Persistent runtime protocol

tama-run-hook --serve omp

This starts the common engine, not an OMP agent. It first emits a JSON ready frame containing its state, then accepts one JSON object per line on stdin and returns one JSON object per line on stdout. Frames must end with LF. Closing stdin ends the process.

{"id":"inspect","op":"status"}
{"id":"reload","op":"reload"}
{"id":"event","op":"dispatch","event":"pre_tool_use:read","payload":{"session_id":"example-session","tool_name":"read","tool_input":{"path":"example.txt"}}}

Responses carry the request id, ok, a result or error, and the observed state. Status requests report their data in state; their result is null. A successful reload returns {"reloaded":true,"changed":true}, or changed:false when the validated catalog already matches. The response is produced after the engine has adopted the candidate, never after inserting a prompt.

A client can send knownCatalogChecksum. When it differs from the loaded checksum, the response also includes the loaded catalog, including on a rejected replacement. Matching clients receive no duplicate catalog. Adapters can therefore update their display and permission bindings from the engine's observed snapshot instead of racing a second file read.

Every dispatch also checks the registry. A valid changed catalog is adopted automatically before its hooks execute, without restarting the engine or changing the event's session identity. The process starts each hook command afresh; script and executable code is not cached between invocations.

The persistent engine leaves the harness-owned session record unchanged. It reads current session permissions for each event and supplies a capability to hook commands only when its session control key, release and catalog checksum match the loaded policy. A stale capability does not authorize newly loaded hooks. One-event adapters still publish their own session records.

Rejected replacements and observed state

A registry read, JSON parsing, shape or declared-checksum failure leaves the preceding loaded generation intact. A dispatch encountering that failure returns ok:false and executes no hook; it does not quietly run the preceding policy instead. After a valid replacement is published, a later dispatch can adopt it without restarting the process.

Diagnostics name the failed registry path and operation, for example parsing hook registry <path>: EOF while parsing a value at line 2 column 0 or hook registry <path> checksum mismatch: expected <declared>, actual <computed>. State includes processId, generation, loadedReleaseId, catalogChecksum, registeredHookCount, reloadCount, lastReloadAtMs and lastReloadError. processId identifies the common engine process, not its caller's harness process. A registry without release metadata reports a null release identity, not a fabricated release.

OMP integration status

The omp-shared-hooks.js adapter forwards ordinary hook events and reload operations to a persistent tama-run-hook --serve omp process. The reload tool and slash command return after the native operation completes; they do not insert a prompt or ask OMP to restart. Runtime status includes the observed native core.processId, separate from the OMP session pid.

Installing this adapter does not replace JavaScript already loaded by an old OMP session. A session still using the legacy adapter needs the /tama_reload_hook_runtime command entered once through OMP's command handler after installation. That loads the new adapter without restarting OMP. Subsequent hook reload requests use the shared engine directly. Compare installed and loaded identities; installation alone does not prove this initial transition.

Claude/Codex and OMP now reach the same native execution loop. npm run test:provider-runtime exercises the actual Node entrypoint and native binary, checks the filesystem effects of a valid hook, and verifies that an invalid catalog or missing engine cannot execute that hook. Set TAMA_TEST_PROVIDER_ADAPTER and TAMA_TEST_NATIVE_BINARY to exercise installed artifacts instead of the repository copies.

The native core's real-process regression tests live under tama/rust/crates/tama-run-hook/tests/runtime_reload/. They execute changed filesystem hook commands, inspect their persisted effects, reject malformed and incorrectly sealed replacements, and retain stdin, stdout, stderr, source revision, binary checksum and exit status.

The OMP adapter is checked separately through the real OMP SDK session and its registered tool dispatcher, not through a substitute extension host:

npm ci
npm run test:omp-runtime

This repository command builds the native engine and executes tests/runtime_reload/omp_runtime.test.ts. It checks actual file changes after the reload tool returns, rejects a malformed replacement, recovers on the next valid catalog, and checks that neither the session nor the native process changes and that no reload prompt is inserted. It also invokes the real Bash tool against an isolated repository and verifies that the refusal names the repository-copy hook, not an unrelated carrier, and that no copy was created. It uses isolated local state and does not require model inference or a browser.

The test calls OMP's actual initializeExtensions mode initializer before invoking tools. Constructing an SDK session without that step leaves actions such as appendEntry unbound and produces Extension runtime not initialized. Action methods cannot be called during extension loading. That error is not suppressed in the adapter.

Reports under rust/target/omp-runtime-evidence/ retain source revision, adapter and native-binary checksums, tool calls and replies, hook decisions, runtime errors, the selected release manifest when present, and the actual result. TAMA_TEST_OMP_ADAPTER and TAMA_TEST_NATIVE_BINARY select installed artifacts for the same test; without them it uses the repository adapter and debug binary.

Completion enforcement

Prompt text and installed instructions describe expected conduct; they do not execute a Stop rule. Execution comes from the enabled registered hook commands dispatched by the runtime. block-stop-with-open-work deterministically reconstructs the latest successful tracker state and blocks any pending or in-progress item. check-open-items-with-model separately reviews the real user contract, bounded current-turn tool evidence, and proposed final response through Tama's existing objective reviewer. It blocks for even one executable unfinished item or unresolved task error, while accepting completed and read-only work, user-stopped or user-restricted work, and a genuinely external unavailable prerequisite.

The reviewer obtains its bearer and signing identity through Skarbiec items tama-objective-authority-model-router and agent:wisent-app, then calls Brama at the configured HTTPS endpoint (default https://brama.wisent.com/v1/chat/completions) with route -best, agent id wisent-app, temperature 0, max_tokens: 160, a 3-second connect timeout, and a 25-second total timeout. Missing transcript or credentials, client/transport/HTTP failure, or an invalid reviewer response prints TAMA_HOOK_INFRASTRUCTURE: check-open-items-with-model: <reason> and exits 70; unavailable review is never reported as successful completion.

Both model hooks invoke stado secrets get <item> --field <field> with an explicit STADO_CREDENTIALS_ADMIN_URL, STADO_CREDENTIALS_ADMIN_CONSUMER, and STADO_CREDENTIALS_ADMIN_TOKEN_FILE binding. The consumer is tama-objective-authority-model-router-client, with its own ~/.stado/tama-objective-authority-model-router-client-skarbiec-token; it does not inherit the operator's credential-store identity. The URL comes from TAMA_OBJECTIVE_AUTHORITY_SKARBIEC_URL, defaulting to http://127.0.0.1:8787. The workload WC_SKARBIEC_* variables do not select the credential CLI's administration binding.

An activation failure records the process outcome before its captured diagnostic: could not start command, timed out after <N>ms, signal termination, or the exit code. A failed credential read names the exact item, field, endpoint and consumer, followed by Stado's own error; no field value is included. A timeout is not reported as an unexplained exit null.

Global emergency disable

The bundled emergency_disable_hooks script is the switch; the desktop runs it from Posture (confirmed as Disable every Tama hook on this machine) and re-runs it with TAMA_EMERGENCY_ACTION=enable for re-enable. Disable:

  1. pauses every supervised session through agent-session-supervisor.py control pause --require-all; an exit trap resumes them after success, failure, or interruption;
  2. reinstalls the session controllers (--session-control-only) so session visibility survives the bypass;
  3. backs up ~/.claude/settings.json and ~/.codex/hooks.json into emergency-backup/ and empties their hooks maps;
  4. moves entrypoints aside to <name>.tama-disabled: the OMP agent hooks directory and every Git hook source the installed registry declares;
  5. stops the editor watcher (~/.shared-hooks/editor-hooks.pid, then the com.wisent.editor-hooks.plist LaunchAgent);
  6. records everything once in emergency-backup/manifest.json and writes hook-emergency-state.json (schema ai.wisent.tama.hook-emergency-state.v1, disabled: true, changedAt).

Repeating disable is idempotent (Tama hooks are already disabled.). The desktop treats the machine as disabled only when both the manifest and the disabled state file exist, and after the script returns it re-reads that durable state — a switch that did not persist is reported as a failure, not claimed as success.

Re-enable

Enable refuses to run without the emergency manifest and a valid bundled release. It performs the full transactional installation of hook-releases with --emergency-manifest, which restores every moved entrypoint from the manifest, regenerates provider configs from the emergency backups, re-bootstraps the editor LaunchAgent, and only then removes the emergency state and manifest. A failed enable preserves the recovery evidence and does not claim the enabled state.

Settings → Deactivate is the composed teardown: it runs the same global disable and then unregisters the privileged daemon, System Extension, and network filter independently, so one failure does not skip later cleanup (desktop). Restoration evidence under ~/Library/Application Support/Tama is deliberately preserved (operations).
