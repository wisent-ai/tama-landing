Hook model

What exactly is a hook, and where is it declared? A hook is one approved policy command bound to one or more agent events, described by a registry that ships sealed inside every release. This page is the registry model; sealing and installation are in hook-releases, and the runtime controls are in enforcement-control.

The registry

shared-hooks/registry.json at the release root is the single declaration. Its top-level fields are version, generatedAt, generatedFrom, managedBy, releaseId, catalogChecksum, events (the per-event hook wiring the runtime executes), adapters (provider config paths), and catalog — the human-auditable record.

catalog carries:

  • agentHooks[] — the approved agent-facing hooks (below);
  • gitHooks[] — repository Git hooks: id, event, scope, hooksPath, source, plus the same category/description/why/side-effect record;
  • editorAdapters and ompAdapters — where editor and OMP integrations attach;
  • maintainedIn — the canonical structured registry source rewritten by the installer;
  • version, updatedAt, and notes — catalogue identity and operator context.

catalogChecksum is the SHA-256 of the registry JSON with the checksum field itself removed (sorted keys, canonical separators). It is recomputed by the installer after path rewriting, and every session record carries it, so the desktop can compare the bundle, the installed runtime, and the live session by checksum rather than by trust.

Machine enforcement state

The operational selection is separate from the sealed registry:

Missing state resolves to all. An unreadable, malformed, wrong-schema, or invalid-shape file reports an error and also resolves to all, so state failure never weakens policy.

One agent hook

Each agentHooks[] entry declares:

| Field | Meaning | |---|---| | id | Stable hook identity, e.g. block-inline-execution | | command | The exact command the runtime executes | | source | The hook's source file inside the release | | occurrences[] | Every event binding: event, blocking, statusMessage | | category | Policy area, e.g. git safety, credential safety, edit safety | | status | Lifecycle state (active) | | description, why, sideEffects | What it does, the justification for it, and what it touches | | aliases | Alternate ids the runtime accepts |

Events are names like pre_tool_use:bash, pre_tool_use:write, user_prompt_submit, or stop. A binding with blocking: true can refuse the action and statusMessage is what the agent surface shows while it runs; nothing in a binding bounds how long the hook may take, because the engine waits for its answer. Hooks read a JSON payload from stdin. A refusal is one decision document, {"decision":"block","reason":"…"}, printed on stdout (as the whole output or as its last line), with the same reason on stderr and a nonzero exit for surfaces that read the exit status. The engine reads only that document as a refusal. A hook that ends nonzero without it — a panic, a missing binary, a gate that printed TAMA_HOOK_INFRASTRUCTURE: because it could not decide — crashed; the engine logs hook <id> malfunctioned: … and the action goes on, because a crash is not a policy decision. Nothing reads the wording of a crash to tell it apart.

Quoted data and executable input

A Bash request is parsed as shell syntax. Literal arguments remain data when they contain apostrophes, escaped quotes, newlines, or examples of commands. Quoting an executable name does not make it data. Command substitutions still run inside double quotes, and recognized interpreter arguments are inspected through their complete argument boundaries rather than the first closing quote.

For example, printf '%s' 'ssh example.invalid' reports text; bash -c 'ssh example.invalid' requests a transport and still requires the normal authorization. Here-document handling keeps the consumer's program separate from expansions the shell performs before delivering that input. Native process arguments keep their quoting boundaries when projected as shell text.

Eval and recognized non-shell interpreter input use non-shell string rules: console.log("$(ssh example.invalid)") does not perform a Bash substitution. Existing embedded-interpreter recognition remains in force. Unclassified shell syntax remains visible to the guard rather than being silently discarded. This reader does not replace the transport's authorization, target, operation, or exact-command checks.

The native interface is tama hook block-unauthorized-ssh with a JSON request on stdin. The Session decision table and Posture show the installed runtime's decisions and reasons. Their installed and loaded release identities must match the release being qualified. An older last-blocking reason is history, not proof that a later request was refused. Source-suite evidence and live-runtime evidence are separate.

tama hook block-background-execution reads a Bash payload on stdin. Its time-limit check inspects leading NAME=value assignment names and option names before =, stopping at --. It does not interpret a quoted sentence or an assignment-shaped operand after the program name as an environment prefix. Thus tama justify record --justification 'checkpoint key=value; no timeout requested' and grep -- --timeout= notes.md do not request a time limit. This does not exempt either command from other hooks.

An actual option such as --timeout=$LIMIT remains refused, including inside bash -c. The reason names the operation: the option '<name>' sets a limit, the command runs '<name>', or the call asks to be stopped after <seconds> s, after BLOCKED: no limit on how long work runs and no guessed wait. Let the command run to its end, or read the state it would wait for. Detected:. Asynchronous requests, detaching programs and bare background operators remain separate refusals.

tests/background-execution/limits.rs exercises the real hook interface through cargo test -p tama-cli --test background_execution_limits. A source change alone does not change installed decisions. The Session decision table and Posture show the loaded release and observed refusal; qualification must use that release and retain the actual result.

tama hook pre-bash refuses git's patch mode (-p, --patch) and interactive mode (-i, --interactive) on any subcommand. Staging, unstaging, stashing or committing in patch mode, and adding, rebasing or cleaning interactively, ask for answers on the terminal; an agent's shell has nobody at it, so such a command waits for good and holds its session with it. The refusal opens BLOCKED: git's patch (-p, --patch) and interactive (-i, --interactive) modes ask for answers on the terminal and names the forms that ask nothing: git add <path> after writing the wanted change, git restore --staged <path>, git show <rev> and git diff <a> <b> for reading patches. tests/interactive-git/refusal.rs runs the built hook through cargo test -p tama-cli --test interactive_git_refusal with the refused forms and the passing ones.

The desktop's catalog snapshot

The app does not parse the registry directly. At build time, Scripts/app_build/export-catalog.mjs renders it into tama-catalog.json inside the app resources: version, generatedAt, hooks[], orphanSources[] (source files no hook references), and repoGitHooks[] (project, event, sourcePath). Each snapshot hook carries id, type, command, sourcePath, category, status, description, why, sideEffects, events[], and justificationRequirements[].

On every load the app validates the snapshot structurally: duplicate hook ids and hooks with no events are errors; a hook whose source path cannot be mapped from its command is a warning. The result — ok flag, errors, warnings, hook count, orphan-source count — is what Posture shows as Structural validation, with the standing warning that the bundled snapshot check does not run high-entropy or live runtime drift checks.

Justification-gated hooks

A hook of type requires_justification names one or more local justification registries instead of blocking outright. Each requirement declares kind, title, registryPath (a ~-relative JSON file), field (the justification text field), minimumWords, and optionally directUserQuoteField. The desktop's Justifications screen reads those registries and shows every entry with its word count, its expires_at expiry, and whether the target it justifies still exists — expired or missing-target entries are the ones to renew or remove.

Numbers and word classifiers

See numeric values and standard operations for declaration, manifest, source-citation and syntax-based operation rules.

Identities

block-identity-literals refuses an email address, a UUID, or an identifier that flattens an address when nothing issued it. A value passes when the harness issued it as the name of a stored transcript (a session id: OMP names each session's transcript under ~/.omp/agent/sessions after it), when a file the written path's own git checkout already tracks carries it (a product's published identifier — a journey version id in a seed, a row id — asked of git grep, which reads only the index), when an artifact outside any conversation carries it (a token cache, a cloud profile, the machine registry), when the operator used it in two or more stored sessions, or when identity_provenance.json records his verbatim quote declaring it. The transcript names and the checkout are asked first, so a write that names a session or an identifier the repository already holds does not wait on a read of every transcript on the machine; an untracked file beside the write counts for nothing. A word shaped like a flattened address that is part of an angle-bracket placeholder — a usage line's <gh-owner-name> argument — is read as the placeholder it is and never searched for. Any other value is refused naming it and saying which source was missing: the UUID <value> has no provenance -- no artifact carries it and no stored user message contains it. IDENTITY_TRANSCRIPT_ROOT, IDENTITY_ARTIFACT_ROOTS and IDENTITY_PROVENANCE_FILE move the three stores. The real tests are tests/identity-literals/session_ids.rs, tests/identity-literals/tracked_ids.rs and tests/identity-literals/placeholders.rs (cargo test -p tama-cli --test identity_literals_session_ids --test identity_literals_tracked_ids --test identity_literals_placeholders), the second against a real git checkout it creates.

When transcript content is required, hook subprocesses share per-file identity snapshots under Tama's state directory in identity-mentions. Each snapshot is bound to the source file's device, inode, byte length, modification time and metadata-change time, plus the identity extractor. Unchanged files are not reopened for their transcript bodies. A per-file OS lock gives a changed file one reader across sessions, and completed shards are atomically published so another hook can reuse them. There is no clock-based expiry. Removed, replaced, appended or permission-changed files do not retain their old provenance verdict. Only actual user-message identity tokens count; assistant messages are not independent operator evidence.

A read, parse or publication failure names its path and operation and refuses the write as unavailable provenance, rather than claiming the identity was invented. Cold or changed reads announce czekam; a contending hook announces its lock wait. These source mechanisms require actual cross-process qualification before an installed runtime is claimed to avoid repeated scans.

TAMA_TEST_SOURCE_REVISION=<full-candidate-revision> cargo test -p tama-cli --test identity_literals_mentions runs the actual hook in separate processes against isolated persisted transcripts. It retains the candidate and binary digest, commands and outcomes, covering a warm shared index, assistant exclusion, equal-size/equal-time replacement, deletion, malformed records and permission loss. Test source alone is not qualification.

block-keyword-literals refuses collections and regex alternations of two or more words used to classify input, and the same vocabulary written as a comparison: a chain of == (or ===, !=) against two or more quoted words on one line, and the arms of a matches! or match pattern joined with |. Moving the collection to JSON, YAML or TOML does not make it acceptable. No declaration allows a word classifier: keyword-provenance.json is retired, and writing it is itself refused. A refusal identifies the file, line, kind (list, alternation, pattern, comparison or data list) and words: src/k.rs:2: a pattern of 3 words decides something by keyword ("okay", "sure", "done"). The supported choices are a model judgment through Brama or the structure the input already carries, such as a field, status code or exit code.

Comments and documentation prose are not word classifiers. Protocol fields, paths and command options are not English trigger words. A collection passed as an ordinary call argument is that call's data: run(["transcripts", "tasks", "show"]) is not a classifier, and neither is a command line bound to a name before it runs, let args = ["build", "status", id, "--json"]: its collection also holds a computed value or an option, which a vocabulary of words never does. The same holds for the argument list of a process call in any language — Command::new("stado").args([…]), a test fixture's service.cli(&[…]), spawnSync("stado", […]), a Swift function that hands a command line back. A list of nothing but words bound to a name is still judged, a collection asked a question where it stands ([…].contains(x)) is reported whatever else it holds, and one comparison with one word (flag == "--json", state == "completed") is not a list. The real test is tests/keyword-literals/argument_vectors.rs (cargo test -p tama-cli --test keyword_literals_argument_vectors), on the built hook with the write payloads above, read from its decision document. In a release manifest, argv is a command vector and promotion.channels names release states. Neither list classifies input; other word arrays in that document are still judged. An edit of a JSON file sends only the changed lines, which do not parse as a document; an array written as the value of argv, or of channels in a release manifest, is exempt the same way. The rest of the fragment is judged as quoted text. YAML command mappings are read as syntax: argv names the executable and its arguments; args names arguments only when the same mapping carries a nonempty string program; each step of a Stado catalog recipe's after_install is one argv, because Stado refuses any step that is not an array of strings. Block and flow sequences, quoted keys, comments and either field order are supported. Only sequences of strings are command vectors; sibling word lists, nested classifier objects, an args list whose program belongs to a different mapping, and an after_install list holding any step that is not itself a sequence remain judged. A complete command mapping within a partial edit retains that meaning. Missing, malformed or ambiguous command context is not treated as proof of a command. Blanking a proven vector preserves line numbers, so any refusal still names the remaining collection's line. The native interface remains tama hook block-keyword-literals, with a write or edit payload on stdin. cargo test -p tama-cli --test keyword_literals_yaml_commands drives that real interface and retains source identity, binary digest, requests, exit statuses and output under Cargo's build directory. Desktop's Session and Posture show the installed hook's decisions; a source repair is not evidence that the installed release accepted an edit. A collection retained in a variable, iterated, or used to answer a membership question is judged; ["ready", "done"].contains(reply) classifies by words. Renaming the variable or moving the same decision into a data file does not change what it does.

A number spelled another way is still a number

The numeric guard also reads a number written so that it does not look like one, and judges it as the number it is: Number('401'), Number(true) and Number(false), and a constant whose value is built only from other upper-case constants and operators (const TWO = ONE + ONE). A name such as ZERO, IDX_ONE or RADIX_TEN bound to a bare number is a bare number under a name, and so is 'helloworld'.length standing for 10. Each is refused like the literal it hides.

What a refusal asks for depends on what the number does. A limit, cut, cap, page size, retry count, wait or timeout that the operator never asked for is removed together with the behaviour it drives: .limit(500) goes and the query answers every row; .slice(0, 160) goes and the text is kept whole; Math.min(limit, 200) becomes a refusal of a malformed limit; a default page size of 50 becomes "no limit unless the caller asks". Moving such a number into a constant, an environment variable or a different spelling is not a repair. A number that is not a choice stays, written as a literal: an HTTP status or exit code, a unit conversion such as 24 * 60 * 60 * 1000, an array index, the radix 10, the ISO date prefix slice(0, 10), a hash prefix, and a limit the vendor documents (Resend's 100 emails per list call, X's 160-character bio).

pre-write-edit also refuses code that opens a private local database file in a product (rusqlite::Connection::open, sqlite3.connect(, new Database( and the other call shapes in ports/private_stores/stores.json). Durable data belongs to the fleet database resolved through stado database; a private file keeps it where the rest of the fleet and the operator's other machines cannot see it. The refusal names that route. When the owning store really cannot serve the data, record why with tama justify record --kind file --file <path> --justification "<why stado database cannot serve it>" — the reason has to name stado database — and write again. Stado itself, the owner of durable data, is not judged; only code files are read. Existing lines in the target or changed donor files follow the committed-line lookup contract.

pre-write-edit refuses a failed read quietly replaced with a stand-in value (zero, minus one, an empty list, map or string, null, nil, undefined), by the code's shape: a catch body that assigns one, a JavaScript .catch arrow that returns one, a read call followed by || or ?? and one, and in Swift an optional try? read in parentheses followed by ?? and one. It also refuses a Swift statement that puts try? before await and uses nothing it returns: a refused read, write or send then looks exactly like success; an assignment to _ discards it the same way. A value that is used — assigned, returned, passed on or compared — is not judged, and waiting out a cancellable Task.sleep is allowed. The Swift checks read only .swift files and only their code: comments and string literals are blanked first, so a sentence quoting the shape is not a call. Wrap the call in do/catch and put the error where the screen shows it, or let it throw. Source: ports/pre_write_edit/sentinels.rs and ports/pre_write_edit/swift.rs.

Asking a model, when shape cannot decide

Some rules are not about shape: whether a claim is grounded, whether a closing report hands work back to the operator. The decider there is a model, and Brama answers it by default. ports::model_judgement is the one route: model_judgement::ask(prompt) sends the prompt through the product's own one-shot call, oko gateway send --prompt, which carries Oko's signed bearer to the gateway and prints its answer as JSON, or — on a machine without Brama — goes to the OpenAI-compatible service declared with oko model-service set, with its declared model. It returns Judgement::Answered(text) or Judgement::Unavailable(reason). A judgement nobody could obtain is never a denial: answer() is None for an unavailable one, so a guard that denies on a verdict lets the turn through and logs the service's own words — no judgement: the model service refused the call: … answered HTTP 503.

A judge Oko has recorded as not answering is not asked. Oko writes that record — judge-health.json beside its transcript index — from every verification pass and from oko tasks judge --probe, and the same probe lifts it. ask reads it first and returns Unavailable with Oko last saw the judge refuse at …: …; not asked again from a hook, because asking anyway costs Brama's whole retry wait inside the event, and a single refused proxy-call can take tens of seconds inside a stop gate. The engine kills no hook for being slow, and the OMP adapter sets no wait of its own; OMP refuses a tool call whose handler has not answered within its extensionHandlers.toolCallTimeoutMs setting, with Extension …/omp-shared-hooks.js timed out after …ms. A hook the harness stopped waiting for is ended by the next event that proves it has no caller, as the runtime page describes, not by a clock.

check-substantiation-with-model uses the model gateway. That is also the route for a judgment about prose that cannot be decided from the input's structure; an embedded word list is not a substitute.

Shared executable identities

Existing command readers share the compiled vocabulary under ports/shell_text/vocabulary/, including shell, interpreter, wrapper and source-extension identities. Other command families use their own existing product tables. ports::shell_text exposes these families to consumers instead of requiring a second copy in each guard.

The shell reader combines syntax-tree argument boundaries with the existing interpreter predicate. The predicate identifies which argument is a program and which interpreter family receives it; it does not turn an interpreter mentioned inside ordinary data into a new command.

These existing tables are not permission to add keyword classifiers. New decisions must follow structured input or a model judgment through Brama. Guard selection, grants and operator-owned authorization records are separate from source-text parsing and are not changed by a reader repair.

Catalogue access

The full catalogue remains structured in shared-hooks/registry.json. Use tama list --json, tama show <hook-id> --json, and tama validate --json for machine-readable inspection. The website explains the catalogue contract without generating a second Markdown registry.
