Hook model

What exactly is a hook, and where is it declared? A hook is one approved policy command bound to one or more agent events, described by a registry that ships sealed inside every release. This page is the registry model; sealing and installation are in hook-releases, and the runtime controls are in enforcement-control.

The registry

shared-hooks/registry.json at the release root is the single declaration. Its top-level fields are version, generatedAt, generatedFrom, managedBy, releaseId, catalogChecksum, events (the per-event hook wiring the runtime executes), adapters (provider config paths), and catalog — the human-auditable record.

catalog carries:

  • agentHooks[] — the approved agent-facing hooks (below);
  • gitHooks[] — repository Git hooks: id, event, scope, hooksPath, source, plus the same category/description/why/side-effect record;
  • editorAdapters and ompAdapters — where editor and OMP integrations attach;
  • maintainedIn — the canonical structured registry source rewritten by the installer;
  • version, updatedAt, and notes — catalogue identity and operator context.

catalogChecksum is the SHA-256 of the registry JSON with the checksum field itself removed (sorted keys, canonical separators). It is recomputed by the installer after path rewriting, and every session record carries it, so the desktop can compare the bundle, the installed runtime, and the live session by checksum rather than by trust.

Machine enforcement state

The operational selection is separate from the sealed registry:

PropertyContract
Path~/Library/Application Support/Tama/hook-enforcement.json
Schemaai.wisent.tama.hook-enforcement.v1; mode is all or only, enabled is the selected id array, changedAt is the transition time, and previous retains the preceding mode and ids
WriterThe operator-facing enforcement controls use the shared Rust enforcement writer, which replaces the file atomically with mode 0600
RetentionThe file persists across sessions, runtime reloads, installation, and emergency disable/re-enable; emergency state temporarily takes precedence without deleting the selection

all requires an empty enabled array; only requires at least one unique, nonempty, exact-trimmed id. Operator writers additionally refuse ids absent from the installed registry. Missing state resolves to all. An unreadable, malformed, wrong-schema, or invalid-shape file reports an error and also resolves to all, so state failure never weakens policy.

One agent hook

Each agentHooks[] entry declares:

| Field | Meaning | |---|---| | id | Stable hook identity, e.g. block-inline-execution | | command | The exact command the runtime executes | | source | The hook's source file inside the release | | occurrences[] | Every event binding: event, blocking, timeout, statusMessage | | category | Policy area, e.g. git safety, credential safety, edit safety | | status | Lifecycle state (active) | | description, why, sideEffects | What it does, the justification for it, and what it touches | | aliases | Alternate ids the runtime accepts |

Events are names like pre_tool_use:bash, pre_tool_use:write, user_prompt_submit, or stop. A binding with blocking: true can refuse the action; its timeout is the hook's execution budget in seconds and statusMessage is what the agent surface shows while it runs. Hooks read a JSON payload from stdin and fail closed: a blocking hook exits non-zero or returns a deny decision when its invariant is violated.

The desktop's catalog snapshot

The app does not parse the registry directly. At build time, Scripts/export-catalog.mjs renders it into tama-catalog.json inside the app resources: version, generatedAt, hooks[], orphanSources[] (source files no hook references), and repoGitHooks[] (project, event, sourcePath). Each snapshot hook carries id, type, command, sourcePath, category, status, description, why, sideEffects, events[], and justificationRequirements[].

On every load the app validates the snapshot structurally: duplicate hook ids and hooks with no events are errors; a hook whose source path cannot be mapped from its command is a warning. The result — ok flag, errors, warnings, hook count, orphan-source count — is what Posture shows as Structural validation, with the standing warning that the bundled snapshot check does not run high-entropy or live runtime drift checks.

Justification-gated hooks

A hook of type requires_justification names one or more local justification registries instead of blocking outright. Each requirement declares kind, title, registryPath (a ~-relative JSON file), field (the justification text field), minimumWords, and optionally directUserQuoteField. The desktop's Justifications screen reads those registries and shows every entry with its word count, its expires_at expiry, and whether the target it justifies still exists — expired or missing-target entries are the ones to renew or remove.

Provenance-gated literals: numbers and words

Two write-time guards refuse a literal in a code file unless the operator asked for it, in their own words, in a real transcript message. block-numeric-literals refuses a bare number; numbers live only in numeric-provenance.json, each as {"value": n, "user_said": "…"}. block-keyword-literals does the same for words: a run of three or more quoted words separated only by commas (["ok", "okej", "zrobione"], &["stop", "przestan", "zatrzymaj sie"], a Python list) or a regex alternation of three or more words ((likely|probably|might), "cannot be decrypted|spawn gpg|no route") is a classifier nobody asked for, and is refused with the file, the line, the words and the undeclared ones:

block-keyword-literals: BLOCKED: a keyword list is a classifier nobody asked for. Decide with a model judgement through Brama, or with data the operator declared; a word may live in code only under keyword-provenance.json with the operator's verbatim quote that asked for it.
  src/words.rs:1: a list of 3 words decides something by keyword ("ok", "okej", "zrobione"); undeclared: "ok", "okej", "zrobione"

A word is letters only, or several joined by single spaces; tool_name, /dev/null, --json and two-member runs are not judged, comments are blanked first, and only code files (the extensions the numeric guard scans) are read — prose and JSON are not. Words live only in keyword-provenance.json, looked up from the written file's directory upward, each entry exactly {"words": ["…"], "user_said": "…"}; writing that file is itself judged: the quote must be a verbatim role=user message in Oko's transcript index (oko-cli transcripts reindex --path <session> refreshes it) and must contain every word. The guard certifies that the operator said the words, not that the classifier is right; the route it points to is a model judgement through Brama or data the operator declared. Asked for on 2026-09-19 after the operator found such lists in Oko's task classifier, Tama's stop guards and Stado's quarantine classifier. Real-binary journey: rust/crates/tama-hook-tools/tests/keyword_literals_guard.rs.

Only a run of words the program keeps is judged. A classifier binds its words to a name, iterates them, or asks the collection a question on the spot; words handed to a call are that call's data. So run(["transcripts", "tasks", "show"]) and spawn(bin, args, { stdio: ['ignore', 'pipe', 'pipe'] }) pass — the guard follows the collection outwards through brackets, braces and property keys and stops at the ( that makes it an argument — while const MARKERS = { words: ["ok", "okej", "zrobione"] } and ["ok", "okej", "zrobione"].contains(reply) are refused. Before this rule the guard reported a finding for the argument list of every command a journey runs, which is how a guard teaches people to ignore it.

Where a guard's own program names live

Tama's guards judge command lines, so they have to know what a shell, an interpreter, a wrapper and a cloud tool are called. Those names are not written into the guards. They are declared as JSON the product compiles in: ports/shell_text/vocabulary/shells.json, interpreters.json, wrappers.json, source_extensions.json, ports/pre_bash/vocabulary/cloud_clis.json and ports/block_background_execution/detaching.json. Each file says in a why field what the family is. ports::shell_text turns a family into a regex branch — shell_alternation, javascript_alternation, scripting_alternation, eval_flag_alternation, awk_alternation, source_extension_alternation, wrapper_alternation — and a guard composes its pattern from those, so adding a shell is one edit to data rather than four edits to regexes.

Two consequences are visible in refusals. A guard that refuses one shell refuses all of them: ksh -c '…' and fish -c '…' earn the same inline-execution refusal as bash -c '…', and the background guard reads the inner command of any of them. A guard that looks past a wrapper looks past every declared wrapper, xargs included. Where the list was a guess at somebody else's vocabulary, the guard matches the shape instead: --provider <name> is recognised for any provider Stado offers, the Weles keeper entry point for any action Weles adds, and node --check for any JavaScript suffix.

Catalogue access

The full catalogue remains structured in shared-hooks/registry.json. Use tama list --json, tama show <hook-id> --json, and tama validate --json for machine-readable inspection. The website explains the catalogue contract without generating a second Markdown registry.
