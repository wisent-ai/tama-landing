Warming the hook binaries

A hook binary that has never been executed still owes macOS its first-run work: the system assesses the executable's signature before it runs, that assessment reaches Apple over the network, and XProtect scans the image. Measured on 2026-09-20, the first run of a freshly installed tama-block-delegating-own-work took 147 seconds and every run after it took under 5 milliseconds. At the time each binding carried a number of seconds and the engine killed the hook at it, so a cold cache refused a finished turn with block-delegating-own-work timed out after 10s — a refusal nobody wrote.

The engine no longer counts seconds. A hook is waited for and its own answer decides the event, because the number was a guess at how long an answer may take and the hook killed at it reported a failure it never had. Nothing in the registry carries a timeout, and no run is killed for being slow: a slow gate is found by what it costs, not replaced by a verdict it never gave. Waiting is not free, though — 147 seconds inside a live event is 147 seconds somebody sits through — so the first-run cost is paid deliberately, outside the event.

tama hooks release runs every binary the registry names once, right after installing, and prints what each one cost. Run the same step on its own when binaries arrived another way, or to see where this machine stands:

tama hooks warm
tama hooks warm --only <hook-id>[,<hook-id>…] --json

Each line carries the state, the measured milliseconds, the hook id and the path: warm ran and exited, missing is a registry entry with no binary at that path. The summary names the binary that cost the most, which is the one to look at. The command exits non-zero when a binary is missing, because a live event would have nothing to run. --json prints one document with the same rows plus warmed and unusable counts and the slowest hook with its slowestMs. An id the registry does not name is refused by name and exits 2.

The run is inert: each binary receives an empty JSON object on standard input, which every hook reads as "no input, decide nothing", and HOME points at a scratch directory inside the checkout's ignored build tree, so a hook that writes state writes it there. No consent variable is required, because nothing about the machine's policy changes.

Tama Desktop carries the same step: the Hooks screen shows a Hook binaries panel with a Warm hook binaries button, the count it warmed, and a row for every binary that was slow or could not run. Both surfaces run the same warm pass — the window through tama request hooks/warm — and read the same document.
