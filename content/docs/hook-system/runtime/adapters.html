Common hook runtime and harness adapters

Split out of enforcement control, which had grown past the three-hundred-line limit Tama's own guard enforces on every file. The enforcement states live there; what executes a hook, and how each harness talks to it, lives here.

What owns the execution loop

Tama owns registry loading, hook execution, enforcement selection and reload. Harness adapters translate their incoming events and outgoing decisions; they do not implement another copy of the hook rules. The native engine is a library inside the one tama program, which runs it as tama run-hook.

The one-event interface remains tama run-hook <event> <agent-id>, with the payload on standard input. Claude receives the canonical decision and exit code 2 on a policy block. Codex receives its existing minimal block response and exit code 0; a passing Codex decision produces no stdout. Those are adapter differences, not different policy evaluations.

The installed run-hook.mjs entrypoint is a process transport to hooks-runtime/current/bin/tama run-hook, not a second evaluator. It preserves stdin, stdout, stderr, exit status and signals. Failure to start the native engine, or a registry startup failure, exits 1 with TAMA_HOOK_INFRASTRUCTURE; it does not fall back to a JavaScript policy engine or report a passing policy decision.

Persistent runtime protocol

tama run-hook --serve omp

This starts the common engine, not an OMP agent. It first emits a JSON ready frame containing its state, then accepts one JSON object per line on stdin and returns one JSON object per line on stdout. Frames must end with LF. Closing stdin ends the process.

{"id":"inspect","op":"status"}
{"id":"reload","op":"reload"}
{"id":"event","op":"dispatch","event":"pre_tool_use:read","payload":{"session_id":"example-session","tool_name":"read","tool_input":{"path":"example.txt"}}}

Responses carry the request id, ok, a result or error, and the observed state. Status requests report their data in state; their result is null. A successful reload returns {"reloaded":true,"changed":true}, or changed:false when the validated catalog already matches. The response is produced after the engine has adopted the candidate, never after inserting a prompt.

Answers arrive as requests finish, not in the order they were sent, and a client matches each to its request by id. Each dispatch runs on its own thread against the generation loaded when it arrived, so a hook that never ends holds only its own request; status and reload are answered at once. The OMP adapter keeps every request in flight side by side and orders only reloads and shutdown.

Within one dispatch the hooks of a tool event run in registry order, one after another, and the first refusal ends the dispatch. The hooks of stop all run whatever the others answer, because an ending answer is refused for every reason at once, so the engine starts them side by side and waits for all of them. Checking an ending then takes as long as its slowest hook, not the sum of them all. Run one after another, their times added up past the handler budget OMP gives a session_stop handler; OMP then settled the turn as if no hook had refused, and the agent ended its answer with work still open. The refusal text and the results records still follow registry order, and every record carries the hook's own ms, so a slow stop hook is named by its record. tests/completion/side_by_side.rs in the Tama repository runs the built engine's stop on the installed registry and its real hooks, and fails when the dispatch lasted as long as its hooks' times added together.

Each hook runs in its own process group. A session ends its turn and submits a prompt one at a time: the harness sends the next stop or user_prompt_submit only after it stopped waiting for the one before. So when one of those hooks starts while the same hook of the same session (session_id in the payload) still runs for the previous event, the engine ends the earlier run's process group — the hook and what it started, such as a model request that is never answered — and writes tama: ended hook <id> (process group <pid>) still running for the previous <event> of session <id> on stderr; the ended run is reported as a malfunction, not as a refusal. No clock is involved.

A newer tool call does not end an older one, because a session runs tool calls side by side. The end of the turn does: the harness sends stop only after every tool call of the turn is over, and user_prompt_submit only once the turn before it ended. A pre_tool_use or post_tool_use hook of that session still running at that moment guards a call the harness has already refused at its own handler limit, so the engine ends its process group as well and writes tama: ended hook <id> (process group <pid>) still running for <tool event> of session <id>: the session's <event> arrived, so that tool call is over and nobody waits for its answer on stderr. Left running, every such hook would keep one unanswered model request open, and each further tool call would add another to a gateway that already does not answer. That tool call's dispatch starts none of its remaining hooks and answers ok:false with the turn of session <id> ended while <event> was still being checked, so that tool call is over and hook <id> and the ones after it were not started. A serving engine whose input closes ends every hook run it still holds the same way, with the core's caller closed its input, so nobody waits for its answer. A payload without a session id is never superseded or ended. tama hooks running lists every hook still running.

A client can send knownCatalogChecksum. When it differs from the loaded checksum, the response also includes the loaded catalog, including on a rejected replacement. Matching clients receive no duplicate catalog. Adapters can therefore update their display and permission bindings from the engine's observed snapshot instead of racing a second file read.

Every dispatch also checks the registry. A valid changed catalog is adopted automatically before its hooks execute, without restarting the engine or changing the event's session identity. The process starts each hook command afresh; script and executable code is not cached between invocations.

The persistent engine leaves the harness-owned session record unchanged. It reads current session permissions for each event and supplies a capability to hook commands only when its session control key, release and catalog checksum match the loaded policy. The OMP adapter rebinds the grant its session holds whenever it loads another release, so an install or reload keeps the operator's consent; a capability written for another generation outside that reload does not authorize newly loaded hooks. One-event adapters still publish their own session records.

Rejected replacements and observed state

A registry read, JSON parsing, shape or declared-checksum failure leaves the preceding loaded generation intact. A dispatch encountering that failure returns ok:false and executes no hook; it does not quietly run the preceding policy instead. After a valid replacement is published, a later dispatch can adopt it without restarting the process.

Diagnostics name the failed registry path and operation, for example parsing hook registry <path>: EOF while parsing a value at line 2 column 0 or hook registry <path> checksum mismatch: expected <declared>, actual <computed>. State includes processId, generation, loadedReleaseId, catalogChecksum, registeredHookCount, reloadCount, lastReloadAtMs and lastReloadError. processId identifies the common engine process, not its caller's harness process. A registry without release metadata reports a null release identity, not a fabricated release.

OMP integration status

The omp-shared-hooks.js adapter forwards ordinary hook events and reload operations to a persistent tama run-hook --serve omp process. The reload tool and slash command return after the native operation completes; they do not insert a prompt or ask OMP to restart. Runtime status includes the observed native core.processId, separate from the OMP session pid.

OMP imports an extension module once per process and has no way to import it again, so omp-shared-hooks.js is only a shell: it imports the adapter itself, from shared-hooks/omp/adapter.js, under that file's SHA-256 digest, and forwards every event, tool and command the adapter registers. tama_reload_hook_runtime, as a tool or as the slash command /tama_reload_hook_runtime, first compares the installed adapter's digest with the loaded one. When they differ it imports the installed adapter in place: the new module is imported first, then the old adapter's session_shutdown handlers run, the new adapter registers itself and its session_start handlers run with the reload's context. The reload then reports Loaded the installed OMP adapter <digest> in place of <digest> before the engine's own answer, so a gate added in a new Tama release (such as block-text-outside-tool-calls on before_provider_request) runs in an open session without restarting OMP. An adapter that fails to import or register is refused with Tama could not reload its OMP adapter: <reason>, and the adapter already loaded keeps running.

Two limits remain. The adapter's sibling modules (hook-exec.mjs, session-control.mjs and the rest) are imported by the adapter once per process, so a change to one of them needs OMP to start again; the reload's answer says so. And a session that started before this shell existed holds the old single-file adapter, which cannot reload itself: it needs OMP to start again once (/restart keeps the session).

Every model request is decided at once, never by waiting on the before_provider_request hooks: OMP waits for a handler only up to its own budget and then sends the request unchanged, so a slow read of Oko's ledger used to let prose through exactly when Oko was under load. The adapter answers each request from the newest answer block-text-outside-tool-calls gave in the session — a refusal requires the request to call a tool — and starts one fresh dispatch in the background (never two at once) whose answer decides the next request. Before the first answer in a session the request is forced, as a ledger that cannot be read already is. A request decided while work just closed is therefore forced once more, and the one after it is free.

The same handler gives every model request the contracts Jeden installed most recently. jeden contracts install --omp writes them between the lines <!-- jeden contracts: start --> and <!-- jeden contracts: end --> in ~/.omp/agent/APPEND_SYSTEM.md, and OMP appends that file to a session's system prompt once, when the session starts, so a contract changed later reached no running session. The adapter (shared-hooks/omp/installed-contract.mjs) reads the file's marked block on each request and puts it in place of the marked block the request carries, wherever that block sits in the payload; a request with no marked block, or a file without one, goes unchanged. A file that exists and cannot be read sends the request under the session's own copy and prints Tama cannot read the installed contracts <path>: <reason>; this model request keeps the contracts its session started with on stderr. jeden contracts status --omp names the sessions that started before the file was last written.

Checked in a real omp --mode rpc process loading the shell with --no-extensions --extension from a copy under the checkout's ignored build directory: /tama_reload_hook_runtime with the adapter unchanged loaded nothing new, after a change to the adapter it reported the new digest in place of the old, and with a syntax error in the adapter it refused and kept the loaded one.
