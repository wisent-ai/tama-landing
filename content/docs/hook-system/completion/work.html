Completion policy and work registers

Role preflight, actionable work and the distinction between a source repair and a qualified result.

Completion enforcement

block-supervisor-stop refuses completion for a session whose local Oko role is supervisor. It reads ~/.oko/session-roles.json inside the native runtime before starting any judge hook: no subprocess, database, network or model request. The refusal directs the supervisor to oko sessions agents, confirmation dialogs, stopped executors and their next open assignments. Only the operator clearing that role with oko sessions role clear SESSION releases this role guard. Other enabled completion guards still apply after it passes.

Malformed or unreadable roles and absent session identity refuse with the exact operation and cause; they are not interpreted as an unassigned session. An absent register means no role has ever been recorded, as in Oko's contract. Unknown record fields are ignored. Enable it with tama enforcement only EXISTING_HOOK_IDS block-supervisor-stop, preserving every id currently shown by tama enforcement status --json. The Desktop Hooks inspector and session refusal records expose the same hook and reason; Oko Desktop's Agent sessions Role menu manages the local role.

When the effective selection enables block-supervisor-stop, OMP reuses a stop assessment only while the local role document has the same content digest. An external role clear or assignment invalidates both an old refusal and an old pass, even if the assistant candidate and transcript identity are unchanged. An unreadable register cancels the retained assessment and refuses with its path and actual read cause. For an executor, the identity also includes the local defect register, blocker register and prepared task snapshot: file identity, size, modification/change timestamps and mode. An assigned defect or changed task reading therefore invalidates the retained decision without another tool call or a guessed expiry. These are local metadata reads, not scans of ledger contents. The native runtime remains the authority that interprets the role and work; metadata alone never grants completion.

The real tests/hooks-running/stop-review/journey.mjs journey includes roles.mjs: genuine Oko role set, clear and reassignment against an isolated home, persisted role checks, and actual native Tama dispatch behind the same assessment cache. Declare TAMA_TEST_OKO_BIN alongside the candidate Tama executable and source revision; the run retains both binary digests and the real command results. A directory substituted for the isolated role file checks causal read refusal and cancellation. An executor case creates a genuine isolated Oko defect after assessment and requires a fresh native decision naming that assignment despite an unchanged assistant candidate. This test source does not establish installed OMP lifecycle or Desktop qualification.

For an executor, the same local preflight selects an open assigned defect first, then open defects of products named by its recorded assignments. It reads Oko's atomic defect and blocker registers without running a process: OKO_DEFECT_REGISTER and OKO_BLOCKER_REGISTER, or ~/Library/Application Support/Oko/defects.json and blockers.json. The refusal names oko defects show ID and the recorded owner for coordination. A valid open blocker naming that exact defect, by full or short id at the beginning of its blocks field, holds only that item; a repository-wide publication wait does not hide the queue. Malformed or unreadable registers refuse with their actual path and cause.

Executor task settlement runs in the background before_provider_request dispatch, before the text gate, only when the local defect selection cannot already name actionable work. A known actionable defect keeps Stop refused without reading the remote task ledger or manufacturing an empty ready snapshot. Once no such defect remains, preparation reads Oko's authoritative session ledger, including relations, rather than Oko's private pre-settlement cache. The result is atomically retained under TAMA_SESSION_CONTROL_ROOT/executor-work (the normal session-control state directory when no override is set). Stop reads that local observation; it starts neither Oko nor a reviewer. After assigned and product defects, the refusal names the next own task through oko tasks show ID. An exact-item blocker holds that task only. Submitted tasks already awaiting review retain the existing completion reader's classification.

The OMP adapter supplies tama_work_generation, renewed on activation, input and tool completion. Missing, unfinished, failed or different-generation observations refuse; a late reader cannot overwrite a newer generation. A failed generation is not automatically retried. A new work boundary initiates a new reading. This is an observation of the ledger at that boundary, not a live subscription to other sessions' remote task mutations. Native callers must prepare the same generation with tama run-hook before_provider_request omp before tama run-hook stop omp. Both receive the session and generation in their JSON input. The Desktop session refusal record uses the same reason.

The real executor defect journey uses isolated Oko role, defect and blocker mutations and requires actual external-failure evidence plus the real blocker reviewer. With actionable defects it also removes access to the Oko executable, requires preparation to avoid task settlement, confirms no task snapshot was created and requires Stop to name the same persisted defect. Retained source is not a passing run or installed-harness qualification.

Every supported harness completion binding reaches the canonical stop event. OMP's blocking boundary is session_stop; agent_end and turn_end are notification-only, not additional cancellation APIs. This does not claim control over operator interruption, process exit, or OMP subagents, which do not emit session_stop. The real supervisor_stop_roles journey uses Oko role set/clear and the built runtime, checks persisted role changes, supervisor refusal, clearing, unknown metadata and unreadable state. Prompt text does not execute a Stop rule. Enabled hook commands do. block-stop-with-open-work reconstructs the successful tracker state and blocks pending or in-progress items. Once that plan is clear, including when every local item is marked blocked, executor roles use the same prepared generation and item selection described above. Other sessions read the authoritative Oko ledger for the native OMP session id. An absent local plan does not skip the applicable reading; an unavailable ledger refuses Stop with its actual error. For sessions without a recorded executor role, when the machine has no Oko CLI (neither TAMA_OKO_CLI nor oko on PATH is an executable), the session's own registers are the only task registers: Stop is refused on the tracker's pending or in-progress items and, once they are clear, on the task-scope declaration while it still names a task or a defect, with BLOCKED: this machine has no Oko CLI, and the session's own declaration still names open work: <entry> — "<the operator's words>" and the way out, tama task scope clear --session <ID>; a cleared declaration lets the next Stop through, and a declaration that cannot be read refuses as an unreadable ledger (cannot confirm completion …), never as an empty one. An installed Oko that cannot be read still refuses. The other gates that read Oko take the same alternative on such a machine: block-text-outside-tool-calls lets the final message through, block-one-off-repairs admits a build, compile or test because no register holds an item without a repair, and tama task scope set accepts the --task or --defect identifier the session names as the entry, with the repositories it names as the scope and nothing written back. require-task-scope then refuses with that one command instead of the Oko commands it names when Oko is installed. check-open-items-with-model uses the same ledger qualification when enabled. Neither guard asks a second model to reinterpret open tasks as permission to stop. block-text-outside-tool-calls runs before model requests and on Stop. The OMP adapter uses a completed gate answer from the current session and work generation and refreshes it in the background; a late answer from an older generation cannot authorize prose. The ledger read does not consume the harness's provider-handler budget. For supported OpenAI function-tool payloads, an open-work refusal sets tool_choice: "required"; this shape is also forced before the first answer. Anthropic requests and unsupported or absent tool shapes are not forced: they are sent unchanged with the limitation on stderr. Their Stop gate still checks completion, but it runs after text may already have streamed and cannot retract that text. Provider acceptance, prevention of streamed prose and refusal of completion are separate outcomes; none is established merely by a published source revision. See the adapter contract and its limitations.

For sessions outside the executor role policy above, any executable task still marked not done in any session blocks completion, and every defect that records no fixing revision blocks it too: of every product, unless the operator limited the session to some products by confirming a task contract scoped to them (contract.terms.scope with contract.terms.confirmedAt, written with oko tasks state --scope … --confirm by the operator); then only of those products, and the refusal counts the other products' open work as outside the session's scope. A scope a session wrote into its own contract limits nothing: the session answers for every product's open work. An entry in oko blockers, a blocked verdict, a judge outage after evidence, or a wait on other open work does not stand an item aside: only Oko recording a task done or withdrawn, or a defect fixed, removes it. A task Oko relates as duplicate-of another is counted once, as the original. The refusal names each session, ordinal and request, and then, separately, the open items that carry no pushed repair yet: those are written, committed and pushed without a build, so an answer that says the rest waits on a build is contradicted by the refusal itself.

When Oko's ruling register (oko rulings) holds a ruling on a listed defect or task, the refusal quotes it word for word with its session and message number and says to follow it and never ask the operator again or list it as a blocker or next step. The register is read as a file on this machine (OKO_RULING_REGISTER moves it); one that cannot be read is named in the refusal rather than left out.

block-one-off-repairs reads the same register for every build, compile and test run, and refuses while any open item carries no repair: a task with no commit or report recorded by oko tasks evidence, or a defect with no revision recorded by oko defects repaired. A code repair is only proven by a build, so building waits for every repair to exist, not for every item to close; the one build then proves them, and each item is closed or reopened on what it shows. The refusal lists the items that still carry no repair. A recorded revision counts as a repair only when it comes after the defect: when the defect's found_in names a commit of the same repository, the repair must descend from that commit and differ from it, so a fix committed before the defect was recorded still counts; otherwise the repair must be committed after the defect's found_at time. A revision this machine cannot resolve is counted as recorded. A build the operator consents to passes before that. His Oko ruling is read first: the newest ruling on build, build:<product>, no-build or no-build:<product> decides for the products built. Then his answer to a build-consent ask: tama build consent ask --target <product> --command <the build> files an Oko ask on subject build:<product> with two choices, zgoda na tę jedną budowę and nie, on the channels he chose. His consent answer admits one build of that product: the gate reads oko asks list, takes the newest consent answer on that subject it has not spent, admits the build, prints build admitted by the operator's answer to ask <id> on build:<product> at <time>, now spent and records the ask in ~/.shared-hooks/build_consent_spent.json, so the next build needs his next answer. A refusal, an ask still waiting, or a spent record that cannot be read admits nothing; the last says <path> is not a list of ask ids or <path> cannot be read on stderr. tama build consent ask without --target or --command is refused by name before Oko is asked. Otherwise the agent records the consent he gave in the conversation as the Tama session capability {"tool": "build", "actions": ["<product>"]} (or {"tool": "build"} for any product) with the lifetime he named — single-use, expires-at or current-session — and the gate lets a build through whose arguments name a granted product. For cargo the products are the -p/--package selections, so a consent to build Tama names tama-cli. For stado release submit --source PATH and stado build submit --source PATH the product is the product the checkout's .wisent-release.json declares (the name Stado builds it under, which a checkout whose directory name is not a product name declares), else the name of the checkout directory PATH resolves to; a relative path such as --source . is resolved against the directory the command runs in, and a path that names no existing directory establishes no product, so only a grant with no product list admits it. stado release submit --build ID names no product in its arguments, so the gate reads the product from the fleet's build record (stado build status ID --json); a build the fleet does not hold is admitted only by a grant with no product list. When the operator withdraws his consent, the agent runs tama sessions revoke-capability --session SESSION_ID, and the gate refuses the next build at once.

After producing and checking the real result, run oko tasks verify --before-stop --session SESSION_ID. Oko's independent Brama judge reads recorded calls and tool results as well as the answer, then saves each verdict. A claim or tracker update cannot replace that qualification. A later operator correction takes precedence. Answering the same refusal in prose does not release it: every later Stop repeats the open task identity until real work records evidence or Oko records a qualified blocker. A recorded judge outage only replaces the verify command with the instruction to record evidence; it does not make the task done.

Done and withdrawn tasks do not block. An unfinished task may pause only with Oko's qualified receipt: the matching task ordinal and request hash, transcript hash, actual failed call/result, independently checked permitted alternatives, cause, observed state and condition for resumption. Tama rejects a prose-only reason, unmatched receipt, missing operation or unchecked alternative. The refusal names the original task and the observations still required; a worker's claim or local “blocked” flag never grants permission to stop.

A report is not the work it describes

block-stop-on-own-work refuses an ending that reports instead of working, with no model: from the transcript, an ending said again after a refusal with no source changed, a plea without one command on the clipboard or with one that cannot run, and a defect recorded with no repair; from the answer itself, the turn-end attestation it carries word for word (no invented limit, no decision handed back, no own work under blockers, and the rest). Every refusal and the journeys that prove them are on their own page: endings a report cannot replace.

A correction is a record, not words

block-unlinked-operator-messages refuses the end of a turn while any operator message of the session is linked to no Oko record. It runs oko rulings unlinked --session SESSION_ID, which reads the session's transcript and names, for each of the operator's messages, the ruling recorded from it or the defect its task is related to; a message linked to neither is a correction that stayed words, the lesson he had to teach again in the next session. Oko's own refusal is relayed, with the two commands that link the message: oko rulings record --session SESSION_ID --ordinal N --subject <task or defect> --by SESSION_ID, or oko tasks relate <task> … <defect> for the defect that names the rule and its mechanism (oko rulings enforce, oko rulings audit). No model decides it, so the gate holds while no model answers. A stop payload without a session is refused; an Oko that cannot be run is refused by name; a machine without the Oko CLI has no register to read and the gate says nothing there. An operator stop order

Every guard above releases the turn only through a tool call: finish the tracker, read the ledger, treat a denial, record evidence. When the operator has written nie koduj (or do not code, nic nie rob, stop coding, a bare stop), every tool call is forbidden, and a session would answer turn after turn with the same lines while the guards refused each one. So block-stop-with-open-work, block-stale-assignment, block-untreated-block-stop, block-stop-with-claimed-work, block-stop-after-unresolved-hook-defect, block-stop-on-own-work and check-open-items-with-model stand down while a stop order stands, and print <hook>: the operator's stop order stands ("…"); ending the turn obeys it, so this guard does not refuse it. on stderr so the release is visible in the hook evidence.

The order stands from the operator's newest such message until the operator gives a new task — a message Oko records in the session's ledger. Questions, remarks and repeated stop orders in between do not lift it; a local tracker entry never does. Without a readable ledger only the newest operator message decides, so an unreadable Oko cannot revive a lifted order. Harness-injected user-role records (todo reminders, hook continuations, attribution agent) are not the operator speaking. The phrase list lives in tama_hook_tools::assignment::stop_order; a new form is added in a commit that quotes the message that needed it.

The real journey is tests/assignment/assignment.test.ts (bun run test:assignment): an open tracker item blocks, the order lets the turn end, questions do not lift it, a task Oko records lifts it and the guard refuses again naming the item, and a missing ledger falls back to the newest message.

Oko keeps diagnosis and resumption in its own ledger. Five unsuccessful rounds trigger diagnosis, not a demand for a person. The Tasks screen shows the same cause, checked operations, resumption condition and next automatic check as the CLI. Missing identity, transcript, ledger, or recognized task status prints TAMA_HOOK_INFRASTRUCTURE: check-open-items-with-model: <reason> and exits 70. Activation reports taskLedger: available, completionAllowed and pendingTasks; open work is not an unavailable dependency.

The OMP adapter forwards an explicit decision: block. OMP must keep that refusal beyond its eight-round advisory continuation limit and give it priority over advisory continue: true results. Explicit user interruption still stops the run; queued stop handlers must not restart it. The hook release and OMP host are separate dependencies. Updating hooks alone cannot repair an older host's continuation limit.
